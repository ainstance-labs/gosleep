## Per-scenario interpretation

### SC-11 — suspect-handoff (0.75 → 1.0): FIXED

The v2 edit added a concrete, step-by-step description of exactly what to write to STATE when a suspect handoff arrives and when a late-arriving worker ID needs to be resolved (with verbatim example lines). The pass rate moved from 0.75 to 1.0 — a clean fix. This proves the hypothesis from the v1 analysis: **concrete mechanical edits (exact fields, example strings) reliably change behavior** when the target behavior is a specific procedure the model has to execute.

### SC-12 — cost-telemetry (0.25 → 0.5): improved, partial

The v2 "append a TELEMETRY line per cycle" edit with a verbatim format string moved the score from 0.25 to 0.5. The improvement is real but partial. Two gaps remain: (a) the agent still does not attempt the sanctioned recovery path — reading the dead workers' ORCHESTRATOR REPORT blocks via a range-read to reconstruct already-lost cost data; and (b) the agent does not commit to a forward process fix (updating the brief/cycle template so future cycles emit TELEMETRY). Notably, both the control run (SC-12 alone, 1538) and the full run (1544) scored 0.5 — this is a stable partial pass, not noise. The edit helped with the "going forward" instrumentation but did not reach the recovery and process-fix behaviors.

### SC-09 — stalled-at-pr (0.0 → 0.0): unchanged, with a notable inversion

The v2 edit added a new rule mandating exactly ONE concrete nudge at the stalled-PR boundary, with forbidden-phrase examples ("I'll keep monitoring", "wait and see"). The score did not move — still 0.0. The anti-pattern the judge flagged in both samples was the same: a vague "keep monitoring" posture with no single committed nudge.

The notable fact here is the **RED 1.0 > GREEN 0.0 inversion**: without the skill, agents naturally send a concrete nudge (passing the scenario). With the skill loaded, they default to the vague patience posture (failing it). The skill's existing, dominant guidance — "idle is not stuck", "don't nudge prematurely", "don't kill productive workers" — appears to overwhelm the newly-added single-nudge rule. Adding a competing rule did not win against the dominant framing. What the skill needs is not another paragraph but an ordered decision sequence: patience-window-elapsed? → commit to exactly ONE nudge → escalate. Until the tension between "be patient" and "act at the boundary" is resolved explicitly — as a decision table, not parallel paragraphs — the patience guidance will keep winning. The RED>GREEN inversion also warrants re-examining the SC-09 scenario and rubric to confirm they are calibrated correctly for the intended behavior.

### SC-19 — orchestrator-rollover (0.0 → 0.0): unchanged outcome, shifted failure mode

The v2 edit added a hard gate: never roll over or start a fresh orchestrator while any worker is alive; terminate the worker and confirm it is dead first. The pass rate did not move — still 0.0. But the failure mode changed. In v1, agents rolled over while a worker (cycle-13) was still alive, orphaning it. In v2, agents now issue a `shutdown_request` to terminate a productive worker early, just so the orchestrator can reach a clean boundary and roll sooner. The fix was applied but misread: agents understood "terminate first, then roll" and treated forced termination as the correct path. The underlying prohibition — **do not force a clean boundary by killing live work** — was not stated. A correct fix must explicitly forbid killing-to-roll as itself an anti-pattern, and require waiting for the worker's natural COMPLETE report before rolling. Only a genuine boundary (worker done by its own logic) is a valid rollover point.

## Meta-finding

**Concrete skill-text edits reliably fix MECHANICAL behaviors; they underperform for JUDGMENT-UNDER-TENSION behaviors where the skill holds competing principles.**

SC-11 is a mechanical behavior: write these exact fields in STATE in this order. Adding an example string fixed it outright. SC-12 is partially mechanical and partially procedural — the instrumentation part improved; the recovery and process-fix parts (which require the agent to reason about what "fixing the process" means) did not.

SC-09 and SC-19 are both judgment-under-tension: the skill holds strong guidance in one direction (patience, don't terminate workers prematurely) and the new rule pushes in the other direction (act now, terminate first). In both cases the new rule lost to the existing strong framing. For these behaviors, a competing paragraph is not sufficient — you need to resolve the tension explicitly (a prioritized decision sequence, a decision table, or a structural harness-level constraint that removes the choice from the agent entirely).

N=2 is also coarse at this sample size: only 0/0.5/1.0 are expressible. Findings at 0.0 and 1.0 are reliable; a 0.5 reading deserves replication at N=4 before treating it as stable.

## Recommendation

**Stop autonomous skill-text iteration. Land the two wins via the PR. Defer SC-09 and SC-19 to an owner approach decision.**

SC-11 is fixed at 1.0 — land it. SC-12 improved from 0.25 to 0.5 — partial progress is worth capturing. SC-09 and SC-19 are unmoved across two full hardening epics (GSL-7 v1 + GSL-24 v2). The specific failure modes are now well-understood (SC-09: tension not resolved; SC-19: killing-to-roll not forbidden), but another round of competing-rule text edits is unlikely to break the pattern.

Owner options for SC-09 and SC-19:

**(a) v3 skill edit — but targeted at the specific failure mode:** For SC-09, a single ordered decision sequence (not a new paragraph) that makes the patience-vs-nudge trade-off deterministic at the boundary. For SC-19, an explicit "killing-to-roll is itself the orphan anti-pattern" statement. If this approach is taken, run at N=4 to get stable readings.

**(b) Accept a structural limit of the skill-text approach for judgment-under-tension behaviors.** Some behaviors may require harness-level enforcement (e.g., the runner could refuse to issue a shutdown_request mid-cycle) rather than relying on skill text alone.

**(c) Re-examine SC-09 calibration.** The RED>GREEN inversion is unusual and may indicate the scenario or rubric is not cleanly measuring the intended behavior. A calibration review before investing further in a v3 fix is prudent.
