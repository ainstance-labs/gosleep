## 0. Терминология (исправлена по требованию владельца)

- **Production skills** — `~/.claude/skills/<name>/`. Ими пользуются ВСЕ оркестраторы и все
  проекты этой машины. Правка здесь — изменение продакшна вживую, без ревью и без отката.
  **Агентам правка запрещена строжайше.** Слово «рабочая копия» применительно к ним — ошибка
  оркестратора, изъято.
- **Development skills** — `skill/<name>/` в репозитории gosleep. Это место разработки: сюда
  вносятся правки, здесь они ревьюятся, отсюда попадают в git с историей.
- **Publish** — перенос development → production. Совершается ТОЛЬКО владельцем, явным действием,
  после ревью.

## 1. Почему запрет обоснован (факт, а не предположение)

Правила ответа оркестратора, записанные в production-скилле `orchestrating-delivery-agents`,
однажды уже парализовали работу: владелец перестал видеть сообщения оркестратора при живом
флоте. Причина — противоречие внутри скилла: правило требовало «ход кончается текстом», а
рабочий пример показывал порядок, при котором последним действием оказывался вызов планировщика,
чей ответ («больше делать нечего») обрывал ход до текста. Ошибка в продакшн-скилле
распространяется на все проекты сразу и обнаруживается только по симптому.

**Нарушение, которое обязан признать текущий оркестратор:** 2026-08-02, по устной команде
владельца «поправь скилл», правки были внесены НАПРЯМУЮ в production-копию
`~/.claude/skills/orchestrating-delivery-agents/SKILL.md` (порядок хода + 6 замен эрраты
GSL-178). Команда владельца была, но правильный путь — правка в `skill/` и publish владельцем —
не существовал, и оркестратор его не восстановил, а обошёл. Судьба этих правок — пункт 4 плана.

## 3. Целевой процесс

```
урок/находка → задача в Jira → правка в skill/<name>/ → коммит (один на правку, ключ задачи в
сообщении) → запись в реестр изменений → админка показывает diff и ждёт → ВЛАДЕЛЕЦ проверяет →
владелец публикует одной командой → publish пишет в реестр «опубликовано», делает бэкап
production и переносит ТОЛЬКО названный скилл
```

Свойства: агент физически не может опубликовать (publish требует явного подтверждения владельца);
каждая правка имеет автора, задачу, коммит и причину; откат возможен из бэкапа и из git.

## 5. Этапы работ (предлагаемый эпик)

1. **Догон development** — перенести production-версии в `skill/` (обратная синхронизация
   global→local, разово, по команде владельца), включая `tmux-agents-orchestration`, которого в
   git нет; каждый скилл — отдельным коммитом с указанием, что именно догнали. После этого
   `skill/` = истина, и вся дальнейшая разработка идёт только там.
2. **Реестр изменений** — `docs/skills/CHANGELOG.jsonl`: одна строка на правку (дата, скилл,
   задача Jira, коммит, урок-первопричина, статус: draft / reviewed / published). Пишется
   агентом при правке, дополняется при публикации.
3. **Publish-инструмент** — `tools/skills/publish.sh <name>`: показывает diff development против
   production, требует подтверждения владельца, делает бэкап production в
   `docs/skills/backups/<name>-<дата>/`, синхронизирует ОДИН названный скилл, дописывает строку в
   реестр. Никаких массовых операций, `--all` не существует. Агенту запуск запрещён правилом и
   проверкой на владельца.
4. **Админка (страница в лаборатории)** — раздел «Скиллы»: список скиллов, для каждого — статус
   (совпадает с production / есть неопубликованные правки), список правок из реестра с уроком и
   ссылками на задачу и коммит, отображение diff, и точная команда публикации для копирования.
   Кнопка «опубликовать» в статическом виде невозможна — публикация остаётся командой владельца;
   если позже включим интерактивную версию веба, кнопка будет вызывать тот же publish.
5. **Проверки** — тест, который падает, если агент изменил файл в `~/.claude/skills/`; тест на
   формат реестра; правило в CLAUDE.md и в скиллах: «production скиллы правит только владелец
   через publish».
6. **Приёмка** — на живом примере: взять реальный урок (например, порядок хода), провести его
   полным путём development → реестр → админка → publish, показать в отчёте все следы.
