# План: система работы со скиллами — репозиторий развивает, владелец публикует

**Статус: ПРЕДЛОЖЕНИЕ на согласование владельцу (2026-08-03).** План описывает будущий
процесс. Ничего из перечисленного не выполняется до команды владельца.

## 0. Терминология

- **Production skills** — `~/.claude/skills/<name>/`. Ими пользуются ВСЕ оркестраторы и все
  проекты этой машины. Правка здесь — изменение продакшна вживую, без ревью и без отката.
  **Агентам правка запрещена строжайше и ни при каких командах.**
- **Development skills** — `skill/<name>/` в репозитории gosleep. Это место разработки:
  сюда вносятся правки, здесь они ревьюятся, отсюда попадают в git с автором и историей.
- **Publish** — перенос development → production. Совершается ТОЛЬКО владельцем, явным
  действием (кнопкой в админке), после ревью.

## 1. Принцип системы

Развитие скилла — это работа с development-копией в репозитории. Ничего иного. Production
не редактируется агентами ни при каких обстоятельствах, ни при каких формулировках команды.
Любое улучшение (урок, эррата, новый пример) — правка в `skill/<name>/`, коммит с ключом
задачи, запись в реестр изменений.

## 2. Публикация — только ручная, только владельцем

Публикация из development в production — **единственная точка процесса, где действует
человек, и этот человек — только владелец**. Форма действия — нажатие кнопки «Опубликовать»
в админке лаборатории напротив нужного скилла. Агенты в шаге публикации не участвуют
вообще: ни как исполнители, ни как «помощники подтвердить». Это не строка в списке
правил, а инвариант, вокруг которого строится всё остальное.

## 4. Целевой процесс

```
урок/находка → задача в Jira → правка в skill/<name>/ → коммит (один на правку, ключ
задачи в сообщении) → запись в реестр изменений → админка показывает diff и ждёт →
ВЛАДЕЛЕЦ нажимает кнопку «Опубликовать» → publish пишет в реестр «опубликовано», делает
бэкап production и переносит ТОЛЬКО названный скилл
```

Свойства: агент физически не может опубликовать (кнопка — интерфейс владельца, а
CLI-инструмент проверяет владельца); каждая правка имеет автора, задачу, коммит и причину;
откат возможен из бэкапа и из git.

## 5. Админка — раздел «Скиллы» в веб-лаборатории

Отдельная страница в лаборатории. Для каждого скилла:

- **Статус:** «совпадает с production» или «есть неопубликованные правки».
- **История урок → правка → задача → коммит:** строки из реестра изменений, каждая с
  ссылкой на задачу Jira и коммит.
- **Diff** локальной копии против production — просмотр прямо на странице.
- **Кнопка «Опубликовать»** на скилл — единственный интерактивный элемент админки.

**Техническое следствие (честно и явно):** сегодняшний веб — статический сайт,
генерируется хроникёром. Статическая страница не может выполнять команды на машине
владельца. Значит кнопка «Опубликовать» требует **локального сервера админки** — процесса,
который слушает на localhost, принимает нажатие кнопки и вызывает CLI-инструмент
`publish`. Это отдельный этап работ в плане (этап 4 ниже), а не допущение и не «когда-нибудь».

## 6. Реестр изменений — источник данных для админки

`docs/skills/CHANGELOG.jsonl` — одна строка на правку в развитии скилла: дата, скилл,
задача Jira, коммит, урок-первопричина, статус (`draft` / `reviewed` / `published`).
Пишется агентом при правке development-копии, дополняется при публикации. Админка читает
этот файл и рисует из него историю и статус.

## 7. Этапы работ (эпик GSL-174)

1. **Догон development** — перенести production-версии в `skill/` (обратная синхронизация
   global → local, разово, действие владельца), включая `tmux-agents-orchestration`,
   которого в git нет; каждый скилл — отдельным коммитом с указанием, что именно догнали.
   После этого `skill/` = истина, и вся дальнейшая разработка идёт только там.
2. **Реестр изменений** — `docs/skills/CHANGELOG.jsonl`; формат зафиксирован,
   валидация на схему.
3. **CLI publish-инструмент** — `tools/skills/publish.sh <name>`: показывает diff,
   требует явного подтверждения владельца, делает бэкап production в
   `docs/skills/backups/<name>-<дата>/`, синхронизирует ОДИН названный скилл, дописывает
   строку в реестр. Никаких массовых операций, `--all` не существует. Агенту запуск
   запрещён правилом и проверкой на владельца.
4. **Локальный сервер админки + кнопка публикации** — процесс на localhost, отдающий
   страницу «Скиллы» и обрабатывающий нажатие кнопки. Кнопка вызывает тот же
   `publish.sh` из этапа 3, показывает результат в интерфейсе. Без этого этапа кнопка в
   статическом дашборде остаётся неактивной, а публикация — командой в терминале
   владельца.
5. **Админка UI** — страница «Скиллы»: список, статус, история из реестра, diff, кнопка.
   Пока сервер (этап 4) не запущен, страница генерируется хроникёром в статическом виде
   и показывает точную команду для копирования вместо активной кнопки.
6. **Проверки** — тест, который падает, если агент изменил файл в `~/.claude/skills/`;
   тест на формат реестра; правило в `CLAUDE.md` и в самих скиллах: «production скиллы
   правит только владелец через админку».
7. **Приёмка** — на живом примере: взять реальный урок, провести его полным путём
   development → реестр → админка → publish владельцем, показать в отчёте все следы.
