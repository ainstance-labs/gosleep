# Аналитика: почему столько агентов, был ли смысл, и как тестировать дешевле

Дата: 2026-06-09 · Jira: TLM-70

## 1. Откуда взялись 240 GREEN-judge (математика)

Раннер на КАЖДЫЙ сценарий поднимает 4 группы агентов:
`N RED-ответов + N GREEN-ответов + N судей-для-RED + N судей-для-GREEN`.

При N=6 и 20 сценариях один полный прогон =
`20 × (6+6+6+6) = 20 × 24 = 480 агентов`, из них:
- ответы (work): 120 RED + 120 GREEN = **240**
- судьи (eval): 120 RED-judge + 120 GREEN-judge = **240 (ровно половина!)**

GREEN-judge за один полный прогон = `20 × 6 = 120`. А полных прогонов было **два** (первый + resume после недельного лимита) → **240 GREEN-judge**. Вот откуда число.

### Полная стоимость eval (по телеметрии)
| Прогон | Агенты | Токены |
|---|---|---|
| smoke | 33 | 0.72M |
| full-attempt-1 (баг args → 2 сценария) | 33 | 0.78M |
| full-run | 480 | 9.07M |
| full-resume | 480 | 10.05M |
| **Итого eval** | **~1026** | **~20.6M** |

## 2. Был ли смысл? Да, но переплатили в ~2–3 раза

**Смысл был:** двурукий RED/GREEN + судья дали честные данные — нашли **8 реальных дыр** и доказали ценность скилла (на злых сценариях лифт 0.00→1.00). Это не «потрачено зря».

**Но стоимость раздута тремя вещами:**
1. **Судья на КАЖДЫЙ ответ** — судьи это 50% всех агентов. Один judge-агент на один ответ — самый дорогой и самый легко устранимый перерасход.
2. **Двойной полный прогон** — resume после недельного лимита фактически перегнал почти весь suite заново (~10M токенов ≈ дубль первого). Это чистая потеря из-за того, что N=6 не влез в лимит.
3. **RED гоняли каждый раз** — базовая линия не меняется, пока не меняется сценарий. Гонять её при каждом прогоне скилла — лишнее.

## 3. Как тестировать дешевле (тот же сигнал, ~⅓ токенов)

| Оптимизация | Эффект |
|---|---|
| **Батчить судью** — один judge-агент оценивает ВСЕ N ответов руки за один вызов (или оба arm'а сценария разом) | судьи с ~12/сценарий → ~1–2/сценарий; минус ~40% агентов |
| **Кэшировать RED** — прогнать базу один раз, переиспользовать; при правке скилла гонять только GREEN | минус ещё ~⅓ на повторных прогонах |
| **Детерминированные проверки вместо LLM-судьи там, где можно** — большинство наших сценариев это да/нет («поднял ли дубликат?», «убил ли воркера?»). Это проверяется ассерциями по структурному ответу, без судьи и без сэмплирования-шума | убирает целый класс judge-агентов И шум N |
| **Right-size N** — N=6 шумит (SC-03 скакал 0.67↔1.0). Для да/нет-решений хватит детерминированной проверки (N не нужен); LLM-судья + N — только для нюансных | меньше прогонов |
| **Тиры прогонов** — на каждую правку: быстрый smoke только по затронутым сценариям (низкий N); полный suite — редко | не гонять 480 на каждый чих |
| **Не передваивать** — держать один прогон в пределах лимита (меньше N / батч), чтобы resume не передвигал весь suite | минус целый дубль |

**Целевой полный прогон с батч-судьёй:** ~240 ответов + ~20 батч-судей ≈ **260 агентов вместо 480** (≈ −46%). С кэшем RED повторный (GREEN-only) прогон ≈ **140 агентов** (≈ −70%).

## 4. Методики тестирования — что нормально, что странно

Наш подход (**LLM-as-judge, two-arm RED/GREEN, pass-rate по N сэмплам**) — это **стандартная** методика для недетерминированного поведения, не странная сама по себе. Странной была наша РЕАЛИЗАЦИЯ (судья на каждый ответ, bespoke-воркфлоу, двойной прогон). Полный спектр подходов:

1. **Детерминированные ассерции / rubric-as-code** — проверяем структурный ответ (вызвал ли инструмент X, избегал ли Y) кодом. Дёшево, быстро, без шума. Лучше всего для чётких решений (большинство наших).
2. **LLM-as-judge** (наш) — для нюансного/открытого. Стандарт, но платный и шумный. Лучшие практики: батчить, сильный судья, калибровать по человеческим меткам, structured rubric.
3. **Pairwise / preference (A/B)** — судья СРАВНИВАЕТ ответ RED vs GREEN напрямую. Надёжнее абсолютных оценок, и сразу показывает лифт.
4. **Golden / reference answers** — сравнение с эталонным ответом (точное или семантическое).
5. **Trajectory / process evals** — оценивают всю траекторию (последовательность tool-вызовов), а не только финальный ответ. Важно для агентов/harness.
6. **Adversarial / red-teaming** — генерим атаки, чтобы сломать скилл (мы это частично делали в hardening-воркфлоу).
7. **Metamorphic / property-based** — инварианты, которые должны держаться при вариациях входа.
8. **Human eval** — золотой стандарт для калибровки судьи; дорого, точечно.

### Готовые фреймворки (вместо нашего самописного воркфлоу)
- **promptfoo** — декларативные тест-кейсы + ассерции (детерминированные И LLM-graded), запуск в CI. Ближе всего к «профессиональному eval-харнессу».
- **Inspect** (UK AISI) — серьёзный фреймворк для агентных/поведенческих evals.
- **OpenAI Evals**, **Braintrust**, **LangSmith**, **DeepEval** — реестры тест-кейсов, judge, трекинг регрессий, CI.
- (Названия/возможности стоит сверить с актуальной докой при выборе — не из памяти.)

## 5. Рекомендация (целевой дизайн нашего тестирования)
1. Перевести чёткие сценарии (да/нет-решения) на **детерминированные ассерции** по структурному `next_action` — убирает большинство судей и шум N.
2. Оставить **LLM-judge только для нюансных** сценариев; там — **батч-судья** (1 вызов на сценарий) + **pairwise RED vs GREEN**.
3. **RED кэшировать** (база меняется только со сценарием). Повседневно гонять GREEN-only.
4. **Тиры:** smoke (затронутые сценарии, низкий N) на каждую правку → полный suite редко.
5. Рассмотреть переезд на **promptfoo/Inspect** — меньше своего кода, CI-ready, дешевле в эксплуатации.

**Итог:** сигнал мы получили ценный, но за него переплатили ~2–3×. Перечисленное выше даёт тот же сигнал за ~⅓ токенов и без шума N на чётких сценариях.
