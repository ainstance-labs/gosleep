## 1. Reference: the tasty-lunch docs system — what "good" looks like, and how much is manual

> Source: full traversal of `/Users/romanlidovskyi/Documents/dev/tasty/tasty-lunch/docs/` (828 files on disk;
> repo = 523 commits over ~1 month, solo owner + AI orchestrator delivery, same skills lineage as gosleep).
> Traversal delegated to one read-only Explore subagent (sonnet), 2026-07-07.

### 1.1 The shape: 17 directories, 4 kinds of memory

| Kind | Dirs | Character |
|---|---|---|
| **Planning contract** (curated, CI-checked) | `plan/` (8 chapters), `adr/` (16, `NNNN-kebab`), `prd/` (19, per phase), `wiki/` | Cross-link/anchor integrity ENFORCED by `pnpm check:docs` (`scripts/check-docs-anchors.mjs`) wired into `pnpm verify` — build FAILS on a dangling ref, missing anchor, or forbidden glyph |
| **Append-only delivery log** | `dev_history/` (**197 files**, per-task `TLM-NNN-phaseNN-cycleN-topic.md`), `handoff/` (**99 files**, `NN-YYYY-MM-DD-handoff-<topic>`, 01→94+), `lessons-learned/` (19), `process/` (RCAs), `prompts/` (verbatim owner briefs) | Excluded from the anchor checker by design ("logs, not the planning contract"); indexed by hand-maintained per-dir README tables updated in the same commit that adds each entry |
| **Live state** | `handoff/ORCHESTRATION-STATE.md` + `ORCHESTRATION-STATE-archive-*.md` (267KB archive!), **`OWNER-QUESTIONS.md`, `OWNER-DECISIONS-*.md`** | Continuously overwritten dashboard + an async owner decision-queue — questions accumulate, orchestrator defaults-and-proceeds, owner answers in the morning |
| **Ephemeral / scratch** | `reviews/` (47, git-ignored), `workflow/` (cycle prompts, git-ignored), most of `reports/` (~19% committed; the whole 155-file `ai-assistant-v3/` never landed) | Deliberately outside git; large dead-weight surface |

### 1.2 Template contracts worth copying verbatim

- **Handoff:** meta line (Date/Cycle/Branch/commit) → TL;DR → What-shipped → **`## ⚠️ Honest gap found`** (institutionalized honesty) → Gate+state (exact command + exit code) → Next → **machine-parseable telemetry footer**: `CYCLE_ID report-p23 · HANDOFF_FILE docs/handoff/92-… · CYCLE_STATUS COMPLETE · BLOCKED_ON_HUMAN none`. A fresh agent (or a script) can grep the footer — this is a proto-machine-layer living inside a human doc.
- **Dev-history:** opens with a greppable one-line blockquote (`> 2026-07-06 — TLM-313 · Phase 23 · cycle p23-c1 · [AI][server] …`) then the same five human sections gosleep uses, then `## Technical reference` (commit, files, verified-by-running, Jira/GH/PRD links). The most uniform template across 197 files — uniformity itself is the evidence that convention-enforcement works at scale.
- **PRD provenance tags:** every requirement is marked **OWNER-RATIFIED / OWNER-ACQUIESCED-DEFAULT / OWNER-CONFIRM-AT-KICKOFF**, plus a global source-wish→phase→requirement-ID traceability matrix in `prd/README.md`. This is the ancestor of the decision-manifest idea in §4: the system already distinguishes "owner said so" from "we defaulted".
- **process/ RCAs:** the orchestrator writes postmortems about **its own failures** (bilingual owner summary + timeline + root causes + `## Standing rules adopted`); a report footer literally reads *"Generated by the orchestrator as a self-analysis of its own failure."* Lessons-learned files each cite a named real incident and close with a rule carried into the next cycle's instructions — a feedback loop with teeth.
- **Reports versioned like software:** `ai-assistant` v1→v4, each superseding with explicit corrections notes; only v1 has real generator scripts (`ai-report-capture.mjs` Playwright evidence harness → `capture-results.json`; `ai-report-postprocess.mjs` idempotently regex-injects MEASURED data into the HTML). v2–v4 are bespoke hand-styled HTML — consistency depends on the agent copying the previous file.

### 1.3 Manual vs automated — the honest split

| Layer | Verdict |
|---|---|
| Handoffs, dev_history, reviews | **Agent-written EVERY cycle by protocol** — the cycle prompts hard-code "invoke `/handoff`"; NOT owner-asked. The "owner asks for a handoff" era is already over in tasty-lunch. |
| Plan/ADR/PRD link integrity | **Genuinely automated** (CI gate). The only *mechanical* automation in the tree. |
| Report evidence (v1 only) | Scripted capture + idempotent injection; narrative agent-written; **owner sign-off gate** on a `SAMPLE.md` before scaling scenario pages to 60. |
| Wiki/status hub | **One-time hand-built, then ABANDONED** — still says "Phase 1 in progress, 1 of 9 epics done" while delivery reached Phase 23. No generator, no CI check → rotted within a month. |
| Owner Q&A | Semi-manual: `OWNER-QUESTIONS.md` accumulates, owner answers in-file; no typing, no push, no deadline semantics. |

### 1.4 What this teaches the Laboratory

1. **Conventions scale; hubs rot.** 197 dev_history files prove skill-enforced conventions produce the *narrative* layer reliably. The one artifact that required *regeneration* (the wiki status hub) died immediately. → The Laboratory's dashboard MUST be script-regenerated from data, never hand-edited HTML.
2. **The machine layer is already trying to be born** — telemetry footers, greppable blockquote headers, LIVE-STATUS grammar. tasty-lunch put machine-readable lines *inside* Markdown; the Laboratory should invert: machine events in JSONL, Markdown generated/decorated from them.
3. **The owner decision-queue exists and works** (OWNER-QUESTIONS/OWNER-DECISIONS, "default-and-proceed, answer in the morning") but is untyped, unpushed, undeadlined — §4 is its systematization.
4. **The residual manual toil is NOT "write the handoff"** (solved). It is: keeping the hub current, regenerating reports, cross-indexing artifacts, translating (RU mirrors), triaging questions. All mechanical, all automatable.
5. **Anti-patterns to avoid:** 81% of `reports/` never committed (scratch policy needed); no root docs README/map; report generators abandoned after v1; per-dir README indexes hand-maintained (should be generated).

### 2.2 What the conventions already guarantee (the strong base)

1. **Every task leaves a paper trail by rule, not by request**: one commit `GSL-N …`, one dev_history file, Jira transition, GH mirror. The delivery-workflow skill makes documentation *part of the definition of done* — this is the single most important precedent for the Laboratory: *docs as a gate, not a favor*.
2. **The orchestrator ledger (ORCHESTRATION-STATE.md) is a real-time, append-only, machine-parsable-ish status surface** — LIVE-STATUS one-liner, cumulative TELEMETRY lines with a fixed grammar (`cycle=N worker=… tokens_out=…`), dated log with task-keyed bullets. It already IS a proto-event-stream; it's just trapped in one Markdown file, orchestrator-writable only.
3. **Handoffs have a two-layer contract** (Part 1 plain-words for the human, Part 2 formal for the machine/agent) — exactly the human-layer/machine-layer split the Laboratory needs, already culturally accepted.
4. **Atomic write discipline** (same-dir hidden temp + rename) is standard for STATE and handoffs — the Laboratory's event log can inherit it directly.
5. **Telemetry is mandatory and gap-flagged** (`tokens_this_cycle=UNRECOVERED — gap flagged`) — honest accounting culture that a cost dashboard can trust.

### 2.3 The gaps (what the Laboratory must add)

1. **No machine-readable layer.** Everything is Markdown prose + one `data/runs.json` for evals. LIVE-STATUS and TELEMETRY have a *grammar* but no *schema*; a dashboard would have to regex a Markdown file. There is no `events.jsonl`, no `status.json`.
2. **No timeline/event feed.** Reconstructing "what happened tonight" = reading the STATE log + N handoffs + git log + Jira. Nothing records events *as they happen* in one append-only place with timestamps. (Incidents like the 2026-07-07 `kill-pane -a` are documented only as prose lessons.)
3. **No aggregated "morning view".** The At-a-glance section of STATE is the closest thing, but it's overwritten (no history), has no links out to the artifacts it mentions, and mixes owner-facing info with orchestrator self-instructions (⛔ directives).
4. **Questions to the owner have no home.** Today a blocker becomes `BLOCKED_ON_HUMAN` + AskUserQuestion (synchronous, dies with the session) or a "Blocked on the human" section in a handoff (buried, one per file). Nothing queues questions across workers/cycles, types them, or tracks answered/unanswered. **This is the #1 autonomy gap: at night AskUserQuestion just blocks a pane.**
5. **Reports don't self-update.** `docs/report/` has generators but no trigger wiring them to delivery events (a landed task doesn't refresh any dashboard).
6. **Reviews/handoffs/dev_history are not indexed together.** Each dir has (at best) its own README; nothing cross-links "task GSL-38 → commit f12092e → dev_history file → review finding → handoff 11 → Jira/GH".
7. **Worker-side telemetry is self-reported prose** in a SendMessage — the STATE file gets it, but nothing validates or aggregates it beyond the running total line.
8. **No push/notification path at all** (mirrors autosk's gap noted in `01-autosk.md` §8): a parked question at 01:00 is discovered at 09:00 only if the owner opens the terminal.

## 3. The Laboratory: auto-documentation system design

> Design goal: **the owner sleeps; the system works AND documents itself; in the morning one place shows
> everything.** Inputs: §1 (what conventions already produce), §2 (gaps), the verified Claude Code hooks
> catalog (code.claude.com/docs/en/hooks, fetched 2026-07-07), and the repo's own prior drafts
> `docs/design/event-schema.md` + `docs/design/web-harness-design.md`, which this section turns into a
> concrete, buildable plan.

### 3.1 The core thesis: three tiers of decreasing determinism

The tasty-lunch evidence (§1.4) sorts every documentation artifact by *how it must be produced*:

| Tier | Producer | Determinism | Cost | What it generates |
|---|---|---|---|---|
| **T1 — Events** | **Claude Code hooks** (`.claude/settings.json`, committable; `async: true` command handlers) | Mechanical — fires whether or not the model cooperates | **0 tokens**, ~0 latency | The timeline: session/worker lifecycle, tool activity, commits, Jira transitions, task create/complete, failures |
| **T2 — Narrative** | Agents by **convention** (existing skills: `handoff`, `delivery-workflow` dev_history, reviewer reports, RCA/lessons) | Behavioral — enforced by briefs + evals (gosleep's own specialty) | Already paid (part of delivery) | Handoffs, dev_history, reviews, RCAs — the human story |
| **T3 — Synthesis** | A **chronicler**: scheduled/boundary-triggered generation — build scripts + a bounded `claude -p` glue job (exactly the sanctioned use per `03` §3-B) or a cheap-tier teammate | Scripted trigger, model-assisted content | Small, budgeted (`--max-budget-usd`) | Dashboard regeneration, indexes, the morning digest, cross-links, freshness checks |

The wiki-rot lesson (§1.4-1) maps to tiers: tasty-lunch had T2 without T1/T3, so anything needing *regeneration* died. gosleep's `docs/report/` has T3 scripts without T1 data or triggers. The Laboratory = wiring all three.

### 3.2 Tier 1 — the deterministic event layer (hooks → `events.jsonl`)

Adopt the envelope from `docs/design/event-schema.md` (`{ts, run_id, seq, actor, type, data}` — add
`session_id`/`agent_id` from hook input). Its "verify hook capabilities at build time" caveat is now resolved —
the current hooks catalog covers every event type it proposed:

| event-schema.md type | Concrete hook (verified 2026-07-07) |
|---|---|
| `agent.spawned` / `agent.terminated` | `SubagentStart` / `SubagentStop` (carry `agent_type`, `agent_id`); `SessionStart` / `SessionEnd` for panes |
| `agent.idle` | **`TeammateIdle`** — fires as an Agent-Teams teammate goes idle (the pulse's blind spot, now free) |
| `tool.call` | `PostToolUse` with matchers — e.g. `Bash` filtered by `if: "Bash(git commit *)"` → `vcs.commit`; matcher `mcp__atlassian__.*` → `tracker.issue.*` |
| `cycle.*` / `handoff.written` | `PostToolUse` matcher `Write\|Edit` with `if` on `docs/handoff/*` paths; plus explicit orchestrator log-writes (below) |
| failures / quota | **`StopFailure`** with matchers `rate_limit\|overloaded\|server_error` — the quota-window detector `04` §3.6 wants, for free |
| questions/permissions | `Notification` (matcher `permission_prompt`/`idle_prompt`), `PermissionRequest`, `PermissionDenied` |
| task board | `TaskCreated` / `TaskCompleted` |
| context health | `PreCompact` / `PostCompact` (a compaction event on the orchestrator = a red flag per the orchestrating skill) |

Mechanics: each hook = `{type: "command", async: true, command: ".claude/hooks/lab-log.sh"}`; the script
reads the hook JSON from stdin, normalizes to the envelope, and appends one line to
`docs/lab/events/YYYY-MM-DD.jsonl` (O_APPEND single-line writes are atomic enough at this volume; daily files
keep any consumer read cheap). Every hook input already carries `session_id`, `agent_id`, `agent_type`, `cwd` —
attribution per worker **without any model cooperation**. Two producers complement the hooks:
- **Explicit emits:** orchestrator/workers append semantic events the hooks can't infer (`cycle.started`,
  `question.posed`, `decision.made`, `verify.verdict`) via a one-line `lab-emit` helper (same envelope). This
  is warren's "questions are events, not modal dialogs" pattern (`04` §3.7 / `02`).
- **Poll-fill (T3):** the chronicler reconciles `gh pr list` / Jira JQL / `git log` into events the local hooks
  missed (e.g. a PR merged from the web UI) — same reconcile-don't-trust philosophy as autosk's watcher (`01` §3).

Why T1 matters most: **liveness derived from artifacts, not self-report** (`04` §3.9 pitfalls — "a wedged agent
can't report"). The same event stream that feeds the dashboard is a better pulse input than `tmux capture-pane`.

### 3.3 On-disk layout (machine layer + human layer)

```
docs/lab/                          # machine-first; committable except scratch
  events/2026-07-08.jsonl          # T1+explicit events, append-only, daily rotation
  status.json                      # snapshot: generated FROM events + STATE at each chronicler pass
  questions/queue.jsonl            # §4 — open questions (append + status-patch records)
  questions/archive.jsonl          # answered/expired, moved by the chronicler
  decisions/manifest.md            # §4 — owner-sovereign decision manifest (the ONLY hand-edited file here)
  decisions/log.jsonl              # every autonomous decision + every owner answer, append-only
  telemetry.jsonl                  # per-cycle token/cost lines (same fields as STATE TELEMETRY grammar)
  digest/2026-07-08-morning.md     # T3-generated morning digest (one per day with activity)
  site/                            # T3-generated static HTML dashboard (see 3.4); never hand-edited
  scratch/                         # gitignored: temps, partials (the tasty-lunch 81%-uncommitted lesson)
```

Rules inherited from existing discipline: atomic writes (same-dir temp + rename) for every non-append file;
append-only JSONL never rewritten (corrections are new records with `supersedes: <seq>`); ORCHESTRATION-STATE.md
**stays authoritative for the orchestrator** — `status.json` is derived, and on conflict the STATE + live git win
(the existing suspect-handoff rule). The human layer (handoffs, dev_history, reviews, digests) stays exactly
where it is today; the Laboratory adds links *into* it, never moves it.

### 3.4 Tier 3 — the admin dashboard ("Лаборатория" screen set)

**Implementation: static HTML regenerated from `docs/lab/` data — no server in v1.** This matches the proven
`docs/report/build-*.py` pattern, works from `file://`, survives the machine being off, is committable (thus
readable from GitHub/phone), and cannot rot the way the tasty-lunch wiki did *because no one edits it by hand*.
Regeneration triggers: (a) chronicler at every cycle boundary; (b) a `PostToolUse` async hook debounced on
writes to `docs/lab/`; (c) on-demand. The prior draft `web-harness-design.md` (Next.js + SSE) remains the v2
path — same data, richer consumer; v1 deliberately ships the data layer + dumb renderer first (its own step-1/2
sequencing). Live steering is NOT this dashboard's job — that's Remote Control / the terminal (§6).

**Information architecture — 7 screens, one nav:**

1. **Overview (the morning screen)** — the digest rendered + runway strip + questions summary. Default landing.
2. **Timeline** — the event feed, newest-first, filterable by actor/type/severity; incident markers.
3. **Tasks** — board keyed by Jira key: status, GH issue/PR links, commit SHAs, dev_history link per task.
4. **Questions** — the §4 queue: open (by type), answered (with who/when), auto-resolved (with the default used).
5. **Fleet** — per-agent cards: state (running/idle/terminated), model, spawned/ended, tokens, last event age.
6. **Cost** — telemetry series: per-cycle tokens, cumulative vs ceiling, per-model split, quota-window events.
7. **Library** — the generated cross-index: handoffs (numbered), dev_history (per task), reviews, reports,
   research, RCAs — each row with date, task keys touched, and links. Kills gap §2.3-6.

### 3.5 Who generates what — summary of responsibilities

| Artifact | Producer | Trigger |
|---|---|---|
| `events/*.jsonl` | hooks (T1) + `lab-emit` one-liners | every lifecycle/tool event, as it happens |
| `status.json`, `site/`, Library index | build scripts run by the chronicler | cycle boundary / debounced hook / on-demand |
| Morning digest | chronicler (`claude -p --max-budget-usd` glue or cheap-tier teammate) | scheduled at owner-wake time (cron/scheduled task) + on-demand |
| Handoffs, dev_history, reviews | unchanged — T2 conventions | unchanged (add: `lab-emit handoff.written` line) |

**The chronicler is NOT a fourth live agent.** It's a bounded, schedulable job (the `03` recommendation:
headless one-shots with strict `--allowedTools` + budget caps). Keeping it out of the teammate roster preserves
the spawn-cap-3 budget and means a chronicler crash can never stall delivery — the data layer just goes stale
until the next tick, and the dashboard *shows its own staleness* (generated-at stamp + max event age on every page).

## 4. Autonomy & the question buffer

> Community context (`04` §3.7): three maturity levels — (a) **park** on any question (autosk), (b) **pause
> with a budget** then auto-resolve (warren's `question_posed` events + pause budget), (c) **buffer-and-continue**
> — log the question, take the reversible default, keep working, surface everything in the morning. (c) is
> named there as "the ideal for gosleep; least implemented in public code". tasty-lunch already field-tested a
> primitive (c) (`OWNER-QUESTIONS.md` / `OWNER-DECISIONS-*.md`, §1.3). This section is the full design.

### 4.1 Question typology (four types, four behaviors)

| Type | Definition | Night behavior | Push? |
|---|---|---|---|
| **BLOCKER** | Work cannot proceed AND no safe default exists: credentials, denylist actions (force-push, prod deploy, destructive migration), irreversible forks | Park the affected work item ONLY (not the fleet); reroute workers to unblocked work; queue the question | **Yes, immediately** (unless manifest quiet-hours says batch) |
| **DECISION** | A genuine fork with viable branches, but a defensible default exists | Record question + chosen default + `auto_apply_at` deadline: *"if unanswered by T, I do X"*; keep working on other things until T, then apply the default and log a `decision.made` | Yes, batched (morning digest), unless marked high-impact |
| **CLARIFY** | Ambiguity with an obviously-reasonable reading | Proceed with the default IMMEDIATELY; record as answered-by-default so the owner can veto retroactively | No — digest only |
| **FYI** | No answer needed: incidents recovered, budget thresholds crossed, policy rules tripped | Record | No — digest only (unless severity ≥ incident) |

Key inversion vs today: **AskUserQuestion stops being the primary interface and becomes one delivery channel.**
The question RECORD is primary (survives sessions, visible to dashboard/digest/push); a synchronous
AskUserQuestion is raised *for the same record* only when the owner is present. Presence signal: the official
`CLAUDE_CLIENT_PRESENCE_FILE` marker pattern (Remote Control, CLI ≥2.1.181) or simply "owner sent a message
within N minutes". Absent → queue + push per type; present → ask live, then still log the answer to the queue
(the learning loop needs it either way).

### 4.2 Queue format on disk

`docs/lab/questions/queue.jsonl` — append-only; a status change appends a patch record (`re: <id>`), the
chronicler compacts answered/expired records into `archive.jsonl`. One record:

```json
{"id":"q-2026-07-08-003", "ts":"2026-07-08T01:12:40Z", "type":"DECISION",
 "from":"orchestrator", "task":"GSL-45", "links":{"jira":"GSL-45","gh":"#52","pr":"#56"},
 "question":"PR #56 has a conflict in README after main moved; rebase or merge main into the epic branch?",
```

Answer / resolution records: `{"re":"q-2026-07-08-003","ts":"...","status":"answered","answer":"merge main in",

`(task, question-hash)`; five workers hitting the same ambiguity = ONE morning item with a `seen_by` list.

### 4.3 The decision manifest — "решай сам по манифесту владельца"

`docs/lab/decisions/manifest.md` — **owner-sovereign** (the one hand-edited file in `docs/lab/`); agents READ it
every cycle, PROPOSE changes as a diff section in the digest, and **never edit it silently**. It formalizes what
today is scattered across "Standing rules" in ORCHESTRATION-STATE, memory files, and the owner's chat directives.
Structure:

```markdown
# Decision manifest — <owner> — vN (updated YYYY-MM-DD)
## 1. Always autonomous (never ask, always log)
- merge green PRs on delivery branches; advance phases; reversible in-repo work
- recover transient worker errors with one continue-nudge (validated 2026-07-07)
## 2. Decide-by-default (queue a DECISION record, apply default at deadline)
- default deadlines: night 10:00 next morning; day +2h
- merge strategy → regular merge; model policy → Fable 5 / Opus-mechanical; N=2 evals
## 3. Always ask, never default (= the denylist, verbatim from the orchestrating skill)
- force-push/history rewrite; deleting branches/tags/releases; prod deploys; secret rotation;
  destructive DB migrations; external communications; deleting cloud resources; spending beyond ceiling
## 4. Escalation & channels
- quiet hours 00:00-08:30: push ONLY BLOCKER; everything else batches into the 06:30 digest
- channel order: Claude-app push → Telegram → (morning) digest
## 5. Budget & runway
- token ceiling per phase: N; on 80% → FYI; on 100% → BUDGET_EXCEEDED = BLOCKER
## 6. Standing preferences (style, language, review strictness…)
```

Sections 1/3 mirror the orchestrating skill's existing authority/denylist — the manifest doesn't invent new
policy, it gives the existing policy a *home the tooling can read* and the owner can version.

### 4.4 Learning from past answers

Every answer (live or queued) appends to `decisions/log.jsonl` with the full question context. Periodically
(weekly, or when the log grows N records) the chronicler mines it: same question-shape answered the same way
≥2-3 times → a **manifest candidate** in the digest: *"You chose 'regular merge' 3× — promote to §2
decide-by-default?"* Owner approves by editing the manifest (or replying "yes" via a channel, which the
orchestrator turns into the edit). This is gosleep's existing loop-guard/memory instinct, but repo-visible and
owner-auditable — and it directly shrinks the future question volume, which is the real autonomy metric:
**questions-per-night should trend to zero for recurring shapes.**

### 4.5 The morning digest

Generated at the manifest's wake time (scheduled task / cron / Routine per `03` §3-D) and on-demand;
`docs/lab/digest/YYYY-MM-DD-morning.md` + rendered on the Overview screen + optional push "digest ready".
Sections, in owner-priority order: (1) **Waiting for you** — open BLOCKERs, then DECISIONs with their deadlines;
(2) **Decided for you** — every auto-resolution with the manifest rule cited (provenance discipline, §1.2 PRD
tags); (3) **What shipped** — tasks/PRs/commits with links; (4) **Incidents** — what broke, what recovered,
RCA links; (5) **Cost & runway** — tokens vs ceiling, quota events; (6) **Manifest candidates** (§4.4);
(7) **Next** — the plan for today. Everything links into the dashboard/Library. The `04` §3.6 rule applies:
*the digest is as important as the work* — an unreviewable night is a failed night even if all PRs merged.

### 4.6 Integration with the ORCHESTRATION-STATE process (minimal deltas)

1. **PULSE gains one step:** on each ~5-10 min self-check, also scan `questions/queue.jsonl` for (a) newly
   answered records → act on them; (b) DECISION records past `auto_apply_at` → apply default, emit
   `decision.made`; (c) BLOCKERs idle too long → re-push per manifest escalation.
2. **`BLOCKED_ON_HUMAN` becomes "queue + reroute", not "stop":** the orchestrating skill's decision-fork list
   stays identical, but the mechanical response is: write the question record, push per type, park only the
   affected work item, continue everything unblocked. (autosk's park-per-task, not park-the-fleet — `01` §7.)
3. **Worker briefs gain one line:** "If you hit an ownable question, emit it via `lab-emit question` with type +
   default + reversibility and CONTINUE on the default if type ≤ DECISION; never block your pane on a human."
4. **STATE stays the orchestrator's authority**; LIVE-STATUS gets one new field: `questions: open=N (B/D/C/F)`.
5. **Session boundaries unchanged** — handoffs now also reference open question ids so a replacement
   orchestrator inherits the queue trivially (it's on disk anyway).

### 5.1 The "autonomy runway" indicator (how much longer can it run without me?)

## 6. Mobile access patterns (survey)

> Deep autosk mobile mechanics (Tauri iOS client, raw TCP+token, reconnect protocol) are in `01` §6 — not
> repeated. Verified 2026-07-07 against official docs (code.claude.com/docs/en/remote-control) + web sweep.

| # | Pattern | What it is | Pros | Cons |
|---|---|---|---|---|
| 1 | **Official Remote Control** (research preview, launched 2026-02-24) | `claude remote-control` (server mode, ≤32 sessions, `--spawn worktree`) / `claude --rc` / `/rc` pairs a LOCAL session to claude.ai/code + Claude iOS/Android app; QR pairing | First-party; **subscription-only by design** (fits `03`'s policy verdict); outbound-HTTPS-only, no inbound ports, TLS + short-lived scoped creds (obsoletes autosk's raw-TCP gap); conversation syncs terminal↔phone; approve permissions from phone; **built-in mobile push** (≥2.1.110: "when Claude decides" + "actions required"); presence-file suppression | Research preview (surface may move); local process must stay alive; ~10 min offline kills the session; one remote session per interactive process outside server mode; it mirrors ONE session — the owner steers the orchestrator, not individual tmux worker panes; claude.ai UI, not our dashboard |
| 2 | **Channels** (official plugin surface) | Telegram/Discord/iMessage (or own server) events forwarded INTO a local CLI session | The natural **inbound answer path for the §4 queue**: owner replies to a question from bed in Telegram; works while owner is outside any Claude app | Plugin setup; still one target session; message-shaped, not dashboard-shaped |
| 3 | **Dispatch** (official, app→Desktop) | Message a task from the Claude mobile app; Desktop spawns a session | Zero-setup task injection ("morning: also do X") | Requires Desktop app running; not a monitoring surface |
| 4 | **Hook-driven push** (ntfy.sh / Pushover / Telegram bot) | `Notification`/`StopFailure`/`SubagentStop` hooks → curl to a push service; **tap-to-tmux** adds tap→SSH-into-the-exact-pane | Trivial (one async hook, ~10 lines); covers FLEET-level events Remote Control can't see (it's per-session); self-hosted ntfy = no third party | One-way; DIY topic auth (ntfy topics are public-by-obscurity unless self-hosted/ACL'd) |
| 5 | **SSH/mosh clients + Tailscale** (Blink/Termius/Prompt; rogs.me mosh+tmux+ntfy pattern) | Real terminal to the real tmux fleet | FULL control — attach to any pane, kill, restart; works when everything else is broken; Tailscale gives E2E WireGuard without exposing ports | Phone terminal UX is poor for reading; no push by itself; manual |
| 6 | **Web-tmux wrappers** (VibeTunnel, ttyd/gotty class) | Browser view of terminal sessions | Pane-level visibility in a browser | DIY auth/TLS burden; still raw terminal rendering; superseded by 1+5 for us |
| 7 | **Third-party companions** (Omnara — push + clean mobile UI + diffs; happy-coder class) | Hosted/self-hosted bridges around Claude Code | Polished mobile UX today | Third-party in the auth path = exactly the category the 2026 crackdowns hit (`03` §2) — verify how each wraps the CLI before touching; maintenance risk |
| 8 | **autosk-style own client** | Build a Tauri/native client on our own daemon | Total control | `01` §6 shows the cost and the gaps (TLS, push, relay) — building this ourselves is unjustified now that #1 exists on-subscription |

**Recommended stack (layered, all official-first):**
1. **Remote Control on the orchestrator's session** with both push toggles ON — steering + permission approvals
   + "Claude decides" push, on-subscription, E2E encrypted. The orchestrator is the correct single session to
   expose: it's the entity the owner talks to anyway.
2. **Hook→ntfy (self-hosted or ACL'd topic) for fleet-level + Laboratory events** — BLOCKER questions, digest-ready,
   quota-window parked, incident. This is the push path that works even when no Remote Control session is up.
3. **Channels/Telegram as the answer path** for queue records (reply "1" → orchestrator applies option 1, logs
   `answered_by=owner channel=telegram`). Evaluate after 1+2 — it's the piece with plugin-maintenance cost.
4. **Tailscale + Blink/mosh as the break-glass layer** — full tmux attach from the phone when the nice paths fail.
5. The dashboard (§3.4) is committable static HTML → also readable from the phone via the GitHub repo (private,
   already authenticated) with zero extra infra.
