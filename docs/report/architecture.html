Архитектура harness

Как устроен этот проект и почему. От исходника навыка до активного навыка, через eval-pipeline, к будущему live-наблюдению за флотом агентов. Главный архитектурный принцип здесь один: сначала событие, потом интерфейс — всё строится поверх единого event stream, а не поверх UI.

Логическая цепочка страницы. (1) Раскладка проекта — где что лежит и как один кусок порождает другой. (2) Eval-pipeline — как сценарий проходит через RED/GREEN-runner и judge к scorecard. (3) Observability — дизайн будущего live-harness. (4) Event schema — предлагаемые типы событий.

1. Раскладка проекта

Harness — это standalone-проект, который пока живёт под docs/ в репозитории tasty-lunch (позже переедет в собственный git-репозиторий). Его задача — превратить навык orchestrating-delivery-agents в профессиональный, измеримый и эволюционирующий продукт. Четыре каталога образуют единый конвейер: исходник навыка → активный навык → eval-suite (его проверяет) → design (его будущее).

docs/orchestration-harness/ ├── skill/ # SOURCE OF TRUTH навыка (3 файла, ~2 670 слов в SKILL.md) │ ├── SKILL.md # процесс оркестрации: lifecycle воркеров, decision forks │ └── references/ │ ├── worker-cycle-template.md │ └── lifecycle-and-edge-cases.md # 16 edge-кейсов E1..E16 │ ├── install.sh # синхронизирует skill/ -> активный навык │ │ │ ▼ │ ~/.claude/skills/orchestrating-delivery-agents/ # АКТИВНЫЙ навык, его читают агенты │ ├── evals/ # поведенческий test-suite (TDD для процесса) │ ├── scenarios/ # SC-01..SC-20: prompt.md + rubric.md на каждый │ ├── runner/eval-runner.js # two-arm RED/GREEN runner (запуск как Workflow) │ └── scorecards/ # результаты: pass-rate, дельта RED->GREEN │ ├── design/ # дизайн будущего live observability harness │ ├── event-schema.md # фундамент: типы событий (см. часть 4) │ └── web-harness-design.md # web vs console, стек, sequencing │ └── report/ # ЭТА база знаний (HTML + data/runs.json) ├── assets/style.css ├── data/runs.json # вся телеметрия (источник цифр этой страницы) └── *.html # dashboard, skill, scenarios, runs, agents, architecture...

skill/ → активный навык

skill/ — единственный источник правды. install.sh копирует его в ~/.claude/skills/, откуда навык подхватывают агенты. Правишь исходник — переустанавливаешь — навык активен. Разделение «исходник vs установленное» делает изменение версионируемым и обратимым.

evals/ проверяет навык

Навык — это процесс, поэтому и тестируется как процесс. Каждый сценарий — это ситуация для оркестратора плюс rubric (правильное поведение + ловушки). Подробный поток — в части 2.

design/ — будущее

Пока live-наблюдение — это tmux-панели. design/ описывает шаг дальше: web-harness поверх event-лога. Детали — в части 3–4.

Каждый каталог кормит следующий. Уроки из delivery-прогона (post-phase8-review) → правки в skill/ → новые ловушки → новые сценарии в evals/ → доказательная эволюция навыка → когда хочется видеть это вживую, включается design/. Это тот же цикл RED → GREEN → REFACTOR, но для процесса, а не для кода.

2. Eval-pipeline: от сценария к scorecard

Это superpowers:writing-skills TDD, сделанный повторяемым. Runner даёт свежему агенту одну и ту же ситуацию дважды: без навыка (RED baseline) и с навыком (GREEN). Каждый из N прогонов на каждой руке судит отдельный judge по rubric. Навык «проходит» сценарий, когда GREEN высокий (≥ 0.8) и бьёт RED.

Поток одного сценария (N=6, как в полном прогоне)

SC-XX ──> eval-runner.js (как Workflow) │ ├── читает prompt.md (ситуация для оркестратора) ├── читает rubric.md (правильное поведение + ловушки — НЕ показывается агенту) │ ├──> RED-рука: 6 agents-under-test БЕЗ навыка (baseline) │ │ │ └──> 6 RED-judges # каждый ответ судит свой judge по rubric │ ├──> GREEN-рука: 6 agents-under-test С навыком в контексте │ │ │ └──> 6 GREEN-judges │ └──> scorecard-synth │ ▼ scorecard.json: RED pass-rate · GREEN pass-rate · дельта · verdict

Один полный сценарий = 6 RED + 6 GREEN + 6 RED-judges + 6 GREEN-judges + общий scorecard-synth. Для 20 сценариев это сотни агентов в одном прогоне — отсюда 480 субагентов в eval-full-run. Смысл двух рук прост: GREEN сам по себе ничего не доказывает; ценность навыка — это дельта над RED, измеренная на одной и той же ситуации.

Verdict-логика

VerdictУсловие
PASSGREEN ≥ 0.8 и GREEN > RED
GUARDRED уже высокий — навык удерживает, но дельты нет
FAILGREEN < порога или не бьёт RED
PENDINGGREEN ещё не досчитан (resume-прогон)

Resume через кэш

Полный прогон упёрся в недельный лимit Anthropic в середине. Решение — кэш: успешные агенты не перезапускаются. В eval-full-resume переиспользованы ~380 успешных агентов, заново гонятся только ~100 упавших GREEN-judges + scorecard. Это делает pipeline идемпотентным и устойчивым к обрывам — тот же принцип, что навык требует от воркеров (см. SC-16).

Масштаб прогона: субагенты по workflow

Eval-прогоны порождают на порядок больше агентов, чем review-прогон — каждый сценарий разворачивается в 4 группы по N агентов плюс судьи. Числа из data/runs.json.

3. Observability: будущий live-harness

Цель — смотреть прогон вживую в браузере: флот агентов, их статусы, вызовы инструментов, сообщения между агентами и что происходит в Jira/GitHub. Дизайн зафиксирован, реализация отложена — здесь записано рекомендованное направление.

Принцип: сначала событие, потом UI

Единственное архитектурное решение, которое делает возможным любой интерфейс (TUI или web): продюсеры (агенты) эмитят стабильный, append-only поток структурированных событий, а потребители (UI / тесты / аудит) подключаются к нему. Один event-лог сразу даёт четыре вещи: live-вид, replay прогона, audit trail и фикстуры для тестов. UI — это просто consumer; он строится поверх event stream, а не наоборот.

SSE против WebSocket

Маленький сервер тейлит лог (runs/<run-id>/events.jsonl) и пушит клиентам. Транспорт выбирается по тому, нужен ли UI контроль над прогоном:

ТранспортНаправлениеКогда
SSE сервер → браузер (one-way) live-вид только для чтения — наблюдаем флот, ничего не трогаем. Дешевле, проще, hits нативный EventSource в браузере.
WebSocket двунаправленный если UI ещё и управляет прогоном — pause / kill агента. Нужна, когда наблюдение превращается в пульт.
Рекомендация. Старт на SSE (наблюдение), переход на WebSocket только когда понадобится управление. Сам поток событий от выбора транспорта не зависит — это и есть смысл «event-first».

Стек и виды

Next.js (App Router)

Совпадает с текущим TS/Next-стеком команды. Route Handler принимает события, SSE-endpoint пушит их в браузер, React рисует UI. Persist событий (JSONL → SQLite/Postgres) даёт replay и аудит.

tmux как raw-вид

tmux-панели остаются «сырым» живым видом: бесплатно, мгновенно, без инфраструктуры. Web-harness не заменяет их, а добавляет графы, timeline и шеринг поверх того же event-лога.

Виды web-UI: дерево/флот агентов (React Flow / d3 / Mermaid), timeline циклов (Gantt), живой feed сообщений, drill-down по агенту (вызовы инструментов, задача, токены), панель Jira/GitHub (API/webhooks).

Опция: Claude Agent SDK

Для «настоящего продукта» можно перенести сам цикл оркестрации на Claude Agent SDK (TypeScript): тогда мы владеем циклом и эмитим события напрямую — first-class observability и control. Сегодня события приходят из хуков Claude Code (PreToolUse / PostToolUse / SessionStart / Stop) плюс явных записей в лог от оркестратора и воркеров; SDK-путь делает эмиссию частью самого loop. (Конкретику хуков/SDK проверять по актуальным докам на момент реализации.)

Sequencing

1. Зафиксировать event schema; научить оркестратор/воркеров эмитить события (хуки + записи в лог). 2. Тонкий viewer (даже tail -f или минимальная SSE-страница), чтобы провалидировать поток. 3. Развернуть полноценные web-виды (дерево, timeline, feed, Jira-панель). 4. (опц.) Переплатформить loop на Agent SDK для чистой programmatic observability + control.
