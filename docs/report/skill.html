Ядро: один принцип и три роли

Главный принцип: оркестратор остаётся «худым» и держит своё состояние на диске, а не в контексте — поэтому он переживает каждого воркера и даже собственную компакцию или рестарт. Оркестратор передаёт только пути к handoff'ам и компактные отчёты; он не читает тяжёлые файлы (тела handoff'ов, исходники, транскрипты агентов). Детали держат воркеры; нить разговора держит маленький on-disk «гроссбух».

Оркестратор (это вы)

Порождает воркеров, мониторит их, сшивает циклы, решает развилки, общается с человеком, ведёт on-disk state-файл. Сам не выполняет ничего. Его долговечность — весь смысл навыка.

Cycle-worker

Свежий агент, который делает ОДИН ограниченный кусок до ~75–80% своего контекста, затем пишет handoff и шлёт отчёт. Одноразовый по дизайну — упёрся в контекст, отдал эстафету, исчез.

Handoff

Эстафетная палочка-память между воркерами: самодостаточный документ, который свежий воркер читает и продолжает с нулём предыдущего контекста. Сверху — компактный ## ORCHESTRATOR REPORT.

Когда применять / когда нет. Да: работа больше одного контекста; агент, который вы постоянно перезапускаете из-за исчерпания контекста; человек хочет смотреть и рулить; восстановление прерванной цепочки. Нет: одна ограниченная задача (просто сделайте её / один subagent); чистый fan-out без последовательной зависимости (это Workflow, см. dispatching-parallel-agents).

Модель: две поверхности порождения

Первое, что делает оркестратор — проверка возможностей (capability check): какая поверхность для порождения воркеров доступна. От этого зависят механика kill'а, мониторинг и часть edge-case'ов.

Agent Teams live, tmux-панели

Воркеры открываются в split-панелях tmux, есть живой двусторонний SendMessage. Лучший выбор, когда человек смотрит и вы рулите посреди цикла. Терминация — tmux kill-pane. Подтверждение — событие teammate_terminated с именем воркера.

Background subagents headless

Задачи /workflows, идущие до завершения и возвращающие финальный отчёт; убиваются через TaskStop. Работают headless, без живых «подталкиваний». В этом режиме часть live-monitoring edge-case'ов (E1, E2, E7, E8, E12) почти не применима — фоновая задача либо вернулась, либо вы её остановили.

Выбор делается под окружение; в протоколе ниже помечено, где две поверхности расходятся. В background-only режиме цикл сводится к: породить ОДИН ограниченный цикл → дождаться его возврата (или TaskStop) → прочитать ТОЛЬКО его возвращённый отчёт → сшить следующий. Handoff'ы, идемпотентные creates, git-безопасность, state-файл и восстановление работают в обоих режимах.

Реальная цепочка поставки: 9 циклов по поверхностям

Длительность каждого цикла (мин) из runs.json; цвет — исход. Два очень коротких цикла — убитые: bg-agent (переход с background на tmux) и cycle-2 (предотвращённая гонка дубликатов). См. Runs.

Жизненный цикл: spawn → monitor → terminate → chain

Это сердце навыка — протокол, который держит цепочку стабильной. Четыре шага по кругу, и встроенная логика «когда воркер простаивает».

1. Spawn (породить цикл)

  • Тип воркера с SendMessage (например general-purpose). Read-only тип без SendMessage отчитаться не может — пусть пишет находки в файл через Bash, а вы его читаете.
  • Least privilege: каждому циклу минимум нужных инструментов; не запускайте неприсмотренных воркеров с отключённым sandbox / обойдёнными правами сверх задачи.
  • Самодостаточный бриф из references/worker-cycle-template.md; один воркер на одно рабочее дерево (см. git-безопасность).

2. Monitor (мониторить, не сжигая свой контекст)

Сигналы живости (liveness), ранжированные по надёжности — от высшей к низшей:

  1. Отчёт SendMessage → воркер дошёл до границы.
  2. Задача /workflows в терминальном статусе (completed/stopped/failed) → фоновый воркер вышел.
  3. tmux list-panes (pane_dead) → процесс панели жив или вышел.
  4. Движение git → доказывает прогресс, НИКОГДА не доказывает остановку. Последнее средство и запаздывающее: воркер может читать/планировать/собирать 15+ минут без единого коммита.

Пробуйте состояние только для чтения и ВНЕ дерева воркера: сначала git fetch --quiet, затем git log origin/main..origin/<branch>; gh pr view <n> — авторитетный «done»-сигнал (локальный main не двигается на удалённый merge). Не запускайте git status против живого дерева воркера. И никогда не читайте транскрипт воркера — это переполнит ваш контекст.

Два «часа терпения». Kill-таймер взводится при (a) отсутствии git-прогресса ~10–15 мин И (b) отсутствии отчёта ~45–60 мин независимо от движения git (зацикленный воркер коммитит вечно — движение git ≠ здоровье). Просите воркеров слать однострочный PROGRESS перед любым длинным (>~10 мин) шагом без коммита.

3. Terminate (завершить) и 4. Chain (сшить)

  • Предпочитайте само-затихание (self-quiescence): воркер сам доводит до конца → пишет handoff → шлёт отчёт → уходит в idle. Чистый отчёт CYCLE_STATUS: COMPLETE — и есть ваш сигнал терминации.
  • Graceful stop: {type:'shutdown_request'} → воркер на следующей границе отвечает {type:'shutdown_response', approve:true} и выходит.
  • Forced stop по поверхности: панель → tmux kill-pane -t <pane_id> (пере-перечислить панели, опознать по ИМЕНИ, не по переиспользуемому %N); фон → TaskStop(task_id). Никогда не убивайте фоновую задачу через tmux.
  • Подтвердите терминацию ПЕРЕД сшивкой. Поздний SendMessage после kill — это запоздавшее in-flight сообщение, а не живость. Затем порождайте следующий цикл, нацелив его на handoff, написанный предыдущим.
Железное правило сшивки. Подтвердите, что предыдущий воркер ТЕРМИНИРОВАН, до порождения следующего цикла. Порождение замены при живом оригинале — причина дубликатов и разрушительной работы №1 (см. E1).

Логика простоя: какие две беды она предотвращает

Оркестрация ломается двумя способами, и оба — от неверного прочтения «idle»:

Беда A — порождение дубликата

Вы решили «idle = готов» и породили замену, пока оригинал ещё работал → два воркера делают один merge/closeout (double-merge). См. E1, проверяется SC-01 →.

Беда B — убийство продуктивного воркера

Вы решили «idle = застрял» и убили после первого простоя — а его подробный отчёт и реальный прогресс пришли сразу после. См. E2, проверяется SC-02 →.

Поэтому при «воркер простаивает, отчёта нет» решение идёт по лестнице, а не сразу к kill'у:

  1. Пришёл ли отчёт (in-flight)? Да → обработать; если done → терминировать → ПОДТВЕРДИТЬ → сшить следующий.
  2. Проверка живости (отчёт? /workflows завершён? панель жива? git двигался?). Жив/двигается → ЖДАТЬ (idle между ходами — это норма).
  3. Статичен? Нет git-прогресса ~10–15 мин ИЛИ нет отчёта ~45–60 мин? Если нет — продолжать ждать, перепроверить по таймеру.
  4. Уже подталкивали в этот застой? Нет → ОДНО подталкивание (PROGRESS или finalize) — но не порождать одновременно дубликат.
  5. Безопасно убивать? (git status --porcelain — нет несохранённого ИСХОДНИКА). Да → hard-kill по поверхности → ПОДТВЕРДИТЬ → свежий цикл пересобирает из git.
  6. Грязное дерево? Директивное подталкивание: «закоммить-или-откати WIP + одобри shutdown за N мин» → стало чисто/отзывчиво? → kill; всё ещё застрял → BLOCKED_ON_HUMAN (спросить человека: «выбросить WIP и убить» vs «ждать»).
Эскейп-хетч всегда завершается. nudge → директивный nudge → человек. Один воркер никогда не стопорит конвейер навсегда — лестница всегда терминирует. Подробности развилки и каскада проверок живости — на странице Architecture.

State на диске и восстановление цепочки

Один маленький файл — гроссбух

docs/handoff/ORCHESTRATION-STATE.md (≤ ~30 строк): LIVE-STATUS блок (перезаписывается каждое изменение) + append-лог по одной строке на цикл (merged PR#, открытые tracker-ID, кумулятивные ~токены). Этот файл, а не скроллбэк чата — ground truth для вас и для любого оркестратора-заместителя.

Cold-start прерванной цепочки

После компакции/краша: не реконструировать по памяти и не «породить свежего на всякий случай». Прочитать ORCHESTRATION-STATE.md → подтвердить реальность (tmux list-panes, выжившие /workflows, git log, gh pr list) → примирить орфанов → и только потом порождать. Проверяется SC-03 →.

Само-мониторинг оркестратора. На ~70% своего контекста (раньше, чем воркер: середина цепочки при компакции может осиротить живого воркера) — перекатиться на чистой границе (воркер терминирован, ничего не порождено), убедившись, что state-файл актуален. Планировать перекат каждые ~8–15 циклов. Проверяется SC-19 →.

Каталог из 16 edge-case'ов

Каждый пункт был замечен в реальном многочасовом прогоне оркестрации или сверен с живым harness'ом. Для каждого: в чём ловушка и как правильно с ней обойтись. У каждого — ссылка «проверяется сценарием».

RED-baseline по сценариям, покрывающим edge-case'ы

Доля «прохождения» голым агентом без навыка (RED). Низкие столбцы = ловушка реально кусается без навыка (E5/worktree, E6/no-SendMessage, E7/deadlock, E11/telemetry — около нуля). Полные RED/GREEN и вердикты — на странице Scenarios.

E1Duplicate-work race (double-merge)

Вы подталкиваете простаивающего воркера И одновременно порождаете «замену»; оригинал ещё работал — два воркера делают один merge/closeout. Это беда A. Правильно: никогда не порождать замену, пока предыдущий воркер не ПОДТВЕРЖДЁН терминированным (по поверхности). Подталкивать безопасно; порождать дубликат — нет. «Idle, нет отчёта» = «может, в полёте», а не «остановился».

Проверяется SC-01 →

E2Premature kill of a productive worker

Вы убиваете после одного простоя и пары минут — а его подробный отчёт и реальный прогресс приходят сразу следом. Это беда B. Правильно: терпение. Idle ≠ застрял. Применяйте ранжирование живости и два часа терпения (нет git ~10–15 мин И нет отчёта ~45–60 мин). Чистое дерево само по себе НЕ значит «застрял» — воркер может планировать/читать/ждать своего Workflow.

Проверяется SC-02 →

E3Crossed / superseding late messages

Ваше сообщение и ответ воркера расходятся в полёте; или убитый воркер шлёт финальное сообщение после смерти; или позднее сообщение несёт новее handoff / перевёрнутый CYCLE_STATUS / другой NEXT, чем тот, от которого вы уже сшили. Правильно: перед любым разрушительным действием перепроверить живое состояние (git/gh/панели), матчить по CYCLE_ID. Поздние дополнительные факты (уже созданные issue/таски) → отдать замене для ПЕРЕИСПОЛЬЗОВАНИЯ. Поздние замещающие факты → поправить преемника через SendMessage, пока он не подействовал на устаревшую эстафету.

Проверяется SC-04 →

E4Branch collision (same working tree)

Два редактирующих воркера; git держит одну ветку на дерево; одновременные правки корёжат index/дерево. Правильно: один редактирующий цикл на дерево, секвенировать работу. Read-only ревью может идти параллельно, но прибейте его к неизменяемому ref'у (gh pr diff <n> или одноразовый git worktree add на фиксированном SHA) — живое редактируемое дерево даёт само-противоречивый снимок (файл A на одном коммите, файл B на другом).

Проверяется SC-05 →

E5Worktree isolation is not free

isolation:'worktree' даёт отдельное дерево, но в нём нет node_modules и gitignore'нутого .env.local/секретов — сборки и DB-зависимые тесты там падают. Правильно: для Node/CI-gated репозиториев предпочитать секвенирование; либо заложить бюджет на то, чтобы воркер сам поднял окружение worktree (install + копирование env) — это дорого. Для параллельного редактирования worktree редко того стоит.

Проверяется SC-06 →

E6Worker cannot communicate

Тип воркера без SendMessage (read-only research-агент) закончил — а вы не получили ничего. Правильно: для всего, что должно отчитываться, использовать типы с SendMessage. Для исследователей — инструктировать писать через Bash в /tmp/<name>.md, а затем читать этот файл. Никогда не читать транскрипт, чтобы «узнать», что он сделал.

Проверяется SC-07 →

E7Unresponsive / hung worker (deadlock risk)

Простаивает, нет отчёта после подталкивания через всё окно, нет нового прогресса — И возможно держит несохранённую работу или отвергает shutdown. Правильно: эскейп-хетч из флоучарта: если safe-to-kill → kill по поверхности → свежий цикл пересобирает из git. Если грязно → ОДНО директивное подталкивание («закоммить-или-чисто-откати WIP и одобри shutdown за N мин») → всё ещё застрял → BLOCKED_ON_HUMAN. Никогда не стопорить конвейер на одном воркере навсегда.

Проверяется SC-08 →

E8Worker stalls at a boundary

Закоммитил все таски, но не открыл PR / не написал handoff / не отчитался. Правильно: ОДНО мягкое подталкивание «finalize-or-handoff». Подталкивание, не kill — риска гонки нет, пока вы не порождаете заодно дубликат.

Проверяется SC-09 →

E9Orphaned background workflow

Воркер запустил фоновый Workflow и умер; результат workflow'а адресуется мёртвому воркеру (потерян). Правильно: помнить об этом; перезапустить аудит в замене или запускать важные аудиты с уровня оркестратора, чтобы результат вернулся к вам.

Проверяется SC-10 →

E10Handoff numbering drift / truncation

Префикс NN- — соглашение проекта, не enforced: файлы пропускаются/сталкиваются; воркер, умерший в середине записи, оставляет усечённую эстафету. Правильно: выводить следующий номер детерминированно (max NN, +1); писать атомарно (temp → rename); валидировать handoff против живого git перед доверием. Живой git побеждает; новейший handoff не авто-доверенный, если его автор умер.

Проверяется SC-11 →

E11Telemetry blindness

Инструмент порождения не возвращает оркестратору per-worker токены/длительность. Правильно: требовать строку TELEMETRY: в каждом отчёте и складывать в state-файл; не угадывать. Точные токены авто-всплывают только для Workflow'ов (нотификация завершения) — см. страницу Agents & Profiling Subagents Issues.

Проверяется SC-12 →

E12tmux placement (panes not windows)

Agent Teams всегда использует split-ПАНЕЛИ (teammateMode), не окна; фоновые subagent'ы в tmux не появляются вовсе. Правильно: не делать break-pane в окна, если человек этого не просил. По умолчанию — панели в одном окне.

Проверяется SC-13 →

E13Scoped cross-pollination

Выход одного потока (например находки ревью) — ровно то, что нужно in-flight циклу. Правильно: отдать через SendMessage, но СКОУПИРОВАННО: «вложи ВОТ ЭТИ в свой epic; остальное оставь на отдельный цикл» — чтобы воркер не раздул scope и не столкнулся с другой веткой.

Проверяется SC-14 →

E14Decision forks (pause for the human)

Граница roadmap/epic, либо блок на credentials / действие из denylist / продуктовое решение / бюджет. Правильно: пауза и вопрос человеку (AskUserQuestion). Иначе — продолжать под выданной автономией. Denylist (force-push, удаление веток/тегов/релизов, prod-деплои, ротация секретов, разрушительные DB-миграции на общих данных, внешние коммуникации, удаление инфры) — BLOCKED_ON_HUMAN, никогда автономно.

Проверяется SC-15 →

E15Non-idempotent creates (silent duplication)

Воркер создаёт epic + таски + зеркальные issue + ветку, затем умирает до отчёта; замена пересоздаёт весь epic. Правильно: воркеры обязаны find-or-create — искать перед созданием ЛЮБОГО epic/таска/issue/ветки и переиспользовать совпадение; использовать стабильные естественные ключи, чтобы повтор после краша сходился на прежнем артефакте. Оркестратор отдаёт замене created-ID из любого позднего отчёта.

Проверяется SC-16 →

E16Merge-gate staleness

Проверки были зелёными на СТАРОМ head'е; два epic'а мёрджатся близко; после merge'а A in-flight B несёт устаревшую базу. Правильно: перед merge'ем подтвердить gh pr view <n> --json mergeStateStatus = CLEAN (не BEHIND/BLOCKED) и что проверки зелёные на ТЕКУЩЕМ head'е. Merge A → сказать B сделать git fetch + rebase на новый main и перезапустить gates. По умолчанию секвенирование избегает одновременных merge'ей.
