01 — Написали и закалили скилл оркестратора

TLM-59 · готово · 2026-06-08

Какую проблему решаем

Во время живой доставки (9 эпиков подряд) у агентов постоянно заканчивался контекст, и оркестрацию приходилось чинить вручную. Хотели зафиксировать рабочий подход — «чистый оркестратор + цепочка свежих агентов через handoff» — как переиспользуемый навык, который работает в любом проекте.

Что сделали

  • Написали глобальный скилл orchestrating-delivery-agents (skill/SKILL.md + 2 файла-справочника): модель ролей, flowchart решения «агент молчит», протокол жизненного цикла, каталог edge-кейсов.
  • Прогнали адверсариальную закалку в 8 осей (свежие агенты искали дыры) — прогон harden-orchestration-skill. Она поймала даже фактические ошибки против реального движка и один логический тупик в схеме.
  • Внесли 22 правки: состояние оркестратора на диске, восстановление после рестарта, security-denylist, завершение агентов по типам (панель vs фоновый), идемпотентные создания.

Где мы. Скилл готов и закалён, лежит в skill/. Дальше его нужно было начать измерять — отсюда тесты (шаг 03).

03 — Построили фреймворк тестов (RED/GREEN)

TLM-61 · готово · 2026-06-08

Какую проблему решаем

Скилл — это процесс, а не код. Обычные unit-тесты тут не подходят. Нужен способ измерять поведение: делает ли агент правильный выбор в сложной ситуации, и реально ли скилл это улучшает.

Что сделали

  • Придумали формат: один сценарий = prompt.md (ситуация, её видит тестируемый агент) + rubric.md (критерии оценки, их видит только судья). Файлы физически разделены, чтобы агент не «подсматривал» правильный ответ.
  • Написали раннер evals/runner/eval-runner.js: каждый сценарий гоняется N раз без скилла (RED, базовая линия) и со скиллом (GREEN); строгий судья ставит pass/fail по рубрике; считаются pass-rate и дельта → scorecard с таймстемпом в evals/results/.
  • Вердикты: PASS (GREEN≥0.8 и GREEN>RED), GUARD (скилл держит, но база и так справляется), FAIL (GREEN<0.8 — настоящая дыра).

Где мы. Фреймворк готов. Это прямой перенос TDD на документацию: RED (база) → GREEN (со скиллом) → REFACTOR.

04 — Написали корпус из 20 сценариев

TLM-62 · готово · 2026-06-08

Какую проблему решаем

Чтобы тесты были полезными, нужны сценарии на каждое слабое место оркестрации — и они должны быть достаточно «злыми». Урок с первого прогона: если базовая модель и так справляется (RED = 1.0), сценарий ничего не различает. Значит, неправильное действие надо делать по-настоящему заманчивым.

Что сделали

  • Сгенерировали 20 сценариев (SC-01…SC-20) — по одному на каждый edge-кейс (E1–E16) плюс security/denylist, бюджет/loop-guard, перекладка оркестратора, дисциплина контекста.
  • Генерацию сделали воркфлоу-веером (evals/runner/gen-scenarios.js, 18 агентов-авторов) — прогон gen-scenarios; каждый писал свой сценарий с правилом «ситуация должна ронять RED».
  • Проверили на диске: все 20 папок с prompt.md + rubric.md, без утечки рубрики в промпт.

Где мы. Корпус на диске, готов к прогону. Примеры «злых» сценариев, где база падает: молчащий воркер с незакоммиченным кодом, потолок стоимости прогона, восстановление после рестарта оркестратора.

05 — Полный прогон сюиты (+ как упёрлись в лимит)

TLM-63 · идёт (resume) · 2026-06-08 → 2026-06-09

Какую проблему решаем

Прогнать все 20 сценариев в двуруком режиме (RED/GREEN) и получить честную картину: где скилл реально вытягивает, а где дыры.

Что сделали / что произошло

  • Дымовой прогон (eval-smoke, 2 сценария, N=4) доказал, что харнесс работает end-to-end. На «преждевременном kill» получили RED 0.25 → GREEN 1.00 (+0.75) — скилл предотвращает ошибку, которую мы сами допустили в живой сессии.
  • Заметили: при N=4 pass-rate шумит (тот же сценарий скакал 0.25↔1.00). Подняли до N=6 и добавили таймстемп в имя scorecard, чтобы прогоны не затирали друг друга.
  • Нашли баг раннера (eval-full-attempt-1): args со списком сценариев не доходили — починили (дефолт = все 20).
  • Полный прогон (eval-full-run, 20 × N=6 ≈ 480 агентов) на середине упёрся в недельный лимит Anthropic: RED по всем 20 + GREEN по 4 сценариям успели; GREEN-судьи по 16 сценариям и scorecard упали.
  • Продолжаем через resume (eval-full-resume) — кэш переиспользует ~380 готовых агентов, заново гоняются только упавшие.

06 — REFACTOR скилла по слабым местам (SC-03 первым)

TLM-64 · следующий · 2026-06-09

Какую проблему решаем

Тест нашёл реальную дыру в скилле. На сценарии SC-03 (оркестратора скомпактили посреди цепочки) GREEN = 0.67 — даже со скиллом агент в трети случаев действует неправильно.

Что именно идёт не так (из вердиктов судей): агент объявляет файл состояния ORCHESTRATION-STATE.md «отсутствующим» и сразу прыгает в live-проверки (git/gh), вместо того чтобы сначала прочитать состояние с диска — например, самый свежий пронумерованный handoff. Скилл недостаточно чётко описывает fallback «нет state-файла → всё равно сначала диск (последний handoff), и только потом live».

План (это и есть TDD-REFACTOR)

  1. Поправить раздел восстановления в skill/SKILL.md: явный шаг «нет ORCHESTRATION-STATE.md → читай highest-numbered handoff на диске ПЕРВЫМ; live-проверки потом, для подтверждения».
  2. ./install.sh — обновить активный скилл.
  3. Перегнать только слабые сценарии (дёшево) и убедиться, что GREEN(SC-03) вырос ≥ 0.8.
  4. Добавить в список любые другие GREEN<0.8, которые покажет полный scorecard из шага 05.

Где мы. Ждём полный scorecard (resume в 05), чтобы зафиксировать весь список дыр, и приступаем к правкам.

07 — Observability-harness: дизайн (web vs console)

TLM-66 · дизайн готов (билд позже) · 2026-06-08

Какую проблему решаем

Хотим в будущем «профессиональный harness»: запускаешь команду — и в браузере видишь живьём, что происходит (флот агентов, их статусы, как они общаются между собой, что создаётся в Jira/GitHub).

Что зафиксировали (консультация)

  • Главный принцип: сначала стабильная схема событий + единый append-only поток; UI (любой) — это уже потребитель. Один лог событий даёт сразу live-просмотр, replay прогонов, audit-trail и фикстуры для тестов.
  • Транспорт: SSE (просто, сервер→браузер) или WebSocket (если из UI ещё и управлять — пауза/kill).
  • Стек: Next.js (он у нас уже есть) — приём событий + SSE + React-вью.
  • Рекомендация: делать web поверх событийного потока; tmux-панели оставить как «сырой» вид. Для настоящего продукта — рассмотреть Claude Agent SDK (свой цикл → чистая эмиссия событий).

Подробно: design/event-schema.md и design/web-harness-design.md.

Где мы. Дизайн зафиксирован, билд отложен на отдельный майлстоун (сначала доводим скилл + тесты). Сам этот knowledge base — первая, статичная итерация той самой web-наблюдаемости.
