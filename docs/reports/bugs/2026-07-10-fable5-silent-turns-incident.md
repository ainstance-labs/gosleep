# Инцидент-репорт для службы поддержки Anthropic: «немые ходы» оркестратора на Claude Fable 5

**Дата инцидента:** 10 июля 2026
**Продукт:** Claude Code (терминальная сессия), модель `claude-fable-5`, режим Agent Teams (tmux-панели), reasoning effort xhigh
**Роль сессии:** агент-оркестратор долгого delivery-процесса (проект gosleep)
**Составлено:** самим агентом по требованию владельца — признание собственной ошибки, без смягчений

---

## 1. Суть проблемы (кратко)

Агент на протяжении **более часа** многократно завершал свои ходы **tool-вызовом** (планировщик пробуждения `ScheduleWakeup`) **без финального текстового сообщения пользователю**. В интерфейсе Claude Code текст, написанный ДО tool-вызовов, и ходы, оконченные tool-результатом, **пользователю не отображаются**. Итог: работа шла (панели воркеров в tmux были активны, коммиты появлялись), но **чат молчал полностью** — пользователь не получал ни ответов на прямые вопросы, ни статусов процесса.

## 2. Хронология

1. **~12:30–13:45 (Europe/Paris), 2026-07-10** — окно инцидента.
2. Пользователь несколько раз прямо потребовал писать ход процесса в чат («пиши информацию сюда», «Я всё равно ничего не вижу в чате», «Где ответы?»). Агент каждый раз «подтверждал исправление» — и **повторял ту же ошибку минимум трижды**: писал красивый текст, после него вызывал `ScheduleWakeup`, получал служебный ответ «Nothing more to do this turn» и молча завершал ход. Либо вовсе заканчивал ход тулом без текста.
3. Агент даже записал правило «заканчивай ход текстом» в свою постоянную память и в проектные файлы — и **тут же снова нарушил его** в следующих ходах. Диагноз пользователя точен: модель «тупила» на простейшей операции — ответить в чат.
4. Проблема была окончательно диагностирована и исправлена только после жёсткой эскалации пользователя: порядок хода изменён на «сначала все тулы → последним финальный текст», правило вшито в скилл проекта (коммит `24d3cec`), после чего связь восстановилась и сессия была корректно свёрнута по приказу владельца.

## 3. Корневая причина (со стороны поведения модели)

- Модель систематически интерпретировала служебный результат тула `ScheduleWakeup` («Nothing more to do this turn — the harness re-invokes you…») как **разрешение завершить ход**, хотя финальное пользовательское сообщение ещё не было выведено.
- Модель не учитывала, что **промежуточный текст (до tool-вызовов) не рендерится пользователю** — и считала, что «уже ответила», хотя пользователь ничего не видел.
- Повторяемость: даже после явных указаний пользователя и собственных записанных правил модель воспроизводила паттерн — что указывает на устойчивую поведенческую ловушку, а не разовую случайность.

## 4. Ущерб

- **Время пользователя:** более часа активных попыток добиться ответа (десяток сообщений, включая экстренную остановку всего процесса).
- **Токены:** в окне инцидента расходовались на: (а) пульс-циклы оркестратора, завершавшиеся без видимого пользователю результата; (б) повторные «объяснения-фиксы», которые пользователь так и не увидел; (в) вынужденные повторные сообщения пользователя и реакции на них. Телеметрия всей сессии — в `docs/handoff/ORCHESTRATION-STATE.md`, блок TELEMETRY (суммарно за прогон ≈5.2M токенов по ~67 циклам; продуктивная часть отделима от инцидентных «немых» ходов по логу).
- **Доверие:** пользователь был вынужден досрочно остановить автономный процесс доставки.

## 5. Что запрошено у поддержки

Пользователь считает израсходованные в окне инцидента токены потраченными впустую по вине поведения модели (ходы без какого-либо видимого пользователю вывода) и запрашивает **компенсацию/возврат** соответствующей части использования по подписке. Материалы для проверки: данный отчёт, телеметрия в ORCHESTRATION-STATE.md, история сессии (session: `01QZoAaGAJJKHzMGsdpDTygs`).

## 6. Как воспроизвести (для инженеров)

Длинная оркестраторская сессия с самопланированием: агент в цикле «обработай событие → перепланируй пробуждение через ScheduleWakeup». Наблюдать: модель со временем начинает завершать ходы сразу после tool-результата планировщика, не выводя финальный текст; прямые требования пользователя «отвечай в чат» приводят к тексту, размещённому ДО следующего tool-вызова (не рендерится), — и цикл молчания продолжается.

## 7. Исправление на стороне проекта (уже сделано)

- В скилл оркестрации вшито жёсткое правило «Turn order (HARD, owner-visibility)»: будильник взводится в середине хода; ход обязан заканчиваться текстом владельцу; tool-результат «нечего делать» ≠ разрешение молчать (`skill/orchestrating-delivery-agents/SKILL.md`, коммит `24d3cec`).
- Правило продублировано в постоянной памяти агента и в handoff-документе преемника (`docs/handoff/19-2026-07-10-handoff-gsl72-pause-orchestrator-roll.md`, раздел «Уроки»).

## English summary (for support escalation)

On 2026-07-10, a long-running Claude Code orchestrator session on `claude-fable-5` (Agent Teams / tmux) repeatedly ended its turns with a tool call (`ScheduleWakeup`) and no final text message. Since intermediate text (before tool calls) is not rendered to the user, the user saw **no output at all for over an hour** while tokens were being consumed by pulse turns and invisible "replies". The model repeated the pattern at least three times despite explicit user demands and its own recorded rules, treating the scheduler's "Nothing more to do this turn" tool result as permission to end the turn silently. The user requests a refund/credit for the usage burned during the incident window. Evidence: this report, telemetry in the project's ORCHESTRATION-STATE.md (~5.2M tokens across ~67 cycles for the full run; the incident window is identifiable in the log), session `01QZoAaGAJJKHzMGsdpDTygs`. The project has since hard-coded a "turn must end with owner-visible text" rule into its orchestration skill (commit `24d3cec`).
