How to read this report — the vocabulary

Every term below is used throughout. Nothing else is assumed.

autosk
the product: a file-based task tracker + workflow engine + three front ends (CLI, TUI, GUI) for coding agents. MIT, local-first.
autoskd
the daemon — a Bun/TypeScript process compiled to a standalone binary. Sole owner of all state; everything else is a JSON-RPC client of it.
.autosk/
the per-project state directory: tasks/<id>/task.json, comments.jsonl, sessions/*.json(l). Plain files, no database.
task / workflow / step
a task is a file-backed ticket (new → work → done|cancel|human); a workflow is a directed graph of steps written in TypeScript; each step is owned by an agent.
session
one run of one agent on one task step — a spawned child process plus its transcript.
agent runtime / harness
the external CLI that actually talks to the LLM: claude (Claude Code) or pi. autosk spawns it headless and speaks its wire protocol.
driver
the daemon-side class that owns one child process and translates its wire protocol (stream-json or JSONL-RPC) into engine events.
transit
the tool call an agent must make to end its step: autosk_transit {to: "<step>|done|cancel|human"}. Declared by the model, validated and committed by the host.
kickback / corrections
if a turn ends without a transit (or the workflow rejects it), the host re-prompts the model with a correction message; budget = 3 attempts by default.
park / human
the universal failure sink: any unrecoverable condition sets the task’s status to human — parked, waiting for a person. Never a silent retry.
pi
an independent, actively developed TypeScript coding-agent CLI (earendil-works/pi, “pi.dev”). autosk drives it exactly like claude — a second, structurally twin harness.
AgentDefinition
the tiny contract an autosk agent implements: {onRun, onSteer, onFollowup, onAbort}. Everything runtime-specific hides behind it.
MCP
Model Context Protocol — how tools are exposed to a model. autosk mints a per-session HTTP MCP server with a bearer token.
worktree
a disposable git checkout (git worktree) an agent works in, so the real repo stays clean until a step lands.
JSONL / stream-json
both wire protocols are newline-delimited JSON over stdio: pi calls its dialect “RPC mode”; Claude Code calls its dialect “stream-json”.

Executive summary — the full picture after two waves

What autosk is

autosk is one senior engineer’s complete answer to “how do I run coding agents as a pipeline instead of a chat window.” Three layers: (1) a file-based task tracker living under .autosk/ inside your repo; (2) an opt-in workflow engine where each workflow is a directed graph of steps written as TypeScript code, each step owned by an agent that a daemon spawns and supervises; (3) three front ends — the autosk CLI, the autosk lazy terminal UI, and a Tauri desktop/iPhone GUI — all pure JSON-RPC clients of the single daemon. Stack: Go (CLI/TUI), Bun/TypeScript (daemon autoskd, compiled to a standalone binary), Tauri/React (GUI), Astro (site). Explicitly inspired by beads, pi.dev and sandcastle (README.md:16-19).

The mechanism that makes it interesting for gosleep: agents are headless CLI child processes speaking newline-delimited JSON over stdio — no PTY, no tmux, no SDK. The daemon spawns claude -p --output-format stream-json … or pi --mode rpc, drives the wire protocol through a ~500-line driver, and forces every step to end in an explicit, host-validated transit tool call. Every failure mode converges on one sink: park the task to human and write an explanatory comment. Auth is subscription-native — the daemon simply runs the operator’s already-logged-in CLI; not a single API key exists in the codebase.

The engine in six sentences

  1. An operator (or agent) creates tasks; autosk enroll attaches a task to a workflow graph and sets it to work.
  2. A single scheduler loop with a global 4-worker FIFO pool scans for schedulable tasks and claims each by creating a queued session — session-creation-as-claim prevents double dispatch (engine.ts:391-453).
  3. The step’s agent spawns a fresh headless child (claude -p or pi --mode rpc) with a prompt carrying the task, the valid transitions, and the full comment history — comments are the inter-step memory.
  4. The model must end its step by calling the ack-only autosk_transit tool; the host observes the call on the wire, validates it against the workflow (onTransit may reject), and commits it after the turn ends.
  5. No transit / rejected transit → kickback re-prompt, 3 attempts; step bounce loops are capped by persisted step_visits counters in task.json.
  6. Every exhausted budget, crash, abort, or structural surprise parks the task to human with an engine comment — bounded autonomy, park early, never spin.

What this means for gosleep — five theses

  1. The driver pattern is the crown jewel. One engine drives two heterogeneous runtimes behind one 4-method contract; everything protocol-specific lives in a per-runtime driver. gosleep’s worker layer should be exactly this thin (§2, §9 rank 1).
  2. The loop-safety vocabulary is complete and small: turn corrections (×3) → persisted per-step visit caps → park-to-human. Adopt wholesale; the counters living in the task file is what makes overnight autonomy auditable (§5, §9 rank 3).
  3. Every gap Wave 1 found is still open — usage-window-aware scheduling, push-on-park, session resume, TLS/tunnel remote. Nobody is closing them from the autosk side. These remain gosleep’s differentiators (§8).
  4. The bug catalog is a gift. The contributor’s six PRs + pi’s own resilience gaps + the TUI’s forensics form a map of orchestration failure modes — dispatch-while-blocked, cancel-vs-result races, agent_settled vs agent_end, children dying pre-protocol — each with a concrete rule gosleep can adopt before hitting it in production (§5, §7).
  5. We take ideas, not dependencies. Everything worth having is a pattern (≈50–500 lines each), not a library: atomic writes, claim ordering, kickback prompts, headless-hardening checklists. §9 ranks all of them by value/effort/risk.

pi-agent/src/driver.ts505 linesthe wire driver — JSONL RPC client over stdio

Purpose: PiDriver wraps the engine’s ChildHandle and speaks pi’s --mode rpc protocol. This single file is the densest concentration of hard-won supervisor knowledge in the whole codebase — each bullet below is a reusable rule for gosleep’s worker harness.

  • Correlation: outbound commands get id: "d<n>" and resolve on the matching {type:"response", id} line (driver.ts:411-421,341-351); all writes are NDJSON lines (driver.ts:423-426). sendPrompt throws if pi rejects the prompt (driver.ts:195-198).
  • Line-oriented resync: non-JSON stdout lines are skipped, not fatal (driver.ts:299-301) — one garbage line never desyncs the channel.
  • Buffered turn-end queue: waitForTurnEnd() returns "ended" | "exited" | "aborted"; turn-end events are buffered in a queue so an agent_end racing the await is never lost (driver.ts:151-153,236-244,393-401). Rule: never await a turn boundary you didn’t subscribe to before sending the prompt.
  • State-dependent input dispatch + one retry: idle → {type:"prompt"} starts a fresh turn; streaming+steer → {type:"steer"}; streaming+followup → {type:"follow_up"}. If pi rejects with a state mismatch (our streaming view raced pi’s — detected by substring heuristics over the error text driver.ts:468-483), retry ONCE with the opposite dispatch shape. Best-effort; never throws (driver.ts:200-234,453-461). A direct port of the retired v1 Rust daemon’s dispatch_input (cited at driver.ts:201-211).
  • Partials — two teardown semantics, carefully separated: a leading+trailing-edge Coalescer bounds message_update snapshots to one emission per 40 ms (driver.ts:50-127). flush() at message/turn boundaries emits the buffered frame before the durable line commits (driver.ts:94-110,311-317); stop() on exit/abort drops the buffered frame so a late timer can never repaint a stale live bubble after the session sealed (driver.ts:112-126,177-190,403-409). Only role:"assistant" snapshots stream (driver.ts:360-371).
  • Transcript mirroring 1:1: committed user|assistant|toolResult messages → ctx.log.message; anything with customType → ctx.log.custom (driver.ts:373-382) — the autosk transcript speaks pi’s message schema natively.
  • Headless hardening: blocking extension_ui_request dialogs are auto-answered {cancelled:true}; fire-and-forget methods (notify/setStatus/setWidget/setTitle/set_editor_text) are ignored (driver.ts:129-130,384-389) — a headless run can never hang on a modal. stderr is always drained (a full pipe would deadlock the child), ANSI-stripped (pi bursts terminal control sequences on teardown even in rpc mode), forwarded via warn with a 100-line cap (driver.ts:135-136,172-176,277-291,489-505).
  • Shutdown ladder: abort command → close stdin → 500 ms grace → kill(); idempotent (driver.ts:253-273). Child exit fails all pending requests with "pi exited" and emits a terminal turn event (driver.ts:177-187).

Loop & resilience layers

  • Turn cycle (agent-loop.ts:155-275): stream response → if stopReason:"length", fail ALL tool calls without executing (truncated args are dangerous agent-loop.ts:383-408) → else execute (parallel or sequential per tool’s executionMode), each through validate→before→execute→after with per-call abort checks; a thrown tool becomes an isError result, never a crash.
  • Steering internals: steer/follow_up enqueue into a PendingMessageQueue drained between turns — they never interrupt an in-flight LLM call; only abort does (AbortController threaded through the provider call and every tool’s execute(…, signal)) (agent.ts:123-157,273-297,310-312; agent-loop.ts:668-709).
  • Retry layers: session-level auto-retry with exponential backoff (default 3 attempts, base 2 s settings-manager.ts:28-33) gated by a regex classifier that retries overloaded/rate-limit/5xx/network but explicitly NOT quota/billing exhaustion (ai/src/utils/retry.ts:7-101); context overflow is a separate path — detected 3 ways incl. “silent overflow” (overflow.ts:129-158), triggering auto-compaction with at most ONE recovery retry per turn (agent-session.ts:1900-1989).
  • Hard-failure shape: any loop exception synthesizes a fake assistant message with stopReason: error and emits the normal event sequence (agent.ts:469-510) — clients always get a well-formed turn end.
  • Tools: read, bash, edit, write on by default; grep, find, ls exist but OFF (core/sdk.ts:245). Truncation 2000 lines / 50 KB; bash streams at ≥100 ms cadence and spills full output to a temp file when truncated (bash.ts:301-393); edit requires unique oldText and serializes same-path mutations. All tool I/O goes through pluggable *Operations seams designed for remote/SSH/container redirection.
  • Extensions load in-process via jiti (TS-transpiling require loader.ts:389-395): project .pi/extensions/ → global ~/.pi/agent/extensions/ → explicit -e/settings → npm packages via the "pi" manifest field. ~30 lifecycle events (several can veto/rewrite — tool_call, user_bash, session_before_*); registerTool makes extension tools first-class. §2.7 · agent_settled vs agent_end — the race, explained simply critical detail

Plain words: agent_end means “the worker put the pen down.” It does not mean the session is finished — pi may pick the pen back up by itself, with no new input from you, in three cases:

  1. Auto-retry: the last turn died on a transient API error (overloaded / 5xx / network) → pi retries with backoff (default 3 attempts, base 2 s).
  2. Overflow compaction: the context overflowed → pi compacts the history and re-runs the turn once (_overflowRecoveryAttempted agent-session.ts:1900-1989).
  3. Queued follow-ups: a follow_up sent mid-turn was queued; the drain loop starts a whole new turn for it.

agent_settled fires only when the internal while(_handlePostAgentRun()) agent.continue() drain is done — “the desk is clear, nothing queued, nothing will restart” (agent-session.ts:1023-1065,534-542; docs/rpc.md:848-854).

The race: a supervisor that treats agent_end as “done” may — while the session is about to continue on its own — send the next prompt (collides with the retry turn), kill the child (loses the retried result), or read “the final message” (gets a truncated one). autosk’s PiDriver keys its turn loop on agent_end (driver.ts:311-318) — workable in practice because autosk treats each turn independently and disables nothing, but it is a latent race with pi’s auto-retry.

gosleep rule: any pi driver we write keys on agent_settled, full stop. More generally: for every harness, identify the event that means “nothing will restart by itself” — and wait for that, not for the first end-shaped event.

Build-better — the gaps autosk leaves open (gosleep differentiators, all still unclosed as of 2026-07-10):

  • Usage-window-aware scheduling: detect subscription-limit exhaustion, quiesce the fleet, auto-resume when the window resets (autosk just parks — §5 row 11).
  • Push-on-park (ntfy / APNs / Telegram): notify the owner the moment work needs a human; autosk has zero notification path.
  • Session resume (claude --resume with the captured session_id; pi’s session tree): daemon restarts and transient failures must not reset in-flight work.
  • TLS/tunnel-first remote access (Tailscale-assumed / SSH) instead of cleartext-token TCP on 0.0.0.0.
