Как читать отчёт — словарик

Каждый термин ниже используется по всему тексту. Больше ничего не предполагается известным.

autosk
сам продукт: файловый таск-трекер + workflow-движок + три интерфейса (CLI, TUI, GUI) для кодинг-агентов. MIT, всё локально.
autoskd
демон — процесс на Bun/TypeScript, собранный в самодостаточный бинарь. Единственный владелец состояния; всё остальное — JSON-RPC-клиенты к нему.
.autosk/
каталог состояния в проекте: tasks/<id>/task.json, comments.jsonl, sessions/*.json(l). Просто файлы, без базы данных.
task / workflow / step
task — «тикет» в файле (new → work → done|cancel|human); workflow — направленный граф шагов, написанный кодом на TypeScript; каждым шагом владеет агент.
session
один запуск одного агента на одном шаге задачи — порождённый дочерний процесс плюс его транскрипт.
агентский рантайм / harness
внешний CLI, который реально говорит с LLM: claude (Claude Code) или pi. autosk запускает его headless и говорит на его wire-протоколе.
driver (драйвер)
класс на стороне демона, владеющий одним дочерним процессом и переводящий его протокол (stream-json или JSONL-RPC) в события движка.
transit
tool-вызов, которым агент обязан завершить свой шаг: autosk_transit {to: "<шаг>|done|cancel|human"}. Модель объявляет, хост валидирует и коммитит.
kickback / corrections
если ход (turn) закончился без transit (или workflow его отклонил), хост допинывает модель корректирующим промптом; бюджет — 3 попытки по умолчанию.
park / human
универсальный сток отказов: любая неразрешимая ситуация переводит задачу в статус human — «припаркована, ждёт человека». Никогда — тихий ретрай.
pi
независимый, активно развиваемый TypeScript CLI-агент (earendil-works/pi, «pi.dev»). autosk управляет им ровно как claude — второй, структурно близнецовый harness.
AgentDefinition
крошечный контракт агента autosk: {onRun, onSteer, onFollowup, onAbort}. Всё специфичное для рантайма прячется за ним.
MCP
Model Context Protocol — способ отдавать модели инструменты. autosk поднимает per-session HTTP MCP-сервер с bearer-токеном.
worktree
одноразовый git-чекаут (git worktree), в котором работает агент, чтобы основной репозиторий оставался чистым до посадки шага.
JSONL / stream-json
оба wire-протокола — это JSON по строкам через stdio: у pi диалект называется «RPC mode», у Claude Code — «stream-json».

Резюме — полная картина после двух волн

Что такое autosk

autosk — это законченный ответ одного сильного инженера на вопрос «как запускать кодинг-агентов конвейером, а не чат-окном». Три слоя: (1) файловый таск-трекер в каталоге .autosk/ внутри репозитория; (2) опциональный workflow-движок, где каждый workflow — направленный граф шагов, написанный кодом на TypeScript, а каждым шагом владеет агент, которого демон порождает и супервизирует; (3) три интерфейса — CLI autosk, терминальный autosk lazy и Tauri-GUI для десктопа/iPhone — все чистые JSON-RPC-клиенты одного демона. Стек: Go (CLI/TUI), Bun/TypeScript (демон autoskd, собранный в самодостаточный бинарь), Tauri/React (GUI), Astro (сайт). Автор прямо ссылается на вдохновение beads, pi.dev и sandcastle (README.md:16-19).

Механизм, из-за которого это интересно gosleep: агенты — это headless дочерние процессы CLI, говорящие построчным JSON через stdio — без PTY, без tmux, без SDK. Демон запускает claude -p --output-format stream-json … или pi --mode rpc, ведёт протокол через драйвер на ~500 строк и заставляет каждый шаг заканчиваться явным, валидируемым хостом tool-вызовом transit. Все отказы сходятся в один сток: припарковать задачу в human и написать поясняющий комментарий. Аутентификация — подписочная по природе: демон просто запускает уже залогиненный CLI оператора; в кодовой базе нет ни одного API-ключа.

Движок в шести предложениях

  1. Оператор (или агент) создаёт задачи; autosk enroll прикрепляет задачу к графу workflow и ставит её в work.
  2. Один цикл планировщика с глобальным FIFO-пулом из 4 воркеров находит планируемые задачи и захватывает каждую созданием queued-сессии — «session-creation-as-claim» исключает двойную диспетчеризацию (engine.ts:391-453).
  3. Агент шага порождает свежий headless дочерний процесс (claude -p или pi --mode rpc) с промптом, несущим задачу, допустимые переходы и всю историю комментариев — комментарии и есть память между шагами.
  4. Модель обязана закончить шаг вызовом ack-only инструмента autosk_transit; хост видит вызов на проводе, валидирует его против workflow (onTransit может отклонить) и коммитит после конца хода.
  5. Нет transit / переход отклонён → kickback-«допинывание», 3 попытки; циклы между шагами ограничены персистентными счётчиками step_visits в task.json.
  6. Любой исчерпанный бюджет, падение, abort или структурный сюрприз паркует задачу в human с комментарием движка — ограниченная автономия, парковаться рано, никогда не крутиться вхолостую.

Следствие для gosleep: относиться к autosk как к замороженной эталонной архитектуре, которую мы разбираем на идеи — не как к зависимости и не как к движущемуся конкуренту. Лицензия MIT и неподвижный HEAD делают его стабильным донором. И заметьте асимметрию: pi жив (HEAD закоммичен сегодня) — сам рантайм pi — живая опция, а его первопартийный packages/orchestrator — прямой prior art для пула воркеров gosleep (§2.9).

Что это значит для gosleep — пять тезисов

  1. Паттерн «драйвер» — главная драгоценность. Один движок ведёт два разнородных рантайма за одним контрактом из 4 методов; всё протокольное живёт в драйвере конкретного рантайма. Слой воркеров gosleep должен быть ровно таким тонким (§2, §9 ранг 1).
  2. Словарь безопасности циклов полон и мал: коррекции хода (×3) → персистентные лимиты посещений шага → парковка в human. Брать целиком; счётчики, живущие в файле задачи, — это то, что делает ночную автономию аудируемой (§5, §9 ранг 3).
  3. Все разрывы, найденные Волной 1, всё ещё открыты — планирование с учётом окна подписки, push при парковке, resume сессий, TLS/туннель. Со стороны autosk их никто не закрывает. Это по-прежнему дифференциаторы gosleep (§8).
  4. Каталог багов — подарок. Шесть PR контрибьютора + собственные бреши pi + форензика TUI образуют карту отказов оркестрации — диспетчеризация заблокированного, гонка cancel-против-результата, agent_settled vs agent_end, дети, умирающие до протокола — и для каждого есть готовое правило, которое gosleep может принять до того, как наступит на грабли в проде (§5, §7).
  5. Мы берём идеи, а не зависимости. Всё ценное — это паттерны (по ≈50–500 строк), а не библиотеки: атомарные записи, порядок захвата, kickback-промпты, чек-листы headless-закалки. §9 ранжирует всё по ценности/усилию/риску.

pi-agent/src/driver.ts505 строкwire-драйвер — JSONL RPC-клиент поверх stdio

Назначение: PiDriver оборачивает движковый ChildHandle и говорит на протоколе pi --mode rpc. Этот единственный файл — самая плотная концентрация выстраданных супервизорских знаний во всей кодовой базе; каждый пункт ниже — переиспользуемое правило для harness’а воркеров gosleep.

  • Корреляция: исходящие команды получают id: "d<n>" и резолвятся на строке {type:"response", id} (driver.ts:411-421,341-351); все записи — строки NDJSON (driver.ts:423-426). sendPrompt бросает, если pi отверг промпт (driver.ts:195-198).
  • Построчная ресинхронизация: не-JSON строки stdout пропускаются, а не фатальны (driver.ts:299-301) — одна мусорная строка никогда не рассинхронизирует канал.
  • Буферизованная очередь концов хода: waitForTurnEnd() возвращает "ended" | "exited" | "aborted"; события конца хода буферизуются в очередь, поэтому agent_end, обогнавший await, никогда не теряется (driver.ts:151-153,236-244,393-401). Правило: никогда не жди границу хода, на которую не подписался до отправки промпта.
  • Диспетчеризация ввода по состоянию + один ретрай: idle → {type:"prompt"} открывает новый ход; streaming+steer → {type:"steer"}; streaming+followup → {type:"follow_up"}. Если pi отвечает state mismatch (наше представление о стриминге разошлось с реальностью pi — детектится эвристикой по подстрокам текста ошибки driver.ts:468-483), ретраим ОДИН раз противоположной формой. Best-effort; никогда не бросает (driver.ts:200-234,453-461). Прямой порт dispatch_input из списанного v1-демона на Rust (ссылка в driver.ts:201-211).
  • Partials — две семантики сноса, тщательно разделённые: Coalescer (передний+задний фронт) ограничивает снапшоты message_update одной эмиссией в 40 мс (driver.ts:50-127). flush() на границах сообщения/хода испускает буферизованный кадр до коммита долговечной строки (driver.ts:94-110,311-317); stop() при exit/abort выбрасывает буферизованный кадр, чтобы поздний таймер не мог перерисовать устаревший «живой» пузырь после запечатывания сессии (driver.ts:112-126,177-190,403-409). §2.7 · agent_settled vs agent_end — гонка на пальцах критическая деталь

Простыми словами: agent_end означает «работник положил ручку на стол». Это не значит, что сессия закончена — pi может взять ручку обратно сам, без нового ввода от вас, в трёх случаях:

  1. Auto-retry: последний ход умер на временной ошибке API (overloaded / 5xx / сеть) → pi ретраит с backoff (по умолчанию 3 попытки, база 2 с).
  2. Компакция при переполнении: контекст переполнился → pi сжимает историю и один раз перезапускает ход (_overflowRecoveryAttempted agent-session.ts:1900-1989).
  3. Отложенные follow-up: follow_up, присланный посреди хода, встал в очередь; цикл вычитки начнёт для него целый новый ход.

agent_settled срабатывает только когда внутренний цикл while(_handlePostAgentRun()) agent.continue() вычитал всё — «стол чист, в очереди пусто, ничего само не перезапустится» (agent-session.ts:1023-1065,534-542; docs/rpc.md:848-854).

Сама гонка: супервизор, считающий agent_end концом, может — пока сессия вот-вот продолжится сама — отправить следующий промпт (столкновение с ретрай-ходом), убить ребёнка (потерять результат ретрая) или прочитать «финальное сообщение» (получить обрезанное). PiDriver autosk завязывает свой цикл ходов на agent_end (driver.ts:311-318) — на практике работает, потому что autosk трактует каждый ход независимо и ничего не отключает, но это латентная гонка с auto-retry pi.

Правило gosleep: любой наш драйвер pi ждёт agent_settled, точка. Обобщение: для каждого harness найди событие, означающее «само ничего не перезапустится», — и жди именно его, а не первое попавшееся событие, похожее на конец.
