01

What “loop engineering” actually is

Every term below is introduced from scratch. You do not need to know any of this vocabulary going in.

One sentence: loop engineering is the discipline of wrapping a coding agent in an outer control loop — restart it fresh, feed it saved state from disk, check its progress, and decide to continue / stop / escalate — so useful work keeps flowing past any single memory window and without a human pressing “continue”.

The insight that started the field is almost embarrassingly simple. An LLM agent is already a loop: the model thinks, calls a tool, reads the result, thinks again — round and round until it decides to stop. But that loop lives inside one context window (the finite amount of text a model can hold at once), and it dies when that window fills up. The community's answer was to put a while true around the whole agent and make the filesystem + git the memory that survives each restart. Everything since — stop conditions, budgets, circuit breakers, checkpoints — is engineering discipline layered onto that while true.

The core mental model — two loops, nested Inner loop = the agent's own think→tool→observe cycle, inside one context window. It is bounded by the window, and it's the model vendor's problem. Outer loop = the harness that re-invokes a fresh agent across windows — the while true. It is bounded only by your guards, and it is your problem. Loop engineering = engineering the outer loop.
A vocabulary map — every one of these appears again below
  • Inner loop — the agent's think→tool→observe cycle inside one context window.
  • Outer loop — the harness that re-invokes the agent across windows (the while true).
  • Harness — everything around the model: tools, state files, restart logic, guards. “Harness engineering” ≈ “loop engineering”; the latter stresses the restart cycle.
  • Stop condition / definition-of-done — a machine-checkable test that ends the outer loop (not “the model feels done”).
  • Circuit breaker / loop guard — detectors that halt a loop making no progress (runaway protection).
  • Checkpoint & resume — durable state written at each boundary so a fresh agent can continue from disk.
  • Heartbeat — a periodic “I'm alive / anything to do?” tick, usually cheap.
  • Watchdog — a separate process that watches the loop and intervenes when it wedges.
  • Park / escalate — routing a stuck task to a human queue instead of retrying forever.
02

Where it came from — the canon, with dates

A short, sourced chronology. Each node is a primary document that was actually fetched or read from source.

↔ Scroll horizontally on a narrow screen. Sources fetched or read from source (see §Sources).

PHASE 0 · 2024 → early 2025

The agent is a loop

Anthropic's “Building effective agents” 1 and Thorsten Ball's “How to build an agent” popularise the observation that a coding agent is ~300 lines: model + tools + a while-loop. That's the inner loop. Its hard limit: the context window.

PHASE 1 · 2025-07-14

The Ralph loop

Geoffrey Huntley ships the founding document of outer-loop engineering 2. Named after Ralph Wiggum (The Simpsons): try the same thing over and over until it works. Deliberately dumb orchestration; all determinism lives in PROMPT.md + specs on disk. Field claim: “shipped 6 repos overnight”.

PHASE 2 · 2025-11 → late 2025

Canonization

Anthropic's harness engineering write-up 3 formalises the same shape (initializer + coding agent). The vendor ships an official ralph-wiggum plugin 5. Community hardens it into production runners (ralph-claude-code 6); Steve Yegge's Gas Town 7 scales it to an org-chart of loops.

PHASE 3 · 2026

It gets a name

Addy Osmani systematises the vocabulary 4 (30+ hours autonomous coding, 11k-line app in one run) and in June 2026 popularises the term “loop engineering”. An explainer wave follows. Consensus five blocks: find work → act → verify → remember → repeat on a trigger.

The arc in one line: 2024 “the agent is a loop” → 2025 “put a loop around the agent” (Ralph) → 2026 “engineer that loop like production infrastructure” (loop engineering).
03

The pattern catalogue — ten reusable moves

Everything the field has learned, factored into ten patterns. Each card: ◆ the essence in plain words · ▚ where it is implemented (real systems) · ▲ the pitfalls that bite people.

1

Outer loop vs inner loop

the load-bearing distinction — everything else hangs off it
Essence

The inner loop (model→tool→observe) is bounded by one context window and is the vendor's problem. The outer loop (spawn a fresh agent → point it at durable state → check progress → decide continue/stop/escalate) is bounded only by your guards and is yours. Loop engineering is engineering the outer loop.

Where

Ralph's one-liner; Anthropic's initializer / coding-agent split; every runner below.

ghuntley/ralphanthropic harness
Pitfalls

Conflating the two loops. Inner-loop tricks (compaction, bigger windows) delay but never remove the need for an outer loop — Osmani: context rot degrades performance well before token limits, so a fresh-context restart beats stretching a tired one.

2

Stop conditions & definition-of-done

how the loop knows it is actually finished
Essence

The loop must end on a machine-checkable test declared before the run — never on the model “feeling done”. State done as data, not prose.

Where

Anthropic: a JSON feature list (200+ items all starting failing; done = all passing; the spec forbids editing/removing tests). Carson's prd.json stories flip passes:false→true; exits only on <promise>COMPLETE</promise> AND all-pass, with a hard max_iterations backstop. ralph-claude-code has the most-engineered exit anywhere: a dual-condition gate (≥2 accumulated completion signals AND explicit EXIT_SIGNAL:true) plus a safety force-exit.

anthropic feature-listsnarktank/ralphralph-claude-code
Pitfalls

Single-signal exits (model declares victory early — Anthropic saw this constantly). The model editing the done-predicate itself (hence “don't touch tests” clauses). Stale exit signals surviving a restart (ralph-cc clears .exit_signals between sessions).

3

Budget guards / token ceilings

hard caps that survive a restart
Essence

Hard, mechanism-level caps on iterations, calls, tokens, and dollars — because a cap that only lives in the prompt does not self-enforce under pressure.

Where

ralph-claude-code: MAX_CALLS_PER_HOUR=100 (hourly reset), optional cumulative token cap, per-run sandbox MAX_COST in USD, 15-min per-call timeout. autosk persists visit-count budgets in task.json, human-resettable. warren adds the hard-won rule that a malformed budget must fail OPEN — a budget typo must never silently cancel every run.

ralph-claude-codeautosk task.jsonwarren
Pitfalls

Budgets that only exist in the prompt (ignored). Budgets without persistence (a restarted loop forgets it already spent the ceiling). Budgets that fail closed on a config typo (warren's lesson — kills every run).

4

Checkpoint & resume

write state at every boundary so anyone can continue from disk
Essence

Every iteration ends by writing durable state (a commit + a progress note), so any next iteration — same loop or a cold restart days later — resumes from disk, not from memory.

Where

Anthropic: claude-progress.txt + descriptive commits; the initializer agent exists purely to create this resume surface. Carson: memory is only git history + append-only progress.txt + prd.json flags, and he checkpoints knowledge too — appending codebase gotchas to AGENTS.md so later iterations inherit them. warren routes even watchdog-killed runs “through reap, not bare finalize” so partial committed work is never lost.

anthropic progress.txtsnarktank AGENTS.mdwarren reap
Pitfalls

Checkpointing to chat/scrollback (lost on compaction). Resuming a stale session instead of fresh context (a session-hijacking bug class). Progress files that grow unbounded. Trusting the checkpoint over live git (gosleep already handles this with atomic temp+rename and “live git wins”).

5

Self-pacing & the cache window

deciding when to wake next — and why 5 minutes matters
Essence

An unattended loop must decide when to wake next. Fixed cron is either wasteful (nothing changed) or slow (something urgent). The 2026 refinement: pick intervals against the prompt-cache lifetime, because cache economics dominate the cost of an idle loop. Fully unpacked in §04.

Where

OpenClaw's canonical heartbeat vs cron split: a heartbeat is a periodic turn in the main session that reads a tiny stable checklist and batches all checks into one turn; cron is detached isolated jobs. Cost levers: isolated sessions (~100K → 2–5K tokens/run), cheap model, active-hours windows. Claude Code's own ScheduleWakeup / dynamic /loop encodes exactly the cache-window rule (“don't pick 300s”).

OpenClaw heartbeatScheduleWakeup
Pitfalls

Polling every N min “to be safe” — each tick is a full agent turn (burnout-by-token-bill). Wake-ups that re-trigger expensive work instead of cheap triage. A heartbeat whose session context grows forever (answer: isolated session + tiny checklist). Fixed cron with no “nothing to do → say OK and exit cheap” fast path.

6

Overnight / unattended

running while the human sleeps; a reviewable morning, not raw logs
Essence

The loop runs while the human sleeps. Every human touchpoint is either removed (auto-approve within scoped permissions), deferred (morning queue), or fatal (park). The morning deliverable is a reviewable digest, not raw logs.

Where

The Ralph lineage (“ship features in your sleep… come back to completed features, passing tests, committed code”). ralph-cc's explicit unattended mode auto-waits through the 5-hour subscription limit instead of exiting. OpenClaw's morning-brief cron + active-hours + “only wake the human for alerts”. Gas Town runs the whole town on patrols and hands the owner a morning-readable capability ledger. autosk's park-to-human morning queue.

geocod.io ralphralph-cc unattendedOpenClaw briefGas Town ledger
Pitfalls

Auto-approving beyond scoped permissions (community consensus keeps merge/deploy/destructive human-gated even at max autonomy). Rate-limit windows misread as errors. Waking to 40 unlabeled branches — the digest is as important as the work. No rollback path.

7

Question buffering

don't stop the whole loop on one question
Essence

Overnight, a blocking question is a stall. Three answers, increasing in sophistication: (a) park the task and move on; (b) pause with a budget — wait for an async human answer, auto-resolve on timeout; (c) buffer & continue — log the question, take the reversible default, keep working, surface the buffer in the morning digest. (c) is the ideal for gosleep and the least implemented in public code.

Where

warren is the most concrete: workers emit question_posed onto an event log → the run flips to paused; a human answers via API, OR the pause budget expires and the run proceeds. Questions are events, not modal dialogs. autosk uses park-to-human as a universal sink. OpenClaw rate-limits the question channel by design (batch, suppress OK-noise). Osmani: “delegated approval with full execution-state preservation”.

warren pause-budgetautosk parkOpenClaw suppress
Pitfalls

Parking too eagerly (one ambiguous lint rule shouldn't stall a feature — that's what buffer-and-default is for). Answering with irreversible defaults (buffering only works when the default is cheap to undo). Question spam — the buffer needs dedup (same question from 5 cycles = 1 morning item).

8

Verification loops

a fresh judge, because the generator can't grade its own homework
Essence

The generator must not grade its own work. A separate stage — a fresh agent, a test suite, or a browser — verifies each increment before the done-flag flips; ratchets stop regressions (a metric may only go up).

Where

Anthropic's decisive finding: Claude marked features done prematurely until given browser automation (Puppeteer MCP) to test “like a user”. Osmani's planner/worker/judge split + test ratchets. Huntley's “backpressure”: compilers and static analyzers wired in so a bad iteration can't advance. Gas Town: the Refinery reviews worker output; the Witness verifies progress independently of the worker's own claims.

anthropic puppeteerosmani judgegastown witness
Pitfalls

A verifier that shares the generator's context (inherits its assumptions — fresh context is the whole point). Verification the model can edit (test deletion). A verifier that hangs and freezes the loop (gosleep's E17 watchdog exists for exactly this; ralph's per-call timeout is the loop-level equivalent).

9

Anti-runaway protections

a spinning loop is worse than a stopped one
Essence

A loop that spins without progress burns budget and can damage the tree — worse than a stopped loop. Detection is multi-signal (progress, error repetition, output shape); response is staged (halt → cooldown → human). Fully worked in §05.

Where

ralph-claude-code's full Nygard-style circuit breaker (CLOSED/HALF_OPEN/OPEN; opens on 3 no-progress loops, 5 same-error loops, >70% output decline, or 2 permission-denial loops; 30-min cooldown then probing). Gas Town's watchdog chain (Witness → Deacon → Boot-the-Dog checks the Deacon every 5 min) with the hard rule never declare an agent stuck from a single store. warren derives heartbeat from the newest event row and self-arms by default.

ralph circuit_breaker.shgastown bootwarren liveness
Pitfalls

Single-signal stuck-detection. Watchdogs nobody watches (Boot exists because the Deacon itself died in practice). Kill paths that destroy partial work (warren's reap rule). Self-reported heartbeats — a wedged agent can't report; derive liveness from artifacts (events, commits, file mtimes).

10

State-on-disk

the filesystem + git ARE the loop's memory
Essence

The filesystem + git are the loop's memory. Everything needed to decide “what next” must be re-derivable from disk by a reader with zero prior context.

Where

Every serious system converges on the same trio: (1) work state — prd.json flags / feature-list JSON / Beads ledger / task.json counters / event log. (2) narrative — append-only progress.txt / capability ledger / AGENTS.md accumulation (the loop improves its own future prompts). (3) loop-control state — .ralph/ exit signals + circuit-breaker JSON + metrics, heartbeat stores, pause/visit budgets.

all systems
Pitfalls

State only in the session (dies with it). Non-atomic writes (truncated batons — gosleep's temp+rename rule). Human-unreadable state (the owner must triage from a phone — autosk's human-resettable JSON counters are the exemplar). Prose walls instead of structured state.

04

The economics of self-pacing

Why an idle loop's cost is dominated by one number you can't see on a dashboard — the prompt-cache lifetime.

First, what the prompt cache is. When you send a big prompt (system instructions, the standing state file, the checklist) to a model, the provider can cache that prefix. If you send almost the same prompt again soon, you pay a fraction of the price for the cached part. The catch: the cache has a lifetime (TTL). Miss the window and the next call re-pays full price for the whole prefix — a cache miss.

What changed. Anthropic's default cache TTL silently dropped from 1 hour → 5 minutes on 2026-03-06. Loops that polled every 15–30 minutes were tuned for the old 1-hour window; overnight they suddenly ate a full cache miss on every single tick — community reports of +30–60% effective cost.

The emergent rule Poll inside the cache window (<5 min) or commit to long sleeps (20–30 min+) and eat exactly ONE cache miss. The worst possible cadence is just past the TTL — say 6–10 minutes — where you pay a full miss every time and gain nothing for it.

The cheap-triage principle Because every wake-up is a full agent turn, the wake-up must do the least work that answers “anything to do?”. OpenClaw's heartbeat shape: read a tiny stable checklist (so the cache stays valid), batch all the checks into one turn, and take a “nothing changed → say OK and exit” fast path. A wake-up that re-runs an expensive slash command instead of a cheap triage is the classic self-inflicted wound (Claude Code bug #54086).
05

Anti-runaway, at reference quality

Two production systems solved “stop a loop that's spinning” properly. Their code carries lessons no design doc conveys — every one of these is a scar from a real incident.

Reference A — ralph-claude-code

The dual exit gate + circuit breaker

v0.11.x, 784 tests — the bash one-liner turned into a production loop runner.

The dual-condition exit — done needs BOTH:

  • ≥2 accumulated completion indicators across recent loops (tracked in .exit_signals JSON), AND
  • the agent's explicit EXIT_SIGNAL: true in its response.

Plus a safety force-exit after 5 consecutive EXIT_SIGNAL=true in case the normal path wedges; and STATUS: COMPLETE with EXIT_SIGNAL:false explicitly continues. Exit signals are cleared between sessions so a stale one can't fire.

The circuit breaker — a Nygard state machine in circuit_breaker.sh:

CLOSED
normal flow
HALF_OPEN
probing
OPEN
tripped

Opens on any of: 3 loops with no progress · 5 loops with the same error · >70% output decline · 2 permission-denial loops. Then a 30-min cooldown → HALF_OPEN (one cheap probe) — it doesn't hard-stop, it retries once. All thresholds env-configurable; state persisted as JSON. Progress = git commits within a loop, but git motion never counts as completion.

Reference B — Gas Town

The watchdog chain, and its scars

Steve Yegge's industrial-scale org-chart of loops — read from Go source.

Who watches whom:

Witness → workers· Deacon → system· Boot → the Deacon, every 5 min

Boot is not a dumb timer — it's a fresh LLM triage agent on each daemon tick, choosing one of four actions: start / wake / nudge / nothing. A flock + marker file keeps it single-flight (it can't overlap itself).

Production war-wounds (each is a fixed incident):

  • Startup grace period — the heartbeat check was killing freshly-started sessions before they could write a first heartbeat (issue #567). Every watchdog needs a warm-up exemption.
  • Counter + cooldown, never one-shot — force-kill only after 3 consecutive ping failures, then a 5-min cooldown between kills.
  • Zombie debounce — needs ≥3 consecutive cycles of “tmux session exists but no agent process” before restart. Pane-alive and process-alive are different signals that diverge routinely during handoffs.
  • Crash-loop backoff — a RestartTracker with exponential backoff (warren independently evolved the same 5-restarts-in-60s budget).
  • Mass-death detection — many deaths at once is a different (systemic) failure than one death.
  • Bounded fan-out — the watchdog checks rigs in a worker pool with per-rig timeouts, so one slow rig can't block all others.
The distilled lesson for gosleep's watchdog-above-the-orchestrator Every watchdog decision must be (a) counter-debounced, (b) cooldown-limited, (c) exempt during warm-up, and (d) the watchdog itself single-flight + rate-limited. A naïve “STATE file is stale → restart the orchestrator” script will fire on false positives its first night — a session between turns, a fresh start mid-write, a transient handoff gap. Debouncing is not gold-plating; it's the difference between a watchdog and a self-inflicted outage.

What to adopt, ranked

Ranking = value for “owner-sleeps” ÷ effort. Each item names the mechanic, what it detects/solves, and the build cost. Items 1 + 2 + 3 together are the minimum viable “owner goes to sleep” package.

Minimum viable “owner sleeps” package #1 self-pulse (never doze off) + #2 night mode & morning digest (a reviewable morning) + #3 question buffer (don't stall on questions). All LOW-to-MED effort, no new infrastructure. #4 makes it survive the orchestrator's own death; #5–#8 raise long-run quality and economy.
1

Armed self-pulse with cache-aware pacing MVP

The orchestrator never ends a turn while the fleet is live without a scheduled wake-up (ScheduleWakeup in Claude Code; a cron/sleep wrapper elsewhere). A pulse is a cheap triage tick: read STATE, probe liveness signals, act only on deltas — OpenClaw's heartbeat shape (tiny stable checklist, “OK → do nothing” fast path). Cadence from the canon: <5 min while actively wedging a stall (cache warm), 20–30 min while workers grind (one amortized miss).

Solves: the whole “orchestrator dozes off / turn ends and nobody watches” class — the owner's pulse-rule mandate, finally mechanized.

EFFORT · LOWVALUE · HIGHskill text + a pacing table; the tools already exist
2

Night mode + morning digest MVP

A declared unattended window. During it, AskUserQuestion is forbidden except for denylist items; every would-be question goes to the buffer (#3). At window end the orchestrator writes docs/handoff/MORNING-DIGEST-<date>.md: work landed, verdicts, parked items, buffered questions, budget spent vs ceiling.

Solves: the owner waking to 40 branches and no narrative; makes “go to sleep” an explicit mode with tightened rails.

EFFORT · LOW-MEDVALUE · HIGHprotocol + template; no new infra
3

Question buffer with pause-budget defaults MVP

Three-tier triage of any fork that isn't denylist: (a) reversible + low-stakes → take the default, log the question+choice to QUESTIONS.md (buffer-and-continue); (b) material but not dangerous → warren-style pause that task with a budget, park it, reassign the worker to the next unblocked task; (c) denylist/irreversible → BLOCKED_ON_HUMAN as today. Dedup identical questions across cycles.

Solves: overnight stalls on questions — today every ambiguity stops a thread until morning.

EFFORT · MEDVALUE · HIGHprotocol in worker template + orchestrator triage rules
4

Watchdog above the orchestrator (the Boot layer)

An external, dumb, non-LLM check (cron script or cheap Monitor loop): “has ORCHESTRATION-STATE.md mtime / the TELEMETRY line advanced in N min while open_workers>0?” If stale → notify the owner AND/OR relaunch a fresh orchestrator pointed at the cold-start protocol, under a warren-style restart budget (e.g. 3/night, then page the owner). Liveness derived from artifacts (file mtime, git), never self-report. Apply §05's debounce lessons — counter-debounce, cooldown, warm-up grace, single-flight.

Solves: a dead/compacted orchestrator orphaning a live fleet overnight — the one failure the skill cannot self-recover from.

EFFORT · MEDVALUE · HIGHsmall script + skill section; the cold-start protocol it triggers already exists
5

Machine-checkable definition-of-done per phase

Adopt the feature-list/prd.json pattern: each epic carries a JSON checklist with passes flags flipped only after verification; loop-level done = all-passing + PR merged, not “worker said COMPLETE”. Ban done-predicate edits (Anthropic's “unacceptable” clause) in worker briefs.

Solves: premature victory across cycle boundaries; gives the loop guard a real predicate to check.

EFFORT · MEDVALUE · MEDfits the existing Jira-mirrored task structure
6

Circuit-breaker upgrade for the loop guard

Extend the existing loop guard with ralph-claude-code's signals: same-error-N-times across cycles, output/progress decline, and a cooldown + HALF_OPEN probe (one cheap retry after a pause) instead of a hard STOP. Counters persisted in STATE and human-resettable (autosk's phone-editable counters).

Solves: both false-halts (a transient flake tripping the guard permanently) and busy-runaways the current two-signal guard misses.

EFFORT · MEDVALUE · MEDextends an existing mechanism
7

Per-cycle learnings checkpoint (the AGENTS.md pattern)

Workers append codebase gotchas to a standing LEARNINGS file that the next brief points at; the loop's prompts improve as it runs (Carson's most-copied trick). We already do this for automation-traps only — generalize it.

Solves: every fresh cycle re-discovering the same traps.

EFFORT · LOWVALUE · MEDgeneralize an existing registry
8

Sleep-time consolidation (idle-gap compute)

While workers grind and the orchestrator waits, spend idle wake-ups on cheap memory work: compress old STATE log entries, distill the night's LEARNINGS, pre-draft the morning digest. The research cousin is Letta's sleep-time compute (paper 2025-04): background agents share memory with the primary and rewrite it asynchronously — reported up to +18% accuracy and 2.5× lower cost/query by precomputing during idle. Distinction worth keeping sharp: Ralph loops do more work overnight; sleep-time compute makes the next day's work cheaper & smarter.

Solves: STATE-file sprawl and morning-digest latency — for free, during waits.

EFFORT · LOWVALUE · nice-to-havea standing “if nothing to triage, do one consolidation chore” clause

Takeaways

What the field settled
  • Loop engineering is a real, dated discipline — not a metaphor. It has a founding document (Ralph, 2025-07), a vendor blessing (Anthropic harness, 2025-11), and a name (2026-06).
  • The whole field is one idea plus discipline: while true around the agent, with the filesystem + git as memory — then stop conditions, budgets, breakers, checkpoints layered on.
  • The 2026 frontier is economic: the 5-minute cache TTL now dictates wake cadence, and idle cost dominates overnight bills.
  • The two hardest-won lessons are both about not trusting a single signal: don't trust the model's “I'm done”, and don't trust one heartbeat store to declare an agent stuck.
What it means for gosleep
  • Our worker side is already canon-grade or better — state, batons, patience clocks, verification, telemetry, authority model. Keep it.
  • Our one structural hole is the orchestrator as a self-scheduling, self-healing loop. Every missing capability is a facet of that.
  • The fix is mostly prose + templates, not infrastructure: adoptions #1–#3 (self-pulse, night mode, question buffer) are the sleep-enabling minimum, all LOW-to-MED effort.
  • #4 (a debounced watchdog above the orchestrator) is what turns “runs overnight” into “survives its own death overnight”. Build it with §05's scars in mind — debounce or it fires false the first night.
