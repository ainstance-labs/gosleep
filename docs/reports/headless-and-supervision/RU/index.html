Закроет ли его Anthropic?
МАЛОВЕРОЯТНО

Каждая волна ограничений 2026 года била по сторонним обвязкам на подписочных OAuth-токенах — и ни разу по официальному CLI. В июне 2026 Anthropic построила для headless-режима систему тарификации. То, что собираются убить, — не тарифицируют. Остаточный риск: размеры пула и ставки могут пересмотреть в любой момент.[8],[10]

Кто сегодня следит за оркестратором?
НИКТО

Наш надзор — ровно один уровень вглубь: оркестратор следит за воркерами; за оркестратором не следит никто. Если он умрёт или зависнет в 3 часа ночи — флот простаивает до утра. Решение (§5): heartbeat-файл + механический launchd-watchdog + restart budget + эскалация к владельцу — ноль токенов, без ИИ в контуре.

TL;DR для владельца, который хочет спать Оставляем текущий движок tmux + Agent Teams (он живёт на щедрой интерактивной квоте, которую Anthropic последовательно защищает). claude -p используем только для ограниченных «клеевых» задач с жёсткими бюджетными капами на каждый запуск и следим за расходом кредитов. Никогда не подключаем наш подписочный логин к сторонним инструментам — это единственное, за что реально банят аккаунты. И достраиваем недостающий слой надзора: тупой, бесплатный по токенам watchdog-скрипт, который перезапускает мёртвого оркестратора из он-диск-леджера и будит вас только тогда, когда его бюджет рестартов исчерпан.
Секция 1

Что такое claude -p — объяснение с нуля

Предварительных знаний не требуется. Каждый термин определяется по мере появления; вся механика — из официальной документации Anthropic (получена 2026-07-07).[1]

1.1 Начнём на шаг раньше: что такое Claude Code

Claude Code — официальная консольная программа Anthropic (CLI). Вы набираете claude в терминале — и прямо там открывается интерактивный чат: вы описываете задачу обычным языком, а агент читает ваши файлы, правит код, запускает команды и тесты, спрашивая разрешение на всё чувствительное. Именно такие интерактивные сессии — то, как сегодня работают оркестратор и воркеры gosleep, внутри панелей tmux.

1.2 Флаг: -p превращает того же агента в одноразовую команду

claude -p "сделай X" (длинная форма --print) запускает ровно того же агента один раз, без чат-интерфейса: он выполняет задачу, печатает ответ в стандартный вывод и завершается. Это и означает слово «headless» — программа работает без своей интерактивной «головы». Один флаг превращает Claude Code в обычный кирпичик Unix: его можно встраивать в конвейеры, скрипты, cron и циклы:

# ведёт себя как любая другая shell-команда
cat build-error.txt | claude -p 'объясни первопричину' > diagnosis.txt

# машиночитаемый результат: ответ + id сессии + стоимость этого запуска
claude -p 'сделай сводку открытых PR' --output-format json

Принципиально: это не другой продукт и не «сырое» обращение к API — та же модель, те же инструменты (Bash/Read/Edit/…), тот же контекст проекта (CLAUDE.md, скиллы, MCP-серверы) и — ключевое для нас — тот же логин, что и у интерактивной сессии.[1]

Что совпадает с интерактивным Claude Code

  • Модель и сам агентный движок
  • Все инструменты: shell, чтение/правка файлов, веб, MCP
  • Контекст проекта: CLAUDE.md, скиллы, конфигурация MCP (если не передан --bare)
  • Аутентификация — существующий подписочный логин машины
  • Скиллы работают: /имя-скилла прямо в строке промпта

Две вещи, которые меняются

  • Некому отвечать на запросы разрешений. Инструменты одобряются заранее (--allowedTools "Bash(git diff *),Read,Edit") или задаётся --permission-mode; всё не одобренное либо автоматически отклоняется, либо прерывает запуск. --dangerously-skip-permissions убирает запросы совсем (с парой зашитых предохранителей вроде rm -rf /).
  • Вывод становится машиночитаемым. --output-format json возвращает результат плюс session_id, total_cost_usd и расход токенов; stream-json даёт поток событий в реальном времени; --json-schema принуждает к структурированному выводу.

1.4 Agent SDK: тот же движок в виде библиотеки — но другие правила

Claude Agent SDK (TypeScript @anthropic-ai/claude-agent-sdk, Python claude-agent-sdk; переименован из «Claude Code SDK») — тот же движок, выставленный как библиотека для программистов. Официальные доки буквально описывают claude -p как «использование Agent SDK через CLI»; механически SDK упаковывает и запускает бинарник Claude Code, общаясь с ним через stdio, — это не отдельная реализация.[2] Что он добавляет по сравнению с вызовом claude -p из shell: внутрипроцессные hooks (PreToolUse/PostToolUse/Stop…), собственные инструменты, колбэк разрешений canUseTool (программное одобрение посреди запуска), нативные объекты сессий, структурированные выводы, двунаправленный стриминг.

Критическая асимметрия: SDK ≠ подписка Документация SDK описывает только аутентификацию по API-ключу / через облачных провайдеров. Явная позиция Anthropic (дословно): «Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Please use the API key authentication methods described in this document instead.»[2] Запрет нацелен на продукты, предлагающие подписочную авторизацию другим людям; про частное личное использование SDK со своим подписочным токеном доки молчат — недокументировано, не одобрено, избегать. Правило на пальцах: claude -p = легально на подписке; Agent SDK = API-ключ.

1.5 Как headless-запуск аутентифицируется (и «гоча», которая молча тратит деньги)

Сначала два слова. Подписка (Pro/Max) — фиксированный месячный тариф, в который вы логинитесь через OAuth командой /login. API-ключ — потокенная девелоперская тарификация: каждый токен стоит реальных денег, потолка нет. Headless-запуск выбирает учётные данные в официальном порядке приоритета (выше — сильнее):[1]

  1. Учётные данные облачного провайдера (Bedrock / Vertex / Foundry)
  2. Переменная окружения ANTHROPIC_AUTH_TOKEN
  3. ANTHROPIC_API_KEY — «в неинтерактивном режиме ключ используется всегда, если присутствует»
  4. Скрипт apiKeyHelper
  5. CLAUDE_CODE_OAUTH_TOKEN — из claude setup-token: официальный, годовой, подписочный токен для CI/скриптов (только inference; требует Pro/Max/Team/Enterprise). Официальный GitHub Action принимает его как полноправный вход.[15]
  6. Подписочный OAuth из /login — умолчание для пользователей Pro/Max.
Гоча: случайный API-ключ молча «перехватывает» подписку Поскольку правило 3 сильнее правила 6, экспортированный где-нибудь в окружении ANTHROPIC_API_KEY заставляет каждый headless-запуск платить через API — потокенно, реальными деньгами, — хотя машина залогинена по подписке. Санитарная проверка перед любым запуском без присмотра: unset ANTHROPIC_API_KEY. В §6 предлагается вшить эту проверку в install.sh/doctor.

Итог: на залогиненной Pro/Max-машине claude -p просто работает на подписке — так задумано, уже сегодня, и для headless-окружений Anthropic даже выпускает официальный подписочный токен (setup-token).[1],[15]

1.6 Официальные автономные поверхности рядом с -p

1.7 Мини-глоссарий (термины, используемые по всему отчёту)

Headless
Работа без интерактивного интерфейса — без человека за клавиатурой; вход подали, выход получили, процесс завершился.
OAuth / подписочный логин
Вход через браузер; токен сохраняется в системном keychain. Это то, что делает /login для Pro/Max.
API-ключ
Потокенная девелоперская тарификация. Безлимитный потолок — и безлимитный счёт.
Пул программных кредитов
С ~2026-06-15: месячный долларовый лимит внутри подписки, из которого списывается headless/скриптовое использование по прайсу API (см. каведат в §2).
Оркестратор / воркер
Разделение ролей в gosleep: один ведущий агент координирует (спавнит, мониторит, сцепляет циклы); одноразовые воркеры выполняют по одному куску работы, ограниченному контекстом.
Watchdog («сторожевой пёс»)
Процесс, единственная работа которого — проверять, что другой процесс жив и здоров, и действовать, когда это не так.
Heartbeat («пульс»)
Периодический наблюдаемый сигнал «я жив» — лучшая практика: таймстемп, записанный на диск, а не убеждение в памяти процесса.
launchd
Встроенный менеджер служб macOS: запускает скрипты по интервалу, переживает перезагрузки и корректнее cron обрабатывает пробуждение после сна.
Tick loop («цикл-тик»)
Паттерн тупого планировщика: проснуться раз в N секунд/минут, просканировать состояние на диске, отреагировать на изменения, завершиться. Без памяти между тиками.
Restart budget («бюджет рестартов»)
«Не больше N перезапусков за окно» — компонент, падающий по кругу, эскалируется к человеку, а не молотится вечно.
Zombie-сессия
Контейнер жив, а мозг мёртв: панель tmux существует, но процесс Claude внутри неё завершился.
Контекстное окно / компакция
Конечная рабочая память модели. Когда она заполняется, сессия сама себя пересказывает («компактится») — оркестратор может потерять нить именно так.

2.2 Вердикт: где claude -p на подписке находится сегодня (2026-07-08)

Легально и работает

claude -p продолжает работать под логином Pro/Max — это официальный CLI, и само сообщение об ошибке энфорсмента говорит, что учётные данные «авторизованы только для использования с Claude Code». Скриптовать официальный CLI ≠ сторонняя обвязка на вашем OAuth-токене. С ~2026-06-15 списание идёт из пула программных кредитов по прайсу API; интерактивная работа в терминале сохраняет классическую модель 5-часовых + недельных окон.

Но с потолком бюджета, а не flat-rate

План Max 20x даёт ≈$200/мес программных кредитов. Загруженный ночной флот на claude -p по ставкам API может сжечь это за считанные дни. «Headless на подписке» теперь легален и поддержан, но ограничен — это бюджет, а не лазейка. Основной объём работы должен жить на интерактивной квоте (tmux + Agent Teams) — она по-прежнему намного щедрее в пересчёте на доллар.

Июньское разделение — самый сильный сигнал всего таймлайна: для headless-использования подписки Anthropic выбрала решение «тарифицировать, а не запрещать». Реалистичный сценарий провала — не «Anthropic банит claude -p», а «квоту/кредиты подожмут» — это проблема бюджетирования, а не экзистенциальная. Мейнтейнер ralph независимо пришёл к тому же выводу и вдобавок отверг обходной путь «программно дёргать интерактивный TUI, чтобы тратить интерактивную квоту» как «враждебный биллинговым намерениям вендора и, вероятно, противоречащий условиям».[10]

3.1 Рекомендованный стек: A + D + B, именно в этом порядке

  1. A (tmux + Agent Teams) остаётся движком. Апрельская волна 2026 эту ставку усилила.[11]
  2. D (Routines) — недостающий ночной кусок. Нативно подписочные, автономные, с cron/GitHub-триггерами. Использовать, чтобы ночью запускать или будить флот и гонять watchdog/отчётные задачи — вместо того чтобы держать живым оркестратора, привязанного к ноутбуку. Статус research preview → обернуть тонким скиллом, чтобы оставался заменяемым.

Ответ на страх владельца — одним предложением Риск «поставить проект не на ту лошадь» лежит на сторонних обвязках, а не на официальном CLI в любом из режимов, — поэтому экспозиция gosleep — это бюджетная ручка, которую Anthropic может подкрутить, а не рубильник; с бюджетной ручкой работают темпом, телеметрией и деградацией в «ждать окна» — всё это есть в §6.
Секция 4

Проблема, которую никто не решает по умолчанию: кто следит за оркестратором?

Оркестратор gosleep следит за воркерами хорошо — таймеры терпения, ранжирование сигналов живости, nudge-и, дерево эскалации перед kill. Но стек надзора у нас глубиной ровно в один уровень. Над оркестратором — никого. Три реальных проекта упёрлись в эту же стену; их шрамы — лучший проектный вход, какой у нас есть.[12]–[14]

4.2 Кейс 1 — Overstory: четыре яруса watchdog-ов, а дыра всё равно выжила

Overstory (jayminwest, заархивирован 2026-05-28) — мультиагентная оркестрация, по форме очень близкая к gosleep: координатор-LLM + воркеры в git worktree + tmux. Его иерархия надзора — самая развитая из всех обследованных проектов:[14]

  • Ярус 0 — механический демон. Обычный не-ИИ процесс, тикающий по всем активным сессиям с прогрессивной эскалацией: уровень 0 — предупредить → уровень 1 — nudge через tmux/почту → уровень 2 — вызвать ИИ-триаж → уровень 3 — убить сессию. Уровень растёт со временем застоя; восстановление его сбрасывает; maxTriagePerTick ограничивает расход ИИ за тик.
  • Ярус 1 — ИИ-триаж. При эскалации одноразовый claude -p (таймаут 30 секунд) читает последние 50 строк лога застрявшего агента и классифицирует: retry | terminate | extend. Отказоустойчив в безопасную сторону: Claude недоступен или логов нет → extend («не убивай то, что не можешь диагностировать»).
  • Ярус 2 — агент-монитор. Персистентный Claude-агент, который «непрерывно патрулирует флот агентов» — ИИ, наблюдающий за ИИ.
  • Ярус 3 — пер-проектный супервизор: DEPRECATED. Автор попробовал четвёртый уровень надзора и списал его. Иерархии надзора выше одного наблюдателя себя не окупили.

Другая механика, которую стоит забрать: принцип ZFC («Zero Failure Crash») — источник истины всегда наблюдаемое состояние, никогда записанное, с явным приоритетом сигналов (живость tmux > живость pid > файл сессий) и правилами конфликтов («tmux жив + записано „зомби" → расследовать, не убивать автоматически»); похоронка worker_died — родитель никогда не блокируется вечно в ожидании мёртвого ребёнка; decision_gate — агент, явно вставший на человеческий вопрос, не застой, watchdog его пропускает; и state-машина только вперёд (completed — липкое состояние: поздний тик watchdog-а не может переклассифицировать чистый выход в зомби).

И всё же: вершина цепочки осталась без охраны Координатор — аналог нашего оркестратора — был исключён из детекции застоя (долгий простой для него норма), поэтому заклинивший-но-живой координатор был невидим для всех четырёх ярусов. И мёртвого координатора никто не перезапускал автоматически — оператор вручную запускал ov coordinator start. Даже у самого watchdog-демона не было супервизора — только защита от коллизий. Четыре яруса машинерии — и ровно та дыра наверху, что у gosleep, выжила.[14]

4.3 Кейс 2 — Warren: растворить проблему вместо того, чтобы решать её

Warren (тот же автор, 2026, очень активен) — это ответ на вскрытие Overstory. Центральный ход: персистентного LLM-оркестратора нет вообще. Координация — обычный код: tick-циклы над долговечным состоянием в базе. Код не галлюцинирует, не исчерпывает контекст и перезапускается идемпотентно; LLM живёт только внутри ограниченных, одноразовых запусков. Вопрос «кто следит за оркестратором» перестаёт существовать, когда оркестратор — это cron-тик на 30 секунд.[13]

Вокруг этого ядра Warren наслаивает четыре независимых механизма надзора — каждый ловит свой класс отказов:

  • Процесс-супервизор (entrypoint контейнера): перезапускает песочницу in-process с экспоненциальным бэкоффом (база 1 с → потолок 16 с) под бюджетом 5 рестартов за 60 с; бюджет исчерпан → выйти с ненулевым кодом, чтобы внешний слой (restart policy docker/fly) перезапустил весь контейнер. Само ядро warren никогда не перезапускается in-process: «никогда не маскируй баг warren внутрипроцессным циклом рестартов» — детекция краш-лупа принадлежит слою выше. Бонусная паранойя: компонент, вышедший с кодом 0 без сигнала завершения, считается отказом — чистый-но-неожиданный выход так же подозрителен, как краш.
  • Heartbeat-watchdog запусков: тик каждые 30 с сканирует работающие задачи; heartbeat = таймстемп новейшей строки событий (никогда не самоотчёт); старше нарочито щедрого бюджета в 45 минут → отменить и провести через «reap», чтобы частично закоммиченная работа всё равно ушла веткой. Детали: включён по умолчанию («страховочная сетка не должна зависеть от того, вспомнил ли оператор про env-переменную»); single-flight-тики; изоляция ошибок по каждому запуску; долгоживущие разговоры исключены (простой ≠ зависание); битый конфиг падает на старте — опечатка ломается громко, а не молча развооружает сетку. Мотивирующий инцидент (2026-06-05): застрявший bash-инструмент навечно припарковал линтер на ~57 CPU-минутах — и никто его не пожал.
  • Замкнутый «хилер»: продакшн-алерты → фингерпринт → диспетчеризация агента-хилера под пер-фингерпринтовыми max-retries + cooldown — шторм алертов не превращается в шторм агентов.
  • Свита детекторов: таймаут пауз, простой разговоров, тик плановых запусков — все одной формы: периодический тик над долговечным состоянием, single-flight, изолированные ошибки, включены по умолчанию.

Объединяющий принцип: каждое решение о живости принимается из долговечного состояния (таймстемпы событий в базе), никогда из убеждений в памяти, — поэтому каждый детектор бесплатно переживает рестарт, и та же логика работает на пути восстановления. Ещё одно правило warren, важное для бюджетов: битые значения бюджета «отказывают открыто» (fail OPEN) — «опечатка в бюджете не должна молча отменять каждый запуск по $0».

4.4 Кейс 3 — Gas Town: цепочка подотчётности с продакшн-шрамами

Gas Town (Steve Yegge, активен весь 2026) гоняет 20–30 агентов на интерактивном CLI и держит персистентного LLM-координатора («Мэра») — то есть выбрал архитектуру gosleep в масштабе 10×, и потому был обязан по-настоящему ответить на наш вопрос. Его ответ — цепочка watchdog-ов: Witness следит за воркерами; Deacon (демон-патруль) следит за здоровьем системы; а Boot the Dog проверяет самого Deacon каждые 5 минут — сторож для сторожа, добавленный после того, как Deacon сам умирал на практике.[12]

Детали реализации — каталог «отказов первой ночи», исправленных за нас заранее:

  • Boot — свежий LLM-триаж-тик, а не демон: запускается заново каждый тик и выбирает одно из ровно четырёх действий — start / wake / nudge / nothing, — сохраняемых в статус-файл; flock + файл-маркер обеспечивают single-flight (никаких перекрывающихся триажей).
  • Детекция зависания — счётчик + cooldown, никогда не одним выстрелом: таймаут пинга 30 с → force-kill только после 3 последовательных провалов → затем 5-минутный cooldown между force-kill-ами. Старение heartbeat-а ярусное: 5 мин = stale, 20 мин = very-stale → расшевелить.
  • Стартовый льготный период (startup grace): появился потому, что проверка heartbeat-а убивала только что запущенные сессии до того, как они успевали записать первый heartbeat (issue #567). Каждому watchdog-у нужно исключение на прогрев.
  • Дебаунс зомби: «tmux-сессия есть, а процесс агента не обнаружен» должно держаться ≥3 последовательных патрульных цикла до зомби-рестарта — переходные провалы при handoff-ах выглядят в точности как смерть.
  • RestartTracker с экспоненциальным бэкоффом — анти-краш-луп для компонентов под демоном (независимо то же открытие, что и restart budget warren).
  • Детекция массовой смерти: много смертей разом — системный отказ, а не N одиночных; реакция другая.
  • Три хранилища heartbeat-ов (файл, состояние сессии, метка в леджере) с жёстким правилом: никогда не объявлять агента застрявшим по одному хранилищу — сперва сверить активность tmux; живая сессия с протухшим хранилищем — это «расхождение записи heartbeat, а не застрявший агент».
  • Watchdog следит за собой: спавны Boot ограничены собственным cooldown-ом; проверки по ригам идут в ограниченном пуле воркеров с таймаутами, «чтобы один медленный риг не блокировал остальные».

4.7 Примечание на полях: кэш-экономика «проверок, как там дела»

Почему каденс пульса — вопрос денег, а не только дисциплины TTL промпт-кэша Anthropic молча упал с 1 часа до 5 минут 2026-03-06 — циклы, настроенные под старый TTL, получили +30–60% эффективной стоимости. Выведенное сообществом правило: опрашивать внутри кэш-окна (<5 мин) или спать долго (20–30 мин+) и съесть ровно один кэш-промах — худший каденс это «чуть за TTL». Для self-pulse оркестратора gosleep: тики <5 минут — только пока активно расклиниваешь застой; 20–30 минут — пока воркеры молотят. Механический watchdog (§5) стоит ноль токенов при любом каденсе — ровно поэтому каждые несколько минут должен бегать механический слой, а не LLM.[16]
Секция 5

Дизайн надзора для gosleep

Прямая пересадка семантики supervisor + watchdog из Warren на наш tmux-мир, закалённая дебаунс-шрамами Gas Town. Пять компонентов, ноль токенов в управляющем контуре, и человек — только в самом конце цепочки эскалации.[12]–[14]

5.1 Принципы дизайна

  • Живость судится по долговечным артефактам — возраст heartbeat-файла, mtime леджера, живость панели tmux, движение git — никогда по скрейпингу содержимого панели или убеждению оркестратора в собственной памяти (правило Warren; ZFC Overstory).
  • Watchdog механический. Никакого ИИ в исполняющем контуре — дуга Overstory→Warren показала, что непрерывный ИИ-надзор не окупается. ИИ появляется максимум как совещательный триаж, и он может только рекомендовать.
  • Восстановление = переподключиться + сверить, никогда не слепой респавн. Свежий оркестратор сеется из он-диск-леджера (STATE + новейший датированный handoff) и переподключается к живым воркерам — паттерн recover/re-wake из Warren, который наш скилл уже кодирует как cold-start-протокол.
  • Каждый рестарт живёт под бюджетом, который кончается человеком. «Никогда не маскируй баг оркестратора циклом рестартов».
  • Каждое решение — с дебаунсом, cooldown-ом и льготным периодом — одношаговый скрипт «протухло → убить» отстреляется по ложным срабатываниям в первую же ночь (Gas Town, эмпирически).

5.5 Весь watchdog как псевдокод

# запускается launchd каждые ~3 мин; flock гарантирует single-flight
[ -f /tmp/gosleep-watchdog.lock ] && exit 0            # single-flight
now=$(date +%s); hb=docs/handoff/.orchestrator-heartbeat

grace_active   && exit 0        # 10 мин после любого респавна: руки прочь (Gas Town #567)
budget_spent   && notify_owner "watchdog: restart budget исчерпан" && exit 0

if ! tmux has-session -t "$ORCH_SESSION"; then          # D1 — смерть
    respawn_orchestrator_cold_start                     # явное имя сессии; семя — леджер
    bump_budget; exit 0
fi

age=$(( now - $(stat -f %m "$hb") ))
ctx=$(tail -1 "$hb" | parse_context_pct)

if (( ctx >= CTX_CEILING )); then                       # D3 — исчерпание контекста
    tmux send-keys -t "$ORCH_PANE" "запиши датированный handoff сейчас" Enter
    mark_pending_rewake; exit 0
fi

if (( age > STALE_SECS )) && open_workers_gt_zero; then # D2 / D4 — зависание или затишье
    cross_check_pane_and_git || exit 0                  # никогда не верить одному хранилищу
    if first_stale_tick; then
        tmux send-keys -t "$ORCH_PANE" "PULSE?" Enter   # один nudge
    elif cooldown_elapsed; then                         # дебаунс ×2 + 15-мин cooldown
        tmux kill-pane -t "$ORCH_PANE_ID_EXACT"         # ТОЛЬКО явный id — никогда -a
        respawn_orchestrator_cold_start; bump_budget    # D5 прикрыт бюджетом выше
    fi
fi
# здоров → выйти молча. Молчащий watchdog — это успех.

Иллюстрация, не финальный код — пороги (STALE_SECS 30–45 мин, CTX_CEILING ~80%, бюджет 3/ночь) — стартовые значения, подкреплённые исследованием; битый конфиг должен отказаться взводиться при установке (fail loud), а промпт респавна обязан быть идемпотентным (сверка с леджером, никогда не двойная диспетчеризация).

5.6 Известные пределы

  • Сон macOS ставит на паузу всё — и watchdog, и флот. Гонять на машине, которая не засыпает, либо принять, что сон когерентно приостанавливает всю систему (launchd хотя бы навёрстывает при пробуждении).
  • Heartbeat может «врать умолчанием», если оркестратор клинит посреди пульса — смягчено тем, что запись heartbeat-а идёт первым действием пульса.
  • Пара оркестраторов (active/standby) рассматривалась и отвергнута: риск split-brain-двойной-диспетчеризации, второй LLM, за которым тоже надо нянчиться, и потолок ~3 тиммейт-панелей на этой машине делают её строго хуже механического watchdog-а. Ни один из обследованных авторов такого не выпустил; Overstory свой лишний ярус списал.[13],[14]
  • Эндгейм ночного режима (эксперимент на потом): инверсия в духе Warren — на время окна без присмотра персистентного оркестратора нет вовсе; тик launchd запускает короткоживущий ход оркестратора через claude -p (сверить леджер → собрать урожай → выдать следующую задачу → выйти). Растворяет D1–D5 по построению — ценой живой панели управления и перечитывания леджера каждый тик. Днём интерактивно, ночью tick-режим; сравнить пропускную способность и частоту отказов, прежде чем коммититься.

5.7 Порядок раскатки

  1. Фаза 1 (сейчас, ноль инфраструктуры): протокол heartbeat-файла + каденс self-pulse, вписанные в оркестрирующий скилл. Heartbeat полезен с первого дня, даже пока его никто не читает, — это «живой ли он?» владельца одним взглядом.
  2. Фаза 2 (собственно фикс): launchd-watchdog + restart budget + уведомление владельца. Единственное изменение, которое убирает «оркестратор умер в 3 ночи — флот простоял до утра».
  3. Фаза 3 (доводка): ИИ-триаж яруса 1 при аномалии (claude -p, ограниченный, безопасное умолчание extend).
  4. Фаза 4 (эксперименты): cloud Routine как ночной триггер запуска/отчёта; пилот tick-режимного ночного оркестратора.
