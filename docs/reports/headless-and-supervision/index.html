Executive verdicts

Three answers before the details

Everything below expands on these three cards. Claims are tagged FACT (primary/official source), FACT·MED (consistent secondary sources, primary not retrieved), COMMUNITY (single secondary source) — the tags come straight from the underlying research notes.

Does claude -p run on our subscription?
YES

It works today, by design, on a machine logged in with a Pro/Max subscription — it is the official CLI, not a third-party tool. Since ~2026-06-15 it bills against a separate monthly programmatic credit pool (reported $20 Pro / $100 Max 5x / $200 Max 20x at API list rates — secondary-source figures), not the generous interactive quota.[9]

Will Anthropic shut it down?
UNLIKELY

Every 2026 crackdown targeted third-party harnesses on subscription OAuth tokens — never the official CLI. In June 2026 Anthropic built a metering system for headless usage. You don't meter what you intend to kill. Residual risk: pool sizes and rates can be re-tuned at will.[8],[10]

Who watches the orchestrator today?
NOBODY

Our supervision is one layer deep: the orchestrator watches workers; nothing watches the orchestrator. If it dies or wedges at 3 am, the fleet idles until morning. Fix (§5): heartbeat file + mechanical launchd watchdog + restart budget + owner escalation — zero tokens, no AI in the loop.

TL;DR for the sleepy owner Keep the current tmux + Agent Teams engine (it rides the generous interactive quota Anthropic keeps protecting). Use claude -p only for bounded glue jobs, with per-run budget caps, and watch its credit burn. Never pipe our subscription login into any third-party tool — that is the one thing that actually gets accounts banned. And build the missing supervision layer: a dumb, token-free watchdog script that restarts a dead orchestrator from the on-disk ledger and pages you only when its restart budget runs out.
Section 1

What claude -p actually is — explained from zero

No prior knowledge assumed. This section defines every word as it appears; all mechanics come from Anthropic's official documentation (fetched 2026-07-07).[1]

1.1 Start one step earlier: what Claude Code is

Claude Code is Anthropic's official command-line program (a CLI). You type claude in a terminal, and an interactive chat opens right there: you describe a task in plain language, and the agent reads your files, edits code, runs commands and tests — asking your permission for anything sensitive. That interactive session is how gosleep's orchestrator and workers run today, inside tmux panes.

1.2 The flag: -p turns the same agent into a one-shot command

claude -p "do X" (long form --print) runs the exact same agent once, with no chat UI: it does the task, prints the answer to standard output, and exits. This is what "headless" means — the program runs without its interactive "head". That single flag turns Claude Code into a normal Unix building block you can pipe, script, put in a cron job, or call in a loop:

# behaves like any other shell command
cat build-error.txt | claude -p 'explain the root cause' > diagnosis.txt

# machine-readable result: answer + session id + cost of this run
claude -p 'summarize open PRs' --output-format json

Crucially, it is not a different product and not a raw API call: same model, same tools (Bash/Read/Edit/…), same project context (CLAUDE.md, skills, MCP servers), and — key for us — the same login as your interactive session.[1]

What stays the same as interactive Claude Code

  • The model and the agent engine itself
  • All tools: shell, file read/edit, web, MCP
  • Project context: CLAUDE.md, skills, MCP config (unless you pass --bare)
  • Authentication — the machine's existing subscription login
  • Skills work: /skill-name inside the prompt string

The two things that change

  • Nobody can answer permission prompts. You pre-approve tools (--allowedTools "Bash(git diff *),Read,Edit") or set a --permission-mode; anything not pre-approved either auto-denies or aborts the run. --dangerously-skip-permissions removes prompts entirely (with a few hard-coded circuit breakers such as rm -rf /).
  • Output becomes machine-readable. --output-format json returns the result plus session_id, total_cost_usd and token usage; stream-json gives a real-time event stream; --json-schema forces structured output.

1.3 Flags that matter for an orchestrator

1.4 The Agent SDK: same engine, library form — different rules

The Claude Agent SDK (TypeScript @anthropic-ai/claude-agent-sdk, Python claude-agent-sdk; renamed from "Claude Code SDK") is the same engine exposed as a programming library. The official docs literally describe claude -p as "using the Agent SDK via the CLI"; mechanically the SDK bundles and spawns the Claude Code binary and talks to it over stdio — it is not a separate implementation.[2] What it adds over shelling out to claude -p: in-process hooks (PreToolUse/PostToolUse/Stop…), in-process custom tools, a canUseTool permission callback (programmatic approval mid-run), native session objects, structured outputs, streaming bidirectional input.

The critical asymmetry: SDK ≠ subscription The SDK docs document only API-key / cloud-provider authentication. Anthropic's explicit line (verbatim): "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Please use the API key authentication methods described in this document instead."[2] The ban is aimed at products offering subscription auth to others; the docs are silent on private personal SDK use over one's own subscription token — undocumented, unendorsed, avoid. Rule of thumb: claude -p = subscription-legal; Agent SDK = API key.

1.5 How a headless run authenticates (and the gotcha that silently costs money)

Two words first. A subscription (Pro/Max) is the flat monthly plan you log into with OAuth via /login. An API key is pay-per-token developer billing — every token costs real dollars with no monthly ceiling. Headless runs pick credentials in this official precedence order (highest wins):[1]

  1. Cloud provider credentials (Bedrock / Vertex / Foundry)
  2. ANTHROPIC_AUTH_TOKEN environment variable
  3. ANTHROPIC_API_KEY — "in non-interactive mode the key is always used when present"
  4. apiKeyHelper script
  5. CLAUDE_CODE_OAUTH_TOKEN — from claude setup-token: an official, one-year, subscription-backed token for CI/scripts (inference-only scope; requires Pro/Max/Team/Enterprise). The official GitHub Action accepts it as a first-class input.[15]
  6. Subscription OAuth from /login — the default for Pro/Max users.
Gotcha: a stray API key silently hijacks your subscription Because rule 3 outranks rule 6, an exported ANTHROPIC_API_KEY anywhere in the environment makes every headless run bill the API — per token, real dollars — even though the machine is logged in with a subscription. Sanity check before any unattended run: unset ANTHROPIC_API_KEY. §6 recommends baking this check into install.sh/doctor.

Bottom line: on a logged-in Pro/Max machine, claude -p just works on the subscription, by design, today — and Anthropic even ships an official subscription token (setup-token) for headless environments.[1],[15]

1.6 Official autonomous surfaces adjacent to -p

Cloud Routines research preview

Scheduled agents on claude.ai infrastructure: a saved prompt + repos + MCP connectors, triggered by cron (≥1 h), API call, or GitHub events; run fully autonomously, no permission prompts. Require subscription login — a set ANTHROPIC_API_KEY actually breaks the feature. Consume subscription usage plus a separate daily routine cap.[3]

/loop + scheduled tasks

Local, session-scoped recurring runs inside Claude Code (die with the session; 7-day expiry). The first-party answer to the simple "re-run this prompt on a timer" case.[4]

Desktop scheduled tasks

Recurring tasks run on your machine via the Claude Desktop app — the consumer-grade sibling of Routines.[4]

1.7 Mini-glossary (terms used throughout this report)

Headless
Running without an interactive UI — no human at the keyboard; input in, output out, process exits.
OAuth / subscription login
Browser-based sign-in; a token lands in the OS keychain. This is what /login does for Pro/Max.
API key
Pay-per-token developer billing. Unlimited ceiling, unlimited bill.
Programmatic credit pool
Since ~2026-06-15: a monthly dollar allowance inside the subscription that headless/scripted usage draws from, metered at API list rates (see §2 caveat).
Orchestrator / worker
gosleep's split: one lead agent coordinates (spawns, monitors, chains); disposable worker agents execute one context-bounded chunk each.
Watchdog
A process whose only job is to check that another process is alive and healthy, and act when it isn't.
Heartbeat
A periodic, observable "I'm alive" signal — best practice: a timestamp written to disk, not an in-memory belief.
launchd
macOS's built-in service manager: runs scripts on an interval, survives reboots, handles wake-from-sleep better than cron.
Tick loop
A dumb scheduler pattern: wake every N seconds/minutes, scan durable state, act on deltas, exit. No memory between ticks.
Restart budget
"At most N restarts per window" — a crash-looping component escalates to a human instead of thrashing forever.
Zombie session
The container is alive but the brain is dead — e.g. a tmux pane exists but the Claude process inside it has exited.
Context window / compaction
The model's finite working memory. When it fills, the session summarizes ("compacts") itself — an orchestrator can lose the thread this way.

2.2 The verdict: where claude -p on subscription stands today (2026-07-08)

Legal & working

claude -p still works while logged in with Pro/Max — it is the official CLI, and the enforcement error message itself says credentials are "only authorized for use with Claude Code". Scripting the official CLI ≠ a third-party harness on your OAuth token. Since ~2026-06-15 it draws from the programmatic credit pool at API list rates; interactive terminal use keeps the classic 5-hour + weekly window model.

But budget-capped, not flat-rate

A Max 20x plan gives ≈$200/month of programmatic credit. A busy overnight claude -p fleet at API rates can burn that in days. "Headless on subscription" is now legal and supported but bounded — a budget, not a loophole. Bulk work belongs on the interactive quota (tmux + Agent Teams), which remains far more generous per dollar.

The June split is the strongest signal in the whole timeline: Anthropic's chosen resolution for headless subscription use was to meter it, not ban it. The realistic failure mode is therefore not "Anthropic bans claude -p" but "the quota/credit gets tighter" — which is a budgeting problem, not an existential one. The ralph maintainer independently reached the same read and additionally rejected the "drive the interactive TUI programmatically to spend interactive quota" workaround as "adversarial to the vendor's billing intent and plausibly against terms".[10]

Section 4

The problem nobody solves by default: who watches the orchestrator?

gosleep's orchestrator watches its workers well — patience clocks, liveness ranking, nudges, kill trees. But the supervision stack is exactly one layer deep. Above the orchestrator sits… nobody. Three real projects hit this same wall; their scars are the best design input we have.[12]–[14]

4.1 Our current model, honestly drawn

What exactly can go wrong at the top? The research names five failure classes:[13]

CodeFailure modeWhat it looks likeWhat happens today
D1DeathPane or process gone — crash, accidental kill, machine event.Fleet orphaned; workers finish and idle; nothing chains the next cycle until the owner wakes.
D2HangAlive but wedged: stuck tool call, permission prompt nobody answers, API-error loop.Invisible — the pane looks alive. Same orphaned fleet, harder to notice.
D3Context exhaustionAlive but compacted/degraded; forgets protocol mid-chain.Worst case: a degraded orchestrator makes wrong decisions instead of no decisions.
D4Silent quiesceEnded a turn without an armed wake-up — nothing will ever prompt it again.The owner's pulse rule (never end a turn without an armed wake-up) covers this by discipline only; a missed wake-up is silent.
D5Crash loopDies repeatedly on the same input; naive auto-restart would thrash forever.No restart machinery exists at all — so today this is "just" repeated D1.

4.2 Case study 1 — Overstory: four watchdog tiers, and the gap survived anyway

Overstory (jayminwest, archived 2026-05-28) was a multi-agent orchestration system very close in shape to gosleep: coordinator LLM + workers in git worktrees + tmux. Its supervision hierarchy was the most elaborate of any project surveyed:[14]

  • Tier 0 — mechanical daemon. A plain non-AI process ticking over every active session with progressive escalation: Level 0 warn → Level 1 tmux/mail nudge → Level 2 invoke AI triage → Level 3 kill the session. Escalation advances with elapsed stall time; recovery resets it; maxTriagePerTick caps AI spend per tick.
  • Tier 1 — AI triage. On escalation, a one-shot claude -p (30-second timeout) reads the last 50 lines of the stalled agent's log and classifies: retry | terminate | extend. Fails safe: if Claude is unavailable or there are no logs → extend ("don't kill what you can't diagnose").
  • Tier 2 — monitor agent. A persistent Claude agent that "continuously patrols the agent fleet" — an AI watching AIs.
  • Tier 3 — per-project supervisor: DEPRECATED. The author tried a fourth supervision level and retired it. Supervision hierarchies above one watcher didn't earn their keep.

Other mechanics worth stealing: the ZFC principle ("Zero Failure Crash") — observable state is the source of truth, never recorded state, with an explicit signal priority (tmux liveness > pid liveness > sessions file) and conflict rules ("tmux alive + recorded zombie → investigate, don't auto-kill"); a worker_died death-notification mail so a parent never blocks forever waiting for a dead child; decision_gate — an agent explicitly paused on a human question is not a stall, the watchdog skips it; and a forward-only state machine (completed is sticky, so a late watchdog tick can't reclassify a clean exit as a zombie).

And yet: the top of the chain stayed unguarded The coordinator — the orchestrator-equivalent — was exempt from stall detection (long idle is normal for it), so a wedged-but-alive coordinator was invisible to all four tiers. And nothing auto-restarted a dead coordinator — the operator had to run ov coordinator start by hand. Even the watchdog daemon itself had no supervisor, only collision detection. Four tiers of machinery, and the exact gap gosleep has survived at the top.[14]

4.3 Case study 2 — Warren: dissolve the problem instead of solving it

Warren (same author, 2026, very active) is the post-mortem answer to Overstory. Its central move: there is no persistent LLM orchestrator at all. Coordination is plain code — tick loops over durable database state. Code doesn't hallucinate, doesn't exhaust context, and restarts idempotently; the LLM only lives inside bounded, disposable runs. "Who watches the orchestrator" stops being a question when the orchestrator is a 30-second cron tick.[13]

Around that core, Warren layers four independent supervision mechanisms — each watching a different failure class:

  • Process supervisor (container entrypoint): restarts the sandbox substrate in-process with exponential backoff (1 s base → 16 s cap) under a 5-restarts-in-60-s budget; budget exhausted → exit non-zero so the outer layer (docker/fly restart policy) recycles the whole container. The warren core itself is never restarted in-process: "never mask a warren bug with an in-process restart loop" — crash-loop detection belongs to the layer above. Bonus paranoia: a component exiting 0 without a shutdown signal is treated as a failure — clean-but-unexpected exit is as suspicious as a crash.
  • Run heartbeat watchdog: a 30-s tick scans running jobs; heartbeat = timestamp of the newest event row (never self-report); older than a deliberately generous 45-minute budget → cancel, and route through "reap" so partial committed work is still pushed as a branch. Design details: on by default ("a safety net must not depend on an operator remembering an env var"); single-flight ticks; per-run error isolation; long-lived conversations exempted (idle ≠ hung); invalid config throws at boot — a typo fails loud, never silently mis-arms the net. Motivating incident (2026-06-05): a stuck bash tool pinned a linter at ~57 CPU-minutes forever, and nothing reaped it.
  • Closed-loop healer: production alerts → fingerprint → dispatch a healer agent, guarded by per-fingerprint max-retries + cooldown — so an alert storm can't become an agent storm.
  • Detector suite: pause-timeout, idle-conversation, plan-run tick — all the same shape: periodic tick over durable state, single-flight, isolated errors, on by default.

The unifying principle: every liveness decision is made from durable state (event timestamps in the DB), never from in-memory beliefs — so every detector survives a restart for free, and the same logic works on the recovery path. One more warren rule that matters for budgets: malformed budget values fail OPEN — "a budget typo must never silently cancel every run at $0".

4.4 Case study 3 — Gas Town: the chain of accountability, with production scars

Gas Town (Steve Yegge, active through 2026) runs 20–30 interactive-CLI agents and keeps a persistent LLM coordinator (the "Mayor") — i.e. it chose gosleep's architecture at 10× scale, and therefore had to actually answer our question. Its answer is a watchdog chain: the Witness watches workers; the Deacon (daemon patrol) watches system health; and Boot the Dog checks the Deacon every 5 minutes — a watchdog for the watchdog, added because the Deacon itself died in practice.[12]

The implementation details are a catalogue of first-night failures pre-fixed for us:

  • Boot is a fresh LLM triage tick, not a daemon: it runs anew each tick and decides one of exactly four actions — start / wake / nudge / nothing — persisted to a status file; a flock + marker file makes it single-flight (no overlapping triage runs).
  • Stuck detection is counter + cooldown, never one-shot: ping timeout 30 s → force-kill only after 3 consecutive failures → then a 5-minute cooldown between force-kills. Heartbeat aging is tiered: 5 min = stale, 20 min = very-stale → poke.
  • Startup grace period: exists because the heartbeat check used to kill freshly-started sessions before they wrote their first heartbeat (issue #567). Every watchdog needs a warm-up exemption.
  • Zombie debounce: "tmux session exists but agent process not detected" must hold for ≥3 consecutive patrol cycles before a zombie restart — transient gaps during handoffs look exactly like death.
  • RestartTracker with exponential backoff — anti-crash-loop for daemon-managed components (independently the same finding as warren's restart budget).
  • Mass-death detection: many deaths at once is a systemic failure, not N individual ones — different response.
  • Three heartbeat stores (file, session state, ledger label) with the hard rule: never declare an agent stuck from a single store — cross-check tmux activity first; a live session with a stale store is "heartbeat-write divergence, not a stuck agent".
  • The watchdog watches itself: Boot spawns are rate-limited by their own cooldown; per-rig checks run in a bounded worker pool with timeouts "so one slow rig cannot block all others".

Human gates need timeoutsWarren (pause budget, 30 min default)Every "ask the owner" pause carries a wall-clock budget; on expiry the flow proceeds with a recorded warning — the sleeping owner never wedges the fleet.
Generous thresholds beat jumpy onesWarren (45-min heartbeat budget)Thresholds at the 30–45-min scale, not 5 — false-positive kills of healthy orchestrators cost more than slow detection.
Watchdog on by defaultWarrenThe safety net must not depend on anyone remembering to arm it.
AI patrol doesn't payOverstory → Warren arcOverstory built continuous AI supervision (Tier 2); Warren dropped AI from the loop entirely. AI may only recommend on anomaly; the mechanical layer enforces.
Kill only by explicit idgosleep itself (2026-07-07)A tmux kill-pane -a once killed a live fleet. The watchdog kills only the exact session/pane id it verified, never "everything else".

4.7 Side-note: the cache economics of checking on things

Why pulse cadence is a money question, not just a discipline question Anthropic's prompt-cache TTL silently dropped from 1 hour to 5 minutes on 2026-03-06 — loops tuned for the old TTL saw +30–60% effective cost. The emergent community rule: poll inside the cache window (<5 min) or commit to long sleeps (20–30 min+) and eat exactly one cache miss — the worst cadence is just past the TTL. For gosleep's orchestrator self-pulse: <5-min ticks only while actively wedging a stall; 20–30-min ticks while workers grind. The mechanical watchdog (§5) costs zero tokens at any cadence — which is precisely why the mechanical layer, not the LLM, should be the thing that runs every few minutes.[16]
Section 5

The supervision design for gosleep

A direct transplant of Warren's supervisor + watchdog semantics onto our tmux world, hardened with Gas Town's debouncing scars. Five components, zero tokens in the control loop, and a human only at the very end of the escalation chain.[12]–[14]

5.1 Design principles

  • Liveness is judged from durable artifacts — heartbeat-file age, ledger mtime, tmux pane liveness, git motion — never from pane-content scraping or the orchestrator's in-memory belief (Warren's rule; Overstory's ZFC).
  • The watchdog is mechanical. No AI in the enforcement loop — the Overstory→Warren arc showed continuous AI supervision doesn't pay. AI appears at most as an advisory triage step, and it can only recommend.
  • Recovery = re-attach + reconcile, never blind respawn. A fresh orchestrator is seeded from the on-disk ledger (STATE + newest dated handoff) and re-attaches to live workers — Warren's recover/re-wake pattern, which our skill already encodes as the cold-start protocol.
  • Every restart sits under a budget that ends at a human. "Never mask an orchestrator bug with a restart loop."
  • Every decision is debounced, cooled down, and grace-perioded — a one-shot "stale → kill" script will fire on false positives its first night (Gas Town, empirically).

5.5 The whole watchdog, as pseudocode

# fired by launchd every ~3 min; flock guarantees single-flight
[ -f /tmp/gosleep-watchdog.lock ] && exit 0            # single-flight
now=$(date +%s); hb=docs/handoff/.orchestrator-heartbeat

grace_active   && exit 0        # 10 min after any respawn: hands off (Gas Town #567)
budget_spent   && notify_owner "watchdog: restart budget exhausted" && exit 0

if ! tmux has-session -t "$ORCH_SESSION"; then          # D1 — death
    respawn_orchestrator_cold_start                     # explicit session name; seeded from ledger
    bump_budget; exit 0
fi

age=$(( now - $(stat -f %m "$hb") ))
ctx=$(tail -1 "$hb" | parse_context_pct)

if (( ctx >= CTX_CEILING )); then                       # D3 — context exhaustion
    tmux send-keys -t "$ORCH_PANE" "write the dated handoff now" Enter
    mark_pending_rewake; exit 0
fi

if (( age > STALE_SECS )) && open_workers_gt_zero; then # D2 / D4 — hang or quiesce
    cross_check_pane_and_git || exit 0                  # never trust a single store
    if first_stale_tick; then
        tmux send-keys -t "$ORCH_PANE" "PULSE?" Enter   # one nudge
    elif cooldown_elapsed; then                         # debounce ×2 + 15-min kill cooldown
        tmux kill-pane -t "$ORCH_PANE_ID_EXACT"         # explicit id ONLY — never -a
        respawn_orchestrator_cold_start; bump_budget    # D5 guarded by the budget above
    fi
fi
# healthy → exit silently. A quiet watchdog is the success case.

Illustrative, not final code — thresholds (STALE_SECS 30–45 min, CTX_CEILING ~80%, budget 3/night) are the research-backed starting points; invalid config must refuse to arm at install time (fail loud), and the respawn prompt must be idempotent (reconcile from ledger, never double-dispatch).

5.6 Known limits

  • macOS sleep pauses everything — watchdog and fleet alike. Run on a box that stays awake, or accept that sleep pauses the whole system coherently (launchd at least catches up on wake).
  • A heartbeat can lie by omission if the orchestrator wedges mid-pulse — mitigated by making the heartbeat write the first act of the pulse.
  • Paired orchestrators (active/standby) were considered and rejected: split-brain double-dispatch risk, a second LLM to babysit, and this machine's ~3-pane teammate cap make it strictly worse than the mechanical watchdog. Neither surveyed author ever shipped it; Overstory deprecated its extra tier.[13],[14]
  • The night-mode endgame (worth a later experiment): Warren-style inversion — no persistent orchestrator at all during the unattended window; a launchd tick runs a short-lived claude -p orchestrator turn (reconcile ledger → harvest → dispatch → exit). Dissolves D1–D5 by construction, at the cost of the live steering pane and per-tick ledger re-reads. Interactive by day, tick-mode by night; compare throughput and failure rates before committing.

5.7 Rollout order

  1. Phase 1 (now, zero infra): heartbeat-file protocol + self-pulse cadence written into the orchestrating skill. The heartbeat is useful from day one even before anything reads it — it's the owner's "is it alive?" glance.
  2. Phase 2 (the actual fix): launchd watchdog + restart budget + owner notification. This is the single change that removes "orchestrator died at 3 am, fleet idled until morning".
  3. Phase 3 (refinement): Tier-1 AI triage on anomaly (claude -p, bounded, fail-safe extend).
  4. Phase 4 (experiments): a cloud Routine as the nightly kick-off/report trigger; the tick-mode night orchestrator pilot.
Section 6

Final recommendations, ranked

Ordered by (value for the sleeping owner ÷ effort). Items 1–4 are the minimum viable "owner goes to sleep" package.

  1. Keep tmux + Agent Teams as the engine; stay subscription-first on official surfaces effort: nonerisk: low

    It rides the most generous quota, satisfies the supervision requirement, and sits on the one surface Anthropic has consistently protected while cutting everything else off (§2, §3). Do not migrate to SDK/API or any third-party harness.

  2. Build the mechanical watchdog: heartbeat file + launchd script + restart budget + owner escalation effort: medvalue: highest

    The §5 design verbatim. Zero tokens, no AI in the loop, kills only by explicit id, all decisions debounced + cooled down + grace-perioded. This closes D1–D5 — the entire "who watches the orchestrator" question.

  3. Mechanize the self-pulse with cache-aware pacing effort: low

    Never end a turn with a live fleet and no armed wake-up; write the heartbeat as the first act of every pulse; cadence <5 min only while actively wedging a stall, 20–30 min while workers grind (the 5-minute cache TTL rule, §4.7). Put it in the skill text, not just in memory.

  4. Use claude -p for bounded glue only — with telemetry on every call effort: low

    Nightly reports, CI checks, watchdog triage: --output-format json + --max-budget-usd + strict --allowedTools; log total_cost_usd + session id into the ledger; alert at N% of the monthly programmatic pool. Pin the CLI version against the coming --bare default (bare mode kills subscription OAuth). Re-verify the pool's $ figures against the primary Help-Center source before building billing logic (§2 caveat).

  5. Encode policy guardrails so future agents can't wander into banned territory effort: low

    A written rules file: subscription OAuth never leaves official surfaces (Agent SDK included); no third-party harnesses, ever; unset ANTHROPIC_API_KEY sanity check in install.sh/doctor so a stray key can't silently hijack billing; API-key escape hatch exists but stays OFF by default.

  6. Port ralph's unattended-loop hardening into the orchestrating skill effort: med

    Dual-condition exit gate (heuristics + explicit EXIT_SIGNAL), circuit breaker (no-progress / same-error / permission-denial thresholds with cooldown + probe), quota auto-wait (degrade to wait-for-window instead of dying), question-detection with corrective re-prompt, control-file protection.[10],[17]

  7. Adopt the fleet-reliability patterns from Gas Town / Warren effort: med

    Zombie-session detection (tmux alive ≠ Claude alive) in the pulse check; harvest-through-reap on any kill (collect committed work + write a worker_died ledger entry); forward-only worker state machine (completed is sticky); failure memory — every watchdog intervention appends a structured record for retros and threshold tuning.

  8. Night mode + morning digest + question buffering effort: med

    A declared unattended window: reversible low-stakes questions take the default and get logged; material ones pause that task under a warren-style timeout budget; denylist items block as today. At window end: MORNING-DIGEST-<date>.md — work landed, verdicts, parked items, deduped questions, budget spent. The owner wakes to a narrative, not 40 unlabeled branches.

  9. Prototype one cloud Routine as the overnight trigger effort: low-medpreview

    Subscription-native, autonomous, cron/GitHub-triggered: "wake the fleet / run the queue / file a report" — instead of keeping a laptop-bound orchestrator warm all night. Wrap in a thin skill; it's a research preview and may shift. Evaluate /loop + scheduled tasks as the local fallback.[3]

  10. Explicitly do NOT adopt standing policy

    Ruflo/claude-flow and every API-only or banned-on-subscription harness; TUI-driving hacks to spend interactive quota programmatically ("adversarial to the vendor's billing intent" — ralph ADR); paired-orchestrator standby schemes; continuous AI patrol agents. Each was evaluated and rejected on evidence, not taste (§3, §4, §5.6).
