Five- to seven-sentence brief

What the owner asked and what we found

2026-08-03 · research

On 24 July 2026 the owner asked for a web admin surface where he could look at reports, see autonomy indicators, questions and tasks in one place, and eventually steer the fleet from a phone. The project built a professional static dashboard of seven screens (docs/lab/site/*.html) but zero buttons that change anything in the system: the 425-line client only knows how to display. The decision to skip the interactive version wasn't made in conversation — the orchestrator auto-applied default d-2026-07-28-004 on 28 July after the owner missed the 25 July 08:00 UTC deadline on question q-2026-07-24-006.

The three references give three different answers. AutoSK runs on the subscription but ships a native Tauri shell rather than a browser UI. Warren is a living, modern template on our stack (React + TS + NDJSON) but requires an Anthropic API key, which we do not have — we run on the subscription. Overstory is Warren's spiritual predecessor, archived. The market as a whole converges on the pattern “local daemon + browser SPA + SSE” — exactly the class our problem belongs to.

Of three realistic options we recommend option A: a thin TypeScript server (~700 lines) on top of the current pipeline, with a single seed action — the “Publish skill” button. First working button: 3.5–5 days from zero; full first release: 10–14 days. The owner's hard rule — “an agent must not be able to publish” — is enforced by a TouchID gate inside the publisher: the biometric sensor is the one machine resource the agent, running under the same UID, cannot reach. The red team found three critical flaws in the first draft — each closed by a mechanism, not a caveat; and the residual risk on a Mac without a sensor is stated openly.

1. What is built today

The lab's web surface exists and works as an observation dashboard. It is professionally laid out, regenerates automatically, reads well on both a phone (via a Markdown projection) and a laptop (via file://). No client handler sends anything outbound; the source contains neither fetch(, nor WebSocket, nor EventSource.

Pages 7 index, timeline, tasks, questions, fleet, cost, library
Client TS 425 lines, 6 functions — all display-only
Action buttons 0 nothing on the page mutates the system
Server none grep across the tree: 0 matches for http.server, express, fastify

What it can do today

Render the 7 screens from render_bundle.json, re-age labels, countdowns for question deadlines, filters, search, theme toggle.

What it physically cannot do

file:// is not allowed to make a network request to a sibling file (CORS). A button would be decorative. The rule is written into docs/lab/site/README.md.

The CLI write path already exists

tools/lab/lab-emit.sh and lab-write.sh — atomic writes under a dir-lock. But there is no bridge from the web to those CLIs.

The panel read three key references line by line and surveyed a market of 20+ tools. Below is the condensed map.

Four market patterns (25+ tools)

  • Pattern A — IDE-extension WebView. Cline, Roo Code, Continue.dev, Zed, Cursor. Lives next to the editor but is IDE-bound.
  • Pattern B — local daemon + browser SPA. OpenHands, vibe-kanban, amux, agent-dashboard, Aider --browser, LangGraph Studio. Closest shape to ours.
  • Pattern C — desktop app / Electron. Goose, Sculptor, Conductor, Devin desktop. Heavy; requires distribution.
  • Pattern D — TUI multiplexer + optional web. Claude Squad, Crush, OpenCode. Observability boils down to “switch to the right pane”.

For live transport the market converges on SSE (AG-UI, amux) for one-way streams and WebSocket where both directions are needed (OpenHands, Devin). Warren's author deliberately moved off WebSocket to NDJSON-over-HTTP — an external signal not to start with WebSocket.

3. Three options for us

All three preserve the current stack and do not rewrite the static pages. They differ in the size of the new surface and in how many days it takes to reach the first working button.

Recommended

A. Thin TypeScript server on top of the pipeline

Node + Hono, ~700 lines of TS + 40 lines of Swift for TouchID + 30 lines of bash for the chronicler's top-level lock. The client gets two new inline modules next to the existing 425-line client. Static pages keep working without the server.

First button: 3.5–5 days Full first release: 10–14 days Reversible: launchctl bootout Risk: low, additive
More expensive

B. Bun + React SPA, Warren-style

Bun server + Vite + React 18 + Tailwind v4 + shadcn/radix + TanStack Query + Recharts. ~1500 lines of server, ~4000+ lines of SPA. Duplicates all seven screens. A JSONL-to-SQLite projection adds a new source of drift.

First button: ~11–12 days Full first release: ~25–30 days Requires: a design lead Risk: medium, design drift
Not recommended

C. Full replacement with Next.js

Next.js 15 App Router, React 19, server actions. Discards the working SSG. Server actions blur the client/server boundary, making it easier to accidentally write into docs/lab/ outside the CLI. Directly contradicts the owner's “don't rewrite the stack”.

First button: ~12–17 days Full first release: ~30–45 days Reversibility: weak, git revert only Risk: high, cut-over

4. What the red team found and how it was closed

The first draft of option A had three critical flaws. Each is now closed by a mechanism, not by a caveat. Below is each finding and the mechanism that replaces it in the second draft.

  1. Local port not protected from local agents

    In the first draft the only protection was against other websites in the owner's browser. Nothing rejected a curl POST launched by a process under the owner's UID — exactly the “agent under the same UID” that the owner explicitly forbade.

    Closed by: three independent layers. A Bearer token on the web endpoint (a random curl without the token is rejected). An env secret GOSLEEP_WEB_TOKEN checked inside publish.sh (bypassing the web via a direct CLI call is rejected). A TouchID biometric gate inside publish.sh — the agent cannot physically pass the biometric sensor.

  2. “Synchronous chronicler after write” does not close the debounce race

    chronicler.py has no top-level exclusive lock. Two chronicler.sh processes can run concurrently; the winner is whoever closes os.replace last. Scenario: the server spawns publish then chronicler; a debounce chronicler that started earlier reads stale state and finishes after the server — the client sees 200 but the page never updates.

    Closed by: 30 lines of bash in tools/lab/chronicler.sh — a top-level mkdir-lock plus a --coalesce-since=<epoch> flag. If the bundle is already fresher than the passed epoch, the second caller exits without work. Guarantee: exactly one chronicler runs at any moment.

  3. Web-side actions are invisible in the timeline — hooks skip the interactive path

    Claude Code PostToolUse hooks fire only for the CLI client's own Bash/Edit tool calls. A child_process.spawn from the Node server is a plain execve; the client hook does not reach it. So every web-issued action bypasses both the timeline and the debounce chronicler.

    Closed by: a withTimeline(endpoint, params, fn) wrapper on every POST. Before spawning the CLI it writes server.intent; after — server.outcome (success or failure). Plus a touch .artifacts/lab/debounce/web-last-write as an extra signal to the debounce waiter. If the server dies between the CLI and the chronicler, the next tick.sh sees the orphan intent and writes server.outcome with status=orphan.

On residual risk, honestly. On a MacBook without TouchID (older Air, headless SSH session) the fallback reads a one-time six-digit code from /dev/tty. An agent in a non-interactive context has no owner-owned /dev/tty and is cut off, but a keyboard script under the same UID could inject the code symbolically. This is weaker than biometrics; without a Yubikey there is no absolute defense. TouchID is the best macOS gives without extra hardware. A residual risk of 1–2% of scenarios remains — we do not hide that.

6. What the owner decides

Decision required

Approve option A and launch the epic GSL-XXX

We won't move without an explicit decision here: any change of scope is exactly the class of question the manifest forbids to close by default (the lesson of 28 July 2026). Below are two independent questions. Answer yes or no to each.

  • Q1. Do we approve option A — the thin TypeScript server on the current pipeline, three defense layers for publication (Bearer + env secret + TouchID), first “Publish skill” button in 3.5–5 days from zero?
  • Q2. If yes, do we start now — as a separate epic on top of the already agreed skills-governance-plan.md (stages 2–3 as prerequisites, steps 4–10 of the migration path as the web part)? Or do we hold until another signal.

What we do not build under any “yes”

  • Electron / Tauri — no.
  • WebSocket — no (SSE is enough; Warren's author moved off WS).
  • PWA manifest, service worker, push, ntfy, tailscale — frozen by the owner's decisions; not designed without an explicit go-ahead.
  • A Warren-style build that requires an Anthropic API key — we run on the subscription.
  • Direct writes from the server into docs/lab/ — only via CLI.
  • Bulk operations (--all, “publish all skills”) — never.
  • git commit from the server — no.
  • Disabling the guard in install.sh — the guard stays on even after the web surface ships.
