## Находки

### Critical

#### 1. Локальный порт защищён только от браузеров чужих сайтов, но НЕ от локальных агентов (защита не выдерживает «главный запрет»)

**Направление:** безопасность.
**Что не так.** Архитектор описывает «пять слоёв защиты» (`architecture-options.md:207`, раздел A.6), из которых только два (`bind 127.0.0.1`, `Referer`/`Origin`) относятся к контролю источника запроса. Оба защищают ровно один вектор — POST'ы из вкладки чужого сайта в браузере владельца. Третий «слой» — «проверка владельца в CLI» — от локального агента структурно не защищает: агент запущен под UID владельца, значит `$USER == "romanlidovskyi"` для него истинно. Idempotency-Key и concurrency=1 — не про доступ, а про дедуп.
**Факт.** Ни в `architecture-options.md` (весь раздел A.6), ни в `docs/plans/skills-governance-plan.md:125-132` (все четыре слоя защиты инварианта) нет ни одного механизма, который отказывает запросу вида:
```
curl -X POST http://127.0.0.1:7331/api/skills/publish \
     -d '{"name":"using-jira"}'
```
запущенному из любого процесса под UID владельца. Ни Host-header check, ни bearer-token, ни interactive-gesture. Всё это есть только в варианте B (раздел B.6: «Bearer-token в заголовке») — в варианте A явно отсутствует.
**Почему опасно.** Ровно то, о чём сказал владелец: «не появляется ли путь, которым агент сможет опубликовать скилл в обход владельца — это главный запрет». Веб-сервер вариант A создаёт этот путь: любой процесс под UID владельца (в т.ч. подсаженный агент Claude Code) может отправить curl-запрос на loopback и заставить сервер выполнить `publish.sh` от имени владельца. Guard в `install.sh` тут не помогает (он про массовый rsync, а `publish.sh` — точечный). Проверка `$USER` в `publish.sh` тоже не помогает — она пройдёт.
**Что делать.** Обязательный шестой слой в варианте A: bearer-token (случайный, 32 байта, генерируется при install launchd-plist, читается ТОЛЬКО из файла с 0600 в `~/.config/gosleep/web.token`, кладётся в браузер через `http://127.0.0.1:7331/?tok=…` при первом заходе, хранится в `sessionStorage`, отправляется в заголовке `Authorization: Bearer …`). Дополнительно — проверка `Host` header (должен быть `127.0.0.1:7331` или `localhost:7331`; блокирует DNS-rebinding). Без обоих — веб-эндпойнт эквивалентен `sudo` без пароля для любого локального процесса.

#### 2. Гонка «синхронный `chronicler.sh --quiet` после действия» НЕ закрывает гонку с параллельным debounce-хроникёром

**Направление:** гонки и целостность данных.
**Что не так.** Архитектор утверждает (`architecture-options.md:74, 209, риск 7.6 в A.9`), что синхронный вызов `chronicler.sh --quiet` после write-action гарантирует свежий bundle к моменту ответа клиенту. Это неверно: `chronicler.py` (3 815 строк) **не имеет top-level exclusive lock** — grep по всему файлу показывает только один mkdir-lock в `apply_retention` (`chronicler.py:3181-3193`), и он берёт лишь `.queue.lock` в узком месте compact_queue. Два `chronicler.sh` могут бежать одновременно; порядок выигрыша определяется тем, кто позже закроет `os.replace` на `render_bundle.json`.
**Факт.** `tools/lab/chronicler.py:3664` (`def main`) не открывает ни одного собственного локa. `tools/lab/tick.sh` **имеет** свой мкдир-lock («ONE TICK AT A TIME», см. `tick.sh:32-33`), но `chronicler.sh --quiet` (`tools/lab/chronicler.sh:74`, `exec python3 chronicler.py "$@"`) вызывается напрямую и никак не сериализуется. Debounce-waiter (`chronicler-debounce.sh:96-108`, функция `rebuild`) вызывает `chronicler.sh --quiet` из фонового процесса; полный проход `chronicler.sh --dry-run` замеряется в **≈5,3 c** (`findings/our-constraints.md:80`) — окно гонки ощутимое.
**Почему опасно.** Сценарий: (a) владелец кликает «опубликовать» в t=0; (b) сервер спавнит `publish.sh` (t=0..0.3с) — оно пишет строку в `docs/skills/CHANGELOG.jsonl`; (c) сервер спавнит `chronicler.sh --quiet` (t=0.3с) — тот читает state и работает до t=5.6с; (d) параллельно за секунду до этого хроникёр-по-debounce'у **уже начал работать** от предыдущего PostToolUse-хука, читал state на t=-1, заканчивает свой `os.replace(render_bundle.json)` в t=6.0с — **после** сервера. Клиенту вернулось 200 в t=5.6с, он перезапрашивает страницу в t=5.7с — и получает старый bundle, где новой публикации ещё нет. UX разрыв: «сервер сказал OK, а на странице ничего не изменилось» → владелец нажимает второй раз.
**Что делать.** Ввести top-level mkdir-lock в `chronicler.sh` (или заставить веб-сервер идти через `tick.sh --force`, который уже сериализован). Второй вариант чище, но `tick.sh` делает больше работы (poll-fill, apply-due, watchdog observe) — ~2× медленнее хроникёра. Лучше — thin lock в chronicler.sh с политикой «второй пришедший ждёт первого до 15с, потом штампует свой запуск и стартует».

#### 3. Rebuild-хук хроникёра НЕ срабатывает на write-actions, инициированные веб-сервером

**Направление:** живой поток событий; hook-фильтрация мимо интерактива.
**Что не так.** Инвариант 7 общих рамок (`architecture-options.md:27`): «любое действие сервера, которое меняет данные, обязано синхронно вызвать `chronicler.sh --quiet` до возврата». Архитектор считает это «синхронный вызов покрывает всё» (риск 7.6 в A.9, стр. 209). Это верно только для write-actions, инициированных **веб-запросом**. Однако существует второй путь: `publish.sh` (или `lab-emit answer`) может фейлануть тихо/частично; часть операций (например, rsync-этап) может пройти, а `chronicler.sh` — нет; или сервер может завершить процесс между CLI и хроникёром. Классические Claude Code-хуки (`PostToolUse: Bash|Write|Edit`) на bash-спавн ИЗ ВЕБ-СЕРВЕРА **не срабатывают вообще** — это hook'и клиента Claude Code, не системные.
**Факт.** `.claude/settings.json:98-121` — все PostToolUse-матчеры (Bash, Write|Edit|MultiEdit, mcp__atlassian__*) — это hook'и клиента Claude Code, которые обрабатываются самим CLI-клиентом при вызове его собственных tool'ов. `child_process.spawn("bash", ["tools/skills/publish.sh"])` из Node.js-процесса — это системный `execve`, до которого хук клиента Claude Code не дотягивается. Никакой автоматической подстраховки «если сервер забудет вызвать chronicler — debounce всё равно подхватит через 90с» не будет.
**Почему опасно.** Debounce-waiter указывается архитектором как «безопасная сетка» (напрямую не проговорено, но подразумевается общим тоном). Он ей не является для веб-write'ов. Единственная страховка — `tick.sh` по расписанию (карриер desktop/launchd, каждые 5 мин), но это МИНУТЫ дрейфа, не секунды. Если сервер упал между CLI и хроникёром, bundle остаётся stale до ближайшего тика.
**Что делать.** Либо документировать: «единственная сеть безопасности для стелых после веб-write bundles — 5-минутный тик»; либо после каждого write-эндпойнта, помимо `chronicler.sh --quiet`, дополнительно `touch .artifacts/lab/debounce/last-write` и заводить waiter (эмулировать хук). Второе — обход дизайна, лучше явно ввести server-side sentinel «данные обновились, но rebuild не подтверждён» и рендерить это в UI (баннер), пока следующий пас не подтвердит.

**Факт.** См. `docs/plans/skills-governance-plan.md:104-134` (этапы 1-6, где этап 4 — «локальный сервер админки», является предпосылкой первой кнопки, а этапы 2 и 3 — предпосылки для этапа 4). Раздел A.8, шаг 1 архитектора: «Пишется `tools/skills/publish.sh` — 1 день». Это отдельный день, не входящий в «1-2 дня для кнопки».
**Почему опасно.** Владелец получит завышенное ожидание и назначит эпик под неверную вилку. Реальность (честная разбивка при чистой воде): этап 2 (реестр CHANGELOG, форма и валидация) — 0.5 дня; этап 3 (`publish.sh`) — 1 день; правка chronicler для новой страницы `skills.html` — 0.5-1 день; скелет сервера + launchd + whoami + Referer/Origin/Host + Bearer-token (см. находку 1) — 1-1.5 дня; POST /publish + client-actions.ts (probe+кнопка+toast) — 0.5 дня; тесты + smoke.sh guard — 0.5 дня. Итого **3.5-5 дней** от нуля до кнопки, из которых 2 дня — предпосылки (не сервер), 1.5-2.5 дня — веб. «1–2 дня» относится только к серверной части при условии, что этапы 2 и 3 уже позади.
**Что делать.** В отчёте пометить: «1–2 дня — это шаги 2 и 3 архитектурного варианта A ПОСЛЕ того, как в репо появились `publish.sh` и первая строка `CHANGELOG.jsonl`. От нуля — 3.5–5 дней». Разбить эпик соответствующим образом.

#### 5. Смена дня UTC ломает SSE-tail: файл `events/YYYY-MM-DD.jsonl` меняется по имени и inode; архитектор об этом не сказал

**Направление:** живой поток событий.
**Что не так.** Раздел A.4 архитектора: «серверный обработчик — это `tail -f` над `docs/lab/events/YYYY-MM-DD.jsonl` + фильтр от `since` + `.write("data: " + line + "\n\n")`. Полсотни строк». Ключевая деталь — daily rotation, документированная в `lab-log.sh:5` («daily rotation (UTC) keeps any consumer read cheap»). В 00:00 UTC хроникёр (точнее lab-log.sh) переключается на новый файл. tail держит FD на вчерашнем файле, там больше ничего не пишется, новые события молча теряются для клиента.
**Факт.** `tools/lab/lab-log.sh:239-258` (`def emit`): `day = utc_date()` и `path = os.path.join(EVDIR, "%s.jsonl" % day)` — путь вычисляется на каждый emit. Файлы за прошлые дни: `docs/lab/events/2026-07-12.jsonl` … `2026-08-03.jsonl` (проверил `ls -la`). Никакого симлинка `today.jsonl` нет.
**Почему опасно.** Владелец в 23:55 UTC открыл дашборд, кухня. В 00:00 UTC агент делает `question.posed`. В UI ничего не меняется — SSE-tail не видит нового файла. Владелец получает молчание вместо тоста. То же для `git checkout` в момент, когда файл событий текущего дня был переработан: inode нового файла отличается, tail продолжает читать «мертвую» позицию в отсутствующем файле (или получает EBADF, или молча висит).
**Что делать.** В `serve.ts` — таймер, который каждую минуту проверяет `utc_date()` и переоткрывает FD, если день сменился. Плюс `stat().st_ino` на текущем открытом файле — если inode изменился (git-операция, ротация, ручное `mv`) → переоткрыть. Клиенту также при переоткрытии — послать `event: rotate\ndata: {new_day: "…"}\n\n`, чтобы он мог заново подгрузить `render_bundle.json` (иначе seq'и обнулятся и «since» — врёт).

#### 6. Idempotency-Key через in-memory Map с TTL 5 мин НЕ переживает рестарт сервера — дубли возможны

**Направление:** действия через CLI, идемпотентность.
**Что не так.** Раздел A.2 архитектора: «Идемпотентность POST: заголовок `Idempotency-Key` + in-memory Map с TTL 5 мин. Прямая калька Warren'овского `idempotency.ts`». In-memory Map теряется при `launchctl reload` (обычная операция; сервер именно так и обновляется). Клиент шлёт повтор POST с тем же ключом — Map пуста, сервер не видит его как дубль, спавнит `publish.sh` ещё раз.
**Факт.** А.6 п.6 архитектора: «При плохой сети или двойном клике не создаётся дубликат публикации/ответа». Утверждение верно только внутри одного процесса сервера. `launchd`-под-контейнер выключается/включается на update.
**Почему опасно.** `publish.sh` (по плану) делает backup + rsync + строка в CHANGELOG. Двойное выполнение → две одинаковые строки в CHANGELOG.jsonl (не «дубль» с точки зрения rsync, потому что rsync идемпотентен, но нарушает append-history-контракт `docs/skills/CHANGELOG.jsonl` — «одна строка на правку»). Для answer'а на вопрос: как показано в разборе `lab-emit.sh` (`_patch` в строке 344, cmd_answer вызывает `_patch` без проверки статуса `open`), два одинаковых answer'а — два патча в queue.jsonl, второй перезаписывает первый в fold-логике. Не фатально, но грязно.
**Что делать.** Idempotency-Map должна быть персистентной (jsonl-файл в `.artifacts/web/idempotency.jsonl`, с fsync на запись; чтение при старте). Ещё лучше — просто отказаться от Idempotency-Key на стороне сервера и завести на клиенте: кнопка публикации становится disabled после клика на 3 секунды с явным индикатором.

#### 7. Owner-check в `publish.sh` через `$USER` — неверный уровень абстракции; веб-сервер и агент неотличимы

**Направление:** безопасность (продолжение находки 1, но независимая проблема).
**Что не так.** Раздел A.6 п.3: «`publish.sh` проверяет `$USER == "romanlidovskyi"` или соответствие UID; отказывается работать не от владельца. Второй слой, обязательный.» Веб-сервер запущен от того же UID, что и агент. Оба удовлетворяют `$USER == "romanlidovskyi"`. Значит: если проверка стоит, она пропускает и веб, и агент; если бы её усилить до «только TTY, не daemon» — веб-сервер сам daemon и не пройдёт (`SessionCreate=true` в launchd не даёт TTY). Проверка либо бесполезна, либо ломает веб.
**Факт.** `docs/plans/skills-governance-plan.md:126-127`: «проверка на владельца внутри `publish.sh` из этапа 3». Механизм проверки не расписан. Единственная семантика, которая различает «владелец сам» и «агент от имени владельца» на macOS без Yubikey — это либо интерактивный TTY (`isatty(0)`), либо secure enclave/Touch ID. Ни первое, ни второе для веба не даст «зелёный» (сервер не имеет TTY, TouchID не срабатывает при HTTP-запросе).
**Почему опасно.** Архитектор ссылается на этот CLI-check как «обязательный второй слой» — но слой не защищает от угрозы, которую называет (агент публикует). См. также находку 1: связка «Bearer token в веб-заголовке» + «CLI-check валидирует, что переменная `GOSLEEP_WEB_TOKEN` совпадает с secret'ом» — это уже настоящий двух-слойный барьер. Без такой связки CLI-check — театр.
**Что делать.** Слой в CLI должен проверять secret, установленный **веб-сервером в env перед `spawn`**, а не идентичность владельца ОС. Secret хранится в 0600-файле; веб-сервер читает его при старте; передаёт как env переменную в spawn публишера; CLI отказывает, если env отсутствует или не совпадает. Тогда: агент вручную `bash publish.sh` — падает (нет env); веб-сервер `spawn publish.sh` — работает. Отдельно — веб-сервер сам защищён Bearer-token'ом (см. находку 1). Два слоя, каждый нетривиальный, оба нужны.

#### 8. Refernrer/Origin check не защищает от no-referrer политики; браузер OWNER'а может быть блокирован

**Направление:** безопасность.
**Что не так.** А.6 п.2: «Принимаем только `Referer: http://127.0.0.1:7331/…` или `Origin: http://localhost:7331`». Современные браузеры при `Referrer-Policy: no-referrer` (или `strict-origin-when-cross-origin` для HTTPS→HTTP) шлют пустой Referer. Origin для same-origin POST'ов из формы **не всегда** отправляется (spec: Origin отправляется для CORS-запросов и cross-origin, для same-origin form POST — implementation-specific; Chrome шлёт, Safari до 13 — нет). Если сервер жёстко требует одного или другого — есть случаи, когда легитимный POST владельца отклоняется.
**Факт.** Стандарт: [Fetch spec, раздел 3.2.5](https://fetch.spec.whatwg.org/#origin-header) — Origin гарантированно есть только для не-CORS-safe методов cross-origin. Для same-origin POST — browser-dependent.
**Почему опасно.** Хуже: если сервер жёстко требует ХОТЯ БЫ одного из них — атакующая страница из cross-origin браузера пошлёт оба со своими значениями (`Origin: https://evil.example`, `Referer: https://evil.example/attack.html`), и сервер отклонит. НО: если атакующий скрипт использует `no-referrer` политику и работает через `fetch()` с `mode: 'no-cors'` + `credentials: 'omit'` — сервер увидит пустой Referer + `Origin: https://evil.example` (fetch всегда шлёт Origin). Заголовок Origin достаточен в fetch-based attack. В HTML-form-POST case Origin может отсутствовать. Значит нужна связка «Origin если есть — проверяем; иначе Referer; иначе — 403». Архитектор не прописал этой политики.
**Что делать.** Явное правило: **обязательный Origin или Referer**, любой должен быть равен `http://127.0.0.1:7331` (не `localhost` — hostname может резолвиться в IPv6, тогда Origin будет `http://[::1]:7331`, нужна вилка). Ещё: обязательный Bearer-token — покрывает случаи, где Origin/Referer невозможны. Дополнительно: `SameSite=Strict` куки, если используются.

#### 12. Идея «`fs.watch` уже правильно обрабатывает rename на macOS» — упрощение; FSEvents ловит rename, но задержка может быть >100 мс

**Что делать.** Явно в спеке эпика: НЕТ watch-based caching для `render_bundle.json`; политика чтения — только «open→read→close, инвалидация по st_ino ПЕРЕД чтением, если ino изменился — читаем заново». `fs.watch` вообще не используется в hot path'е bundle.

## Проверено и держится (это важно не меньше находок)

1. **`lab-write.sh` действительно атомарен.** Проверил `tools/lab/lab-write.sh:33-83`: `tempfile.mkstemp` в той же директории → `f.write` → `f.flush` → `os.fsync(f.fileno())` → `os.replace(tmp, target)`. При падении между `flush` и `replace` — временный файл выметается 60-секундным guard'ом при следующем write'е.
