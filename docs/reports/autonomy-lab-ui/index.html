Autonomy, the Question Buffer,
the Laboratory, UI & Mobile

A design dossier for turning GoSleep from a system where documentation is written by convention or on request into one where it is produced by itself — where a fleet of agents works overnight, buffers its own questions, and greets the owner in the morning with one place that shows everything.

Phase GSL-41 · writer-autonomy Reference: tasty-lunch 828 docs / 523 commits Source: 05-lab-ui-mobile-autonomy + 01-autosk Compiled 2026-07-08
00 · The thesis

One sentence, six moving parts

Every artifact a delivery system produces sits somewhere on a spectrum of how deterministically it can be generated. The reference project (tasty-lunch) proved the two ends of that spectrum with brutal clarity: the narrative layer, enforced by skill conventions, scaled to 197 files without a hiccup — and the one artifact that required regeneration, a hand-built wiki status hub, rotted within a month. The Laboratory is the machine that wires the whole spectrum together so nothing rots and nothing needs a human's hand at 3 a.m.

4

7
dashboard screens, regenerated from data — never hand-edited, therefore never rotting
min()
the autonomy runway = the nearest of six independent exhaustion clocks
▲ The core inversion

Today AskUserQuestion is the primary interface for a question — and at night it just blocks a pane until someone wakes up. The Laboratory inverts this: the durable question record becomes primary (it survives sessions, feeds the dashboard, the digest, and push), and a live prompt is raised only when the owner is actually present. Absent → queue, take the reversible default, keep working, surface it in the morning.

01 · The problem

Docs today: written by convention or on request. The goal: by itself.

GoSleep already has a strong base — every task leaves a paper trail by rule, not by favor. But nothing records events as they happen, questions to the owner have no home, and the dashboards that would tie it all together don't self-update. The lesson for what to build — and what never to build — comes from the reference project.

The tasty-lunch lesson: conventions scale, hand-built hubs rot

tasty-lunch is the same skills lineage as GoSleep: one solo owner + an AI orchestrator, 523 commits in ~a month, 828 docs on disk1. Reading its whole documentation tree sorts every artifact into a clean verdict — and the verdict is the design brief for the Laboratory.

✓ What scaled — by convention

197 dev_history files. 94+ handoffs, numbered 01→94, each with a machine-parseable telemetry footer. 19 lessons-learned, each citing a real incident and closing with a rule carried into the next cycle. The cycle prompts hard-code “invoke /handoff” — the “owner asks for a handoff” era is already over. Uniformity across 197 files is the evidence that convention-enforcement works at scale.

✗ What rotted — hand-built, then abandoned

The wiki status hub was hand-built once and never regenerated. It still reads “Phase 1 in progress, 1 of 9 epics done” — while delivery had reached Phase 23. No generator, no CI check, so it died within a month. Separately, 81% of the reports/ tree was never committed (a whole 155-file report set never landed) — scratch with no policy.

⚠ The one rule this dossier is built around

Anything that must be regenerated to stay true will rot unless a script regenerates it. 197 append-only narrative files survived because writing them is part of “done.” The single artifact needing regeneration died the moment a human stopped hand-editing it. → The Laboratory's dashboard must be script-regenerated from data, never hand-edited HTML.

The eight gaps the Laboratory must close

1 · No machine-readable layer

Everything is Markdown prose. LIVE-STATUS has a grammar but no schema. There is no events.jsonl, no status.json — a dashboard would have to regex a Markdown file.

2 · No timeline / event feed

Reconstructing “what happened tonight” = reading STATE + N handoffs + git log + Jira. Nothing records events as they happen in one timestamped place.

3 · No aggregated morning view

The At-a-glance section of STATE is the closest thing, but it's overwritten (no history), links to nothing, and mixes owner info with orchestrator self-instructions.

4 · Questions have no home #1 gap

A blocker becomes a synchronous AskUserQuestion (dies with the session) or a buried handoff paragraph. Nothing queues, types, or tracks questions across workers. At night AskUserQuestion just blocks a pane.

5 · Reports don't self-update

docs/report/ has generators but no trigger wiring them to delivery events. A landed task refreshes no dashboard.

6 · Artifacts aren't cross-indexed

Nothing links “GSL-38 → commit f12092e → dev_history → review finding → handoff 11 → Jira/GH.” Each dir has, at best, its own README.

7 · Worker telemetry is self-reported prose

Token counts arrive inside a SendMessage; nothing validates or aggregates beyond one running-total line.

8 · No push path at all

A parked question at 01:00 is discovered at 09:00 — only if the owner opens the terminal. (autosk has the same gap.2)

02 · The Laboratory

Three tiers of decreasing determinism

The tasty-lunch evidence sorts every artifact by how it must be produced. That sort is the architecture: a deterministic event floor that costs nothing, the existing convention-driven narrative in the middle, and a bounded synthesis job on top that regenerates everything derived. The wiki rotted because it had the middle tier without the floor or the roof.

TierProducerDeterminismCostWhat it generates
T1 · Events Claude Code hooks (.claude/settings.json, async:true) Mechanical — fires whether or not the model cooperates 0 tokens, ~0 latency The timeline: session/worker lifecycle, tool activity, commits, Jira transitions, failures
T2 · Narrative Agents by convention (existing skills) Behavioral — enforced by briefs + evals Already paid (part of delivery) Handoffs, dev_history, reviews, RCAs — the human story
T3 · Synthesis The chronicler — claude -p glue or cheap-tier Scripted trigger, model-assisted content Small, budgeted (--max-budget-usd) Dashboard regen, indexes, morning digest, cross-links, freshness checks

Tier 1 — the deterministic event layer

Adopt the envelope from the repo's own event-schema.md draft: {ts, run_id, seq, actor, type, data} plus session_id/agent_id from hook input. Its open caveat — “verify hook capabilities at build time” — is now resolved: the current hooks catalog covers every event type it proposed.3

Event typeConcrete hook (verified 2026-07-07)
agent.spawned / terminatedSubagentStart / SubagentStop (carry agent_type, agent_id); SessionStart/End for panes
agent.idleTeammateIdle — fires as a teammate goes idle (the pulse's blind spot, now free)
tool.call → vcs.commitPostToolUse matcher Bash(git commit *); matcher mcp__atlassian__.* → tracker.issue.*
handoff.writtenPostToolUse matcher Write|Edit with if on docs/handoff/*
failures / quotaStopFailure matchers rate_limit|overloaded|server_error — the quota-window detector, for free
questions / permissionsNotification, PermissionRequest, PermissionDenied
task boardTaskCreated / TaskCompleted
context healthPreCompact / PostCompact (compaction on the orchestrator = a red flag)
Why T1 matters most

Liveness derived from artifacts, not self-report. A wedged agent can't report it's wedged — but its event stream simply stops. The same stream that feeds the dashboard is a better pulse input than tmux capture-pane. Two producers complement the hooks: explicit lab-emit one-liners for semantic events hooks can't infer (cycle.started, question.posed, decision.made), and poll-fill — the chronicler reconciles gh pr list / Jira JQL / git log for anything the local hooks missed (a PR merged from the web).

On-disk layout — machine layer beside the human layer

docs/lab/                          # machine-first; committable except scratch
  events/2026-07-08.jsonl          # T1 + explicit events, append-only, daily
  status.json                      # snapshot: generated FROM events + STATE each pass
  questions/queue.jsonl            # §03 — open questions (append + status-patch)
  questions/archive.jsonl          # answered/expired, moved by the chronicler
  decisions/manifest.md            # §03 — owner-sovereign; the ONLY hand-edited file here
  decisions/log.jsonl              # every autonomous decision + every owner answer
  telemetry.jsonl                  # per-cycle token/cost lines (STATE grammar)
  digest/2026-07-08-morning.md     # T3-generated digest (one per active day)
  site/                            # T3-generated static HTML dashboard; never hand-edited
  scratch/                         # gitignored: the tasty-lunch 81%-uncommitted lesson

Rules inherited from existing discipline: atomic writes (same-dir temp + rename) for every non-append file; append-only JSONL never rewritten (corrections are new records with supersedes:<seq>); ORCHESTRATION-STATE.md stays authoritative — status.json is derived, and on conflict STATE + live git win.

Tier 3 — the “Laboratory” dashboard, and why it is static

Static HTML regenerated from docs/lab/ data — no server in v1. This matches the proven build-*.py pattern, works from file://, survives the machine being off, is committable (thus readable from GitHub on a phone), and cannot rot the way the wiki did — because no one edits it by hand. Regeneration triggers: (a) chronicler at every cycle boundary; (b) a debounced PostToolUse hook on writes to docs/lab/; (c) on-demand. Live steering is not this dashboard's job — that's Remote Control / the terminal (§05).

The chronicler is NOT a fourth live agent

It is a bounded, schedulable job — headless one-shot with strict --allowedTools + budget caps. Keeping it out of the teammate roster preserves the spawn-cap-3 budget and means a chronicler crash can never stall delivery: the data layer just goes stale until the next tick, and the dashboard shows its own staleness (generated-at stamp + max event age on every page). This is the anti-wiki-rot alarm built in.

The 7-screen information architecture

1 · Overview

The morning screen. Digest rendered + runway strip + questions summary. Default landing.

2 · Timeline

The event feed, newest-first, filterable by actor / type / severity; incident markers pinned.

3 · Tasks

Board keyed by Jira key: status, GH issue/PR links, commit SHAs, dev_history link per task.

4 · Questions

The §03 queue: open (by type), answered (who/when), auto-resolved (with the default used).

5 · Fleet

Per-agent cards: state, model, spawned/ended, tokens, last-event age.

6 · Cost

Telemetry series: per-cycle tokens, cumulative vs ceiling, per-model split, quota-window events.

7 · Library — the generated cross-index (kills gap #6)

Handoffs (numbered), dev_history (per task), reviews, reports, research, RCAs — each row with date, task keys touched, and links. This is the index that ties “GSL-38 → commit → dev_history → review → handoff → Jira/GH” together, generated, never hand-maintained.

03 · The question buffer

Buffer-and-continue: the autonomy pattern that lets the owner sleep

The community describes three maturity levels of night behavior4: (a) park on any question (autosk), (b) pause with a budget then auto-resolve, (c) buffer-and-continue — log the question, take the reversible default, keep working, surface everything in the morning. (c) is named as “the ideal for GoSleep; least implemented in public code.” tasty-lunch already field-tested a primitive version (OWNER-QUESTIONS.md / OWNER-DECISIONS). This is the full design.

Four types, four behaviors

TypeDefinitionNight behaviorPush?
BLOCKER Work can't proceed AND no safe default exists: credentials, denylist actions (force-push, prod deploy, destructive migration), irreversible forks Park the affected item only (not the fleet); reroute workers to unblocked work; queue the question Yes, immediately (unless quiet-hours says batch)
DECISION A genuine fork with viable branches, but a defensible default exists Record question + chosen default + auto_apply_at deadline: “if unanswered by T, I do X.” Keep working until T, then apply & log decision.made Yes, batched (digest), unless high-impact
CLARIFY Ambiguity with an obviously-reasonable reading Proceed with the default immediately; record as answered-by-default so the owner can veto retroactively No — digest only
FYI No answer needed: incidents recovered, budget thresholds crossed, policy rules tripped Record No — digest only (unless severity ≥ incident)

Queue format on disk — docs/lab/questions/queue.jsonl

{"id":"q-2026-07-08-003", "ts":"2026-07-08T01:12:40Z", "type":"DECISION",
 "from":"orchestrator", "task":"GSL-45", "links":{"jira":"GSL-45","gh":"#52","pr":"#56"},
 "question":"PR #56 conflicts in README after main moved; rebase or merge main in?",
 "options":[{"label":"rebase","pros":"linear history","cons":"rewrites commits"},
            {"label":"merge main in","pros":"no rewrite","cons":"merge bubble"}],
 "default":"merge main in", "default_rationale":"no-force-push standing rule; reversible",
 "reversibility":"high", "impact_if_wrong":"cosmetic history",
 "auto_apply_at":"2026-07-08T10:00:00Z", "status":"open"}

// resolution appends a patch record, never a rewrite:
{"re":"q-2026-07-08-003","status":"answered","answer":"merge main in","answered_by":"owner","channel":"telegram"}

Dedup rule (the “question spam” pitfall): before posing, grep open records for the same (task, question-hash); five workers hitting the same ambiguity = ONE morning item with a seen_by list.

The decision manifest — “decide it yourself, by the owner's manifest”

docs/lab/decisions/manifest.md is owner-sovereign — the one hand-edited file in docs/lab/. Agents READ it every cycle, PROPOSE changes as a diff in the digest, and never edit it silently. It gives the policy that is scattered across “Standing rules” in STATE, memory files, and chat directives a single home the tooling can read and the owner can version. Its autonomy tiers mirror the orchestrating skill's authority/denylist — it invents no new policy.

# Decision manifest — <owner> — vN (updated YYYY-MM-DD)
## 1. Always autonomous (never ask, always log)
- merge green PRs on delivery branches; advance phases; reversible in-repo work
- recover transient worker errors with one continue-nudge (validated 2026-07-07)
## 2. Decide-by-default (queue a DECISION, apply default at deadline)
- deadlines: night → 10:00 next morning; day → +2h
- merge strategy → regular merge; model policy → Fable 5 / Opus-mechanical; N=2 evals
## 3. Always ask, never default (= the denylist, verbatim)
- force-push/history rewrite; delete branches/tags/releases; prod deploys; secret rotation;
  destructive DB migrations; external comms; delete cloud resources; spend beyond ceiling
## 4. Escalation & channels
- quiet hours 00:00-08:30: push ONLY BLOCKER; else batch into the 06:30 digest
- channel order: Claude-app push → Telegram → (morning) digest
## 5. Budget & runway
- token ceiling per phase: N; on 80% → FYI; on 100% → BUDGET_EXCEEDED = BLOCKER
## 6. Standing preferences (style, language, review strictness…)

Learning loop — questions-per-night → 0

Every answer (live or queued) appends to decisions/log.jsonl with full context. Periodically the chronicler mines it: the same question-shape answered the same way ≥2–3× becomes a manifest candidate in the digest — “You chose ‘regular merge’ 3× — promote to §2 decide-by-default?” The owner approves by editing the manifest (or replying “yes”). This directly shrinks future question volume — the real autonomy metric.

Presence-aware delivery

A synchronous AskUserQuestion is raised only when the owner is present — the official CLAUDE_CLIENT_PRESENCE_FILE marker (Remote Control), or simply “owner sent a message within N minutes.” Absent → queue + push per type. Present → ask live, then still log the answer to the queue — the learning loop needs it either way.

The morning digest — the deliverable that defines “GoSleep worked”

Generated at the manifest's wake time (scheduled task / cron / Routine) and on-demand; written to digest/YYYY-MM-DD-morning.md, rendered on the Overview screen, optionally pushed “digest ready.” Sections, in owner-priority order:

1 · Waiting for you

Open BLOCKERs, then DECISIONs with their deadlines.

2 · Decided for you

Every auto-resolution with the manifest rule cited (provenance discipline).

3 · What shipped

Tasks / PRs / commits with links.

4 · Incidents

What broke, what recovered, RCA links.

5 · Cost & runway

Tokens vs ceiling, quota events.

6 · Manifest candidates

The learning-loop proposals + tomorrow's plan.

The digest is as important as the work

An unreviewable night is a failed night even if all PRs merged. Everything in the digest links into the dashboard / Library — provenance is the discipline (it descends directly from tasty-lunch's OWNER-RATIFIED / OWNER-ACQUIESCED-DEFAULT PRD tags).

Integration with the pulse — minimal deltas

Existing mechanismThe one change
PULSE (every 5–10 min self-check)Also scan queue.jsonl: newly answered → act; DECISIONs past auto_apply_at → apply default, emit decision.made; BLOCKERs idle too long → re-push per manifest

Widgets beyond the basic IA

Laboratory self-health

Docs-freshness meters: dashboard generated-at, dev_history coverage (tasks Done with a history file ÷ tasks Done), handoff age vs last session boundary, index staleness. The system documents itself, so it must also grade itself — the anti-wiki-rot alarm.

Spawn queue

Who's waiting for a slot and why (today this lives only in LIVE-STATUS prose). Surfaced as a Fleet card in QUEUED state with its reason.

Incident pins

Incident records (e.g. the kill-pane -a class) are pinned to the top of the Timeline until their RCA link exists — a visible “unclosed loop” marker.

Who consumes which surface

Owner morning → Overview/digest. Owner awake → Timeline/Fleet (raw tmux panes stay the live view). Owner remote → push → phone. Orchestrator itself → status.json + queue at pulse (cheaper than re-deriving from prose STATE).

05 · Mobile

Official Remote Control vs. the DIY autosk path

The single highest-value mobile feature for an owner-asleep system is push on a parked question. autosk proves the daemon-side steering is the easy 90% — but leaves exactly the three gaps GoSleep must not inherit: no TLS, no relay, no push. The official Remote Control (launched 2026-02-24) closes all three on-subscription. Build on it, don't rebuild it.

The contrast — autosk's transport vs. Remote Control

The verdict

autosk's gaps are GoSleep's opportunity — and Remote Control already fills them, on-subscription, E2E-encrypted, with push. Building our own mobile client/daemon transport (the autosk path) is unjustified now that #1 exists. The research preview status is the only risk.
