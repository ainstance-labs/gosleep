1. Terminology (corrected per the owner)

Earlier discussion used the phrase «working copy» — it is imprecise and the orchestrator has withdrawn it. The proper terms are below.

Production skills

~/.claude/skills/<name>/

Used by every orchestrator and every project on this machine. Editing here is changing production live, with no review and no rollback. Agents are strictly forbidden to edit.

Development skills

skill/<name>/ (gosleep repo)

The development site: edits are made here, reviewed here, and land in git with history and an author.

Publish

development → production

Moving a change from development to production. Performed only by the owner, explicitly, after review. The single point where a human acts.

2. Why the ban is justified (fact, not conjecture)

The orchestrator response rules recorded in the production skill orchestrating-delivery-agents have already paralysed the work once: the owner stopped seeing the orchestrator's messages while the fleet was alive.

Incident · a production rule that broke the channel

The rule required «a turn ends with text», while the worked example showed an order where the last action was a scheduler call — its response («nothing more to do») cut the turn off before the text.

A contradiction inside a skill is invisible to tests. A bug in a production skill propagates to every project at once and is only discovered by symptom — already in production.

6. Target process

One direct flow from lesson to production, with exactly one point where a human acts — publish. Everything else has an author, a task, a commit, and a cause.

7. Work stages (proposed epic)

Six sequential stages. Acceptance — on a live example, not on paper.

  1. Development catch-up

    Move the production versions back into skill/ (a one-off reverse sync, global → local, on the owner's command), including tmux-agents-orchestration, which is not in git. Each skill lands as a separate commit stating what was caught up. After this step, skill/ is the truth and all further development happens only there.

  2. Change registry

    docs/skills/CHANGELOG.jsonl — one line per edit: date, skill, Jira task, commit, root-cause lesson, status draft / reviewed / published. Written by the agent at edit time; extended at publish time.

  3. Publish tool

    tools/skills/publish.sh <name>: shows a diff of development against production, requires the owner's confirmation, backs up production to docs/skills/backups/<name>-<date>/, syncs one named skill, and appends a line to the registry. No mass operations — --all does not exist. Agents are forbidden to run it, by rule and by an owner-check.

  4. Admin UI — a «Skills» page in the lab

    List of skills, status (matches production / has unpublished edits), history from the registry with a lesson and links to the task and commit, diff view, and the exact publish command ready to copy. A «Publish» button in static HTML is impossible — publishing stays the owner's command; if we later enable an interactive web tier, the button will call the same publish.

  5. Checks

    A test that fails if an agent modified a file under ~/.claude/skills/; a test for the registry format; and a rule in CLAUDE.md and inside the skills: «production skills are edited by the owner only, via publish».

  6. Acceptance

    On a live example: take a real lesson (e.g. the turn ordering), run it end to end through development → registry → admin UI → publish, and show every trace in the report.
