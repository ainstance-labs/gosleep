Skills governance system:
the repo evolves, the owner publishes

Plan for the future process. Only the local skill in the project repo evolves. The move to production is done by one person — the owner — by pressing a button in the lab admin UI. No agent takes part in the publish step.

Sign-off required

Agree on the system and launch epic GSL-174

One action · agree on the plan

Below — the principle, the target process, the admin UI design and seven work stages. Agreement is the signal to file tasks under the stages of epic GSL-174.

Publish — always the owner No agent takes part in the publish step under any wording of the command.

1. Principle of the system

Evolving a skill means working with the local (development) copy in the project repo. Edits, commits, review and registry entries happen there and only there. Production is never edited by agents, under any circumstance and under any wording of the command.

01
System invariant

Publish is manual, owner-only, one button press in the admin UI

Moving a change from development to production is the single point of the process where a human acts, and that human is the owner alone. The act is pressing the «Publish» button next to the target skill in the lab admin UI.

No agent takes part in the publish step — neither as executor nor as a «confirmation helper». The constraint is enforced on four layers: a rule in CLAUDE.md, an owner-check inside the publish CLI, a test that fails if a file under ~/.claude/skills/ was modified by an agent, and a guard in install.sh — two committed lines at the top of the script (echo… + exit 1) that physically block the bulk local → global sync. The guard was added by the owner on 2026-07-20 and is already in effect today — the other three layers arrive with the system. Once the system is built the guard stays on: the new system has no bulk sync at all — exactly one named skill is published per button press.

2. Terminology

The three terms the rest of this document refers back to.

Production skills

~/.claude/skills/<name>/

Used by every orchestrator and every project on this machine. Editing here is changing production live, with no review and no rollback. Agents are strictly forbidden to edit.

Development skills

skill/<name>/ (gosleep repo)

The development site: edits are made here, reviewed here, and land in git with history and an author.

Publish

development → production

Moving a change from development to production. Performed only by the owner, explicitly (a button in the admin UI), after review. The single point of the process where a human acts.

Why install.sh currently cannot run as a whole

The installer syncs every subfolder from skill/ to ~/.claude/skills/ at once, with --delete. One run today would wipe the ATLASSIAN_API_TOKEN lesson that lives only in the production using-jira, and would completely remove tmux-agents-orchestration, which is not in git. The 2026-07-20 guard is the fourth layer of the invariant defense from section 1 (echo… + exit 1 at the top of the script) and the only one of the four that is already in effect today. It cannot be lifted; the replacement is a per-skill publish with review. After the system is built the guard stays on — the new system has no bulk sync at all.

4. Target process

One direct flow from lesson to production, with exactly one point where a human acts — the owner presses the «Publish» button in the admin UI. Everything else has an author, a task, a commit, and a cause.

5. Admin UI — a «Skills» page in the lab

A dedicated page in the lab. It shows the list of skills and everything the owner needs to decide about publishing without switching to a terminal.

  • Status: «matches production» or «has unpublished edits».
  • History lesson → edit → task → commit: rows from the change registry, each with links to the Jira task and the commit.
  • Diff of the local copy against production — viewed on the page.
  • «Publish» button per skill — the only interactive control.

Technical consequence (spelled out honestly)

Today's web is a static site generated by the chronicler. A static page cannot execute commands on the owner's machine. So the «Publish» button needs a local admin server — a process on localhost that accepts the click and invokes the publish CLI. That is a separate stage of work (stage 4 in section 7), not an assumption. Until that server runs, the page shows the exact command to copy instead of an active button — publishing itself stays a command the owner runs in the terminal.

6. Change registry — data source for the admin UI

docs/skills/CHANGELOG.jsonl — one line per development-edit: date, skill, Jira task, commit, root-cause lesson, status draft / reviewed / published. Written by the agent when editing the development copy, extended at publish time. The admin UI reads this file to render history and status.

7. Work stages (epic GSL-174)

Seven sequential stages. Acceptance — on a live example, not on paper.

  1. Development catch-up

    Move the production versions back into skill/ (a one-off reverse sync, global → local, the owner's action), including tmux-agents-orchestration, which is not in git. Each skill lands as a separate commit stating what was caught up. After this step, skill/ is the truth and all further development happens only there.

  2. Change registry

    docs/skills/CHANGELOG.jsonl: schema fixed, format validated. Written by the agent when editing; extended at publish time.

  3. Publish CLI

    tools/skills/publish.sh <name>: shows a diff of development against production, requires the owner's explicit confirmation, backs up production to docs/skills/backups/<name>-<date>/, syncs one named skill, and appends a line to the registry. No mass operations — --all does not exist. Agents are forbidden to run it, by rule and by an owner-check.

  4. Local admin server + publish button

    A process on localhost that serves the «Skills» page and handles the button click. The button invokes the same publish.sh from stage 3 and shows the result in the UI. Without this stage the button in the static dashboard stays inert and publishing remains a command the owner runs in the terminal.

  5. Admin UI

    The «Skills» page: list, status, registry history, diff, button. Until the server (stage 4) is up, the page is rendered by the chronicler in static form and shows the exact command to copy instead of an active button.

  6. Checks

    The four layers of the invariant defense from section 1: a rule in CLAUDE.md and inside the skills («production skills are edited by the owner only, via the admin UI»); an owner-check inside publish.sh from stage 3; a test that fails if an agent modified a file under ~/.claude/skills/; and a test for the registry format. The guard in install.sh (echo… + exit 1, added 2026-07-20) is the fourth layer, already in effect; it is not filed as its own stage but is listed here as part of the same defense and stays on after the system is built.

  7. Acceptance

    On a live example: take a real lesson (e.g. the turn ordering), run it end to end through development → registry → admin UI → publish by the owner, and show every trace in the report.
