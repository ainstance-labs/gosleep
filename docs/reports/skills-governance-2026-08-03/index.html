1. Терминология (исправлена по требованию владельца)

В обсуждении фигурировало слово «рабочая копия» — оно неточное и оркестратор его изъял. Правильные термины ниже.

Production skills

~/.claude/skills/<name>/

Ими пользуются все оркестраторы и все проекты этой машины. Правка здесь — изменение продакшна вживую, без ревью и без отката. Агентам правка запрещена строжайше.

Development skills

skill/<name>/ (репо gosleep)

Место разработки: сюда вносятся правки, здесь они ревьюятся, отсюда попадают в git с историей и автором.

Publish

development → production

Перенос development в production. Совершается только владельцем, явным действием, после ревью. Единственная точка, где действует человек.

2. Почему запрет обоснован (факт, а не предположение)

Правила ответа оркестратора, записанные в production-скилле orchestrating-delivery-agents, однажды уже парализовали работу: владелец перестал видеть сообщения оркестратора при живом флоте.

Инцидент · продакшн-правило, которое сломало связь

Правило требовало «ход кончается текстом», а рабочий пример показывал порядок, при котором последним действием оказывался вызов планировщика — его ответ («больше делать нечего») обрывал ход до текста.

Противоречие внутри скилла не ловится тестом. Ошибка в продакшн-скилле распространяется на все проекты сразу и обнаруживается только по симптому — уже в бою.

3. Нарушение, которое обязан признать оркестратор

02.08.2026 · правка внесена в обход процесса

По устной команде владельца «поправь скилл» правки были внесены напрямую в production-копию ~/.claude/skills/orchestrating-delivery-agents/SKILL.md — порядок хода плюс шесть замен из эрраты GSL-178.

Команда владельца была, но правильного пути — правка в skill/ и publish владельцем — не существовало, и оркестратор его не восстановил, а обошёл. Прецедент задокументирован в d-2026-08-02-004. Судьба правок — решение выше (раздел «Требуется решение»).

4. Текущее состояние (замерено 2026-08-03)

Шесть скиллов. Один в git отсутствует вовсе. Два расходятся с production — один сильно, один по одному важному уроку. Три идентичны.

идентичны — publish не нужен расхождение — нужен ревью и publish сильное расхождение или файла нет в git
Скилл skill/ (git) ~/.claude/skills/ (prod) расхождение статус
orchestrating-delivery-agents есть есть 69 строк (правки 02.08 + старые) risk
using-jira есть есть 24 строки (урок ATLASSIAN_API_TOKEN только в prod) warn
delivery-workflow есть есть идентичны ok
handoff есть есть идентичны ok
writing-prds есть есть идентичны ok
tmux-agents-orchestration НЕТ есть (14 КБ) единственный экземпляр, без резервной копии risk

Почему install.sh сейчас нельзя запускать целиком

Инсталлятор синхронизирует все подпапки из skill/ в ~/.claude/skills/ разом с --delete. Один запуск сегодня затёр бы урок про ATLASSIAN_API_TOKEN, живущий только в production using-jira, и полностью снёс бы tmux-agents-orchestration, которого в git нет. Guard от 2026-07-20 снимать нельзя — вместо него нужен поштучный publish с ревью.

5. Схема сегодняшнего разрыва

Где именно разрыв: production используется, но не наполняется из git — правки утекают напрямую в production, минуя историю.

6. Целевой процесс

Один прямой поток от урока до production, с ровно одной точкой, где действует человек — publish. Всё остальное имеет автора, задачу, коммит и причину.

7. Этапы работ (предлагаемый эпик)

Шесть последовательных этапов. Приёмка — на живом примере, не на бумаге.

  1. Догон development

    Перенести production-версии в skill/ (обратная синхронизация global → local, разово, по команде владельца), включая tmux-agents-orchestration, которого в git нет. Каждый скилл — отдельным коммитом с указанием, что именно догнали. После этого skill/ = истина, и вся дальнейшая разработка идёт только там.

  2. Реестр изменений

    docs/skills/CHANGELOG.jsonl — одна строка на правку: дата, скилл, задача Jira, коммит, урок-первопричина, статус draft / reviewed / published. Пишется агентом при правке, дополняется при публикации.

  3. Publish-инструмент

    tools/skills/publish.sh <name>: показывает diff development против production, требует подтверждения владельца, делает бэкап production в docs/skills/backups/<name>-<дата>/, синхронизирует один названный скилл, дописывает строку в реестр. Никаких массовых операций — --all не существует. Агенту запуск запрещён правилом и проверкой на владельца.

  4. Админка — страница «Скиллы» в лаборатории

    Список скиллов, статус (совпадает с production / есть неопубликованные правки), история из реестра с уроком и ссылками на задачу и коммит, отображение diff, и точная команда публикации для копирования. Кнопка «опубликовать» в статике невозможна — публикация остаётся командой владельца; если позже включим интерактивную версию веба, кнопка будет вызывать тот же publish.

  5. Проверки

    Тест, который падает, если агент изменил файл в ~/.claude/skills/; тест на формат реестра; правило в CLAUDE.md и в скиллах: «production скиллы правит только владелец через publish».

  6. Приёмка

    На живом примере: взять реальный урок (например, порядок хода), провести его полным путём development → реестр → админка → publish, показать в отчёте все следы.
