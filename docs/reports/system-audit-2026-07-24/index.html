Every technical term in this report, in one place

Each entry answers the same question: what is this thing, and why does it appear in an audit of a system that is supposed to work while you sleep.

Orchestrator
The single agent session that plans the work, starts the worker agents, checks on them and writes down what happened. In this project it is one Claude Code session running in a terminal. Everything else in this report either serves it or worries about what happens when it stops.
Worker (teammate agent)
A short-lived agent the orchestrator starts for one job — audit this zone, write this report, fix these files. It has its own context and reports back with a message. It cannot start other workers: the platform allows exactly one level of nesting.
Pulse (heartbeat)
The orchestrator's habit of waking itself every few minutes to check the fleet, and the small file it writes each time to prove it is alive. Two different things share the name: the discipline (“check every 5–10 minutes”) and the artefact (a line of JSON on disk).
Watchdog / supervisor
A program that watches the orchestrator from outside and restarts it if it dies. Ours is written and tested but has never been switched on. “Switched on” has a precise meaning here — see <em>armed</em>.
Armed
A mechanism is <em>armed</em> when something on this machine will actually run it without a person: a launchd job exists, a cron line exists, a hook fires. Code that merely exists and passes its tests is <em>built</em>, not armed. The whole audit turns on this distinction.
launchd / cron
The two ways macOS runs something on a schedule without a human. <code>launchd</code> is the modern system service manager; <code>cron</code> is the classic timer table. Neither of them currently holds a single entry for this project.
Headless mode (<code>claude -p</code>)
Running an agent with a single prompt and no interactive terminal: it starts, answers, exits. Useful for scripts and timers. The open question was whether it works on a subscription instead of a paid API key — measured during this audit, it does.
Subscription vs API key
Two ways to pay for model calls. The subscription is the flat plan you already have; the API key bills per token. If an autonomous mechanism needed an API key, it would be a second, metered bill running all night — which is why the headless question mattered.
Circuit breaker
Borrowed from electrics: a rule that trips and stops a loop when it repeats without progress — “this step has been visited five times, stop and escalate”. Ours exists as two pages of prose and has never fired, because nothing counts the visits.
Question buffer
The mechanism that lets an agent park a question instead of stopping to ask you. Each question gets a type, a deadline and a default answer; you read the batch in the morning. This is the one pillar the skills hold confidently.
Default by deadline
The rule that a parked question answers itself with its default once its deadline passes, so the night is not blocked. The audit found the rule written down everywhere and applied by nobody — no process exists that walks the queue and applies it.
Decision manifest
Your written standing preferences, so an agent can decide small things the way you would. Each automatic decision is supposed to cite the clause it relied on. Today three decisions cite a clause identifier that does not exist in the manifest.
Laboratory / chronicler
The laboratory is the self-documenting layer: hooks capture raw events while agents work, and a builder called the <em>chronicler</em> turns them into the pages you open. The capture is automatic. The builder is not — nothing runs it on a schedule.
Stale (freshness)
Data is <em>stale</em> when it is older than the interval it promises. A dashboard rebuilt on demand and read a day later shows yesterday's world with today's confidence. Freshness is why an unarmed builder is not a cosmetic problem.
Idempotent
A job you can safely run twice: running it again changes nothing new. This is the property that makes a machine tick safe — if two ticks overlap, or one runs after a crash, nothing is duplicated or corrupted.
Machine tick
The proposed cure for most of this report: one small scheduled job, outside any model, that runs a list of idempotent chores — rebuild the dashboard, apply due defaults, refresh task statuses, check what is armed — and writes one line to one ledger.
Ledger
An append-only log of what a mechanism did and when — the thing you read afterwards to find out whether the night went well. A mechanism without a ledger can only be judged by whether its output looks right.
Context window / roll
A model session can hold only so much text; when it fills, the session must hand over to a fresh one — a <em>roll</em>. Rolling too early wastes a session; rolling too late loses the thread. The rule for when to roll is one of the five places the skill contradicts your orders.
Prompt-cache TTL
How long the provider keeps a session's prompt cached so the next call is cheap. The skill's whole cadence economics was calculated against a five-minute window. That window is now an hour, which invalidates the reasoning built on top of it.
Handoff
A written note one session leaves so the next one can continue with no memory of the conversation: where we are, what is running, what to do next. Today an agent writes it by hand when it remembers to.
PRD
Product Requirements Document — the phase-by-phase development plan. It matters here because the orchestrator is told to pick up the next phase on its own, and it picks it from a document that has not changed since 8 July.
Epic / Task
The two-level work hierarchy this project uses in Jira: an Epic is a body of work with one branch and one pull request, a Task is one commit inside it. Every finding below points at the epic that would close it.
Red team
An independent pass whose job is to attack findings, not to add them: reproduce the evidence, and withdraw or downgrade anything that does not survive. Three red teams ran here; what they withdrew has its own section.
Calibration
Adjusting a severity label after review — usually downward. This report always shows the calibrated severity as the headline and the auditor's original label struck through beside it, so a withdrawn alarm can never read as a live one.
CRITICAL / MAJOR / MINOR / INFO
Severity constants, kept in English in both languages because they are identifiers, not words. CRITICAL means broken and doing harm right now; MAJOR means a real gap with a workaround or a delay; MINOR is a defect worth fixing cheaply; INFO carries no defect.
Loop engineering
The current craft name for designing an agent's repeating cycle: when it wakes, what it checks, when it stops, how it escapes a loop that is going nowhere. Most of what is missing in this report is loop engineering that was written down but never wired up.
Loopback server (127.0.0.1)
A web server that listens only on this machine — nothing from the network can reach it. It is the cheapest way to turn a folder of static pages into a console you can click, without authentication, deployment or a database.
SSE (server-sent events)
A one-way channel that lets a page receive updates as they happen instead of showing whatever was true when it was built. It is what turns the dashboard from a photograph into a window.
Permission relay (Channels)
A platform feature that forwards an agent's “may I run this?” prompt to another surface — a phone, say — so you can approve it remotely. It matters for autonomy: a permission prompt at 3 a.m. would otherwise end the night.
Runway
The autonomy indicator: how long the orchestrator can keep going before it hits a wall — context, budget, or a blocking question. It has never produced a number in any build, because two of its inputs do not physically exist.
Smoke test
A fast test suite that answers one question — is the thing fundamentally working? A green smoke run says the code is correct; it says nothing about whether anything on this machine ever calls that code.
tmux pane
A split of a terminal window. Each worker agent lives in its own pane, which is how the orchestrator starts and watches them. It is also why the fleet is capped at about three concurrent workers on this machine.

Section 5

Who watches the orchestrator — today and as proposed

The gap your mandate opens with, drawn as a picture, plus what the platform now gives us for free and what it still refuses to give.

What the platform now gives us

  • claude agents --json, with a machine status computed by the harness rather than by the model
  • A per-user supervisor process that restarts a crashed session, with three safety catches
  • Standard states Working / Needs input / Idle / Completed / Failed / Stopped — a ready-made indicator for “the orchestrator is blocked on a question”
  • Hidden but working subcommands: claude attach / logs / stop / respawn / rm / daemon
  • A machine going to sleep is survivable; the supervisor reconnects on wake
  • Desktop scheduled tasks: a 1-minute minimum, a catch-up run after sleep, learnable permissions, and a history that records why a run was skipped
  • --max-budget-usd for -p — a first-class spending ceiling, which we use nowhere
  • claude setup-token — long-lived authentication on the subscription
  • Channels — event push into a live session, plus permission relay

What it still does not give

  • The supervisor is not a permanent service: “Service install is disabled in this version — the daemon runs on demand and exits when the last client disconnects”. There is nobody to restart the thing that does the restarting
  • A machine shutdown is not survivable: sessions become failed and require a human
  • The supervisor restarts a process, not the work: it has no concept of “context is running out”, “write a handoff before you die”, “a legitimate pause on a quota limit”, or “the cycle counter has not moved for 60 hours”
  • Our topology is not covered: teammate workers living in tmux panes do not appear in claude agents --json at all
  • /loop and session-scoped cron cannot resurrect a dead session
