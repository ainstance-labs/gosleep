2 GSL-228 MINOR Tier-2 floor: secrets correctness

Tier-2 secrets pattern for `leak` misses the natural phrase `leak the token`

The secrets denylist uses \brotate\s+(?:the\s+)?…, \bshare\s+(?:the\s+)?…, \bpublish\s+(?:the\s+)?…, \bcommit\s+(?:the\s+)?…, \bexpose\s+(?:the\s+)?… — all allow the optional the. The leak(ed) alternative, however, is \bleak(?:ed)?\s+(?:secret|token|…) — with NO optional the. Result: leak the token, leak my token, leak this token are accepted as DECISION and get a 2-hour default. Reproduced: question --type DECISION --question 'leak the token' --default no --reversibility high → q-…. Fix: symmetric \bleak(?:ed)?\s+(?:the\s+)?…. Design comment (line 111): “if a new false positive shows up, tighten the pattern rather than widening the escape hatch” — this is the opposite case (false NEGATIVE), so the fix is to WIDEN the pattern.

3 GSL-228 MINOR Tier-2 floor: secrets correctness

Tier-2 `rotate` bypasses when a qualifier sits between `the` and the noun

\brotate\s+(?:the\s+)?(?:secret|token|credential|credentials|password|api[- ]?key|key)\b requires the secret-word to follow rotate or rotate the with no words in between. Real phrases like rotate the AWS key, rotate the master key, rotate our api key, rotate my token do NOT match — the qualifier (AWS, master, our, my) breaks the pattern. Verified by adversarial probe: rotate the AWS key accepted as DECISION. The passing existing test (rotate the api key) works only because api key collapses to the alternative api[- ]?key. Fix: allow one or two intervening words ((?:\S+\s+){0,2}) or a broader qualifier group.

4 GSL-228 MINOR Tier-2 floor: external comms correctness

`post on social media`, `tweet the launch`, `email the team` bypass the external-comms pattern

The external_comms catch pattern is \b(send|write|post|publish|announce|broadcast|tweet|email)\b.{0,40}\b(customer|user|external|public|press|announcement|blog|homepage|newsletter|subscriber|audience|community|prod site|status page)\b. Real-world external-comms actions like post on social media, tweet about the launch, email the team about status are ACCEPTED because none of social, media, team, launch sit in the noun-anchor group. This is a design-vs-scope call, but the hard-floor claim (‘money/comms/secrets/destructive → BLOCKER by code’) is looser in practice than the wording suggests. Suggest adding team, channel, social media, slack, twitter/x, linkedin or moving to a two-tier check (verb alone → CLARIFY; verb + strong-noun → BLOCKER).

5 GSL-229 MINOR qshape collapse correctness

qshape false-merge: negation (`not`) is a stopword — `merge PR` ≡ `NOT merge PR`

QSHAPE_STOPWORDS includes not, and tokens ≤2 chars are dropped (so PR is dropped). Direct test: qshape('should we merge PR') == qshape('should we NOT merge PR') (both reduce to token merg). Also bump to v2 ≡ bump to v3 (versions normalised to <n>, a stopword). The candidates loop groups by (qshape, decision.lower); with N≥3 it would surface these as manifest candidates. Impact bounded: candidates is ADVISORY (comment line 362 — manifest is owner-edited), so the learning loop cannot silently install a rule. Still a semantic risk — negation is not a filler word. Fix: remove not from stopwords, or invert-sign tokens (ˆmerg) so opposites do not collapse.

6 GSL-227 MINOR Rule validation correctness

`delegation:` rules accept future dates, malformed dates, unknown origins

--rule delegation:<origin> <date> is accepted whenever the delegation prefix + a date-like token matches — but the origin is not checked against an allowlist and the date is not required to be well-formed or in the past. Reproduced: --rule 'delegation:owner 2099-12-31' → d-…001, 'delegation:owner 20260816' → d-…002 (malformed date), 'delegation:noname 2026-08-16' → d-…003 (unknown origin), 'delegation: owner 2026-08-16' → d-…004 (space after colon). This weakens the provenance guarantee for orchestrator autonomous decisions. Fix: ^delegation:(owner|orchestrator)\s+\d{4}-\d{2}-\d{2}$ with a past-or-today check on the date.

7 GSL-230 MINOR park subcommand design

`park` accepts past `--wake-at` — reopener would immediately re-fire

park --re <id> --wake-at 2020-01-01T00:00:00Z succeeds and writes a deferred patch with defer_until=2020-01-01T00:00:00Z. Any downstream reopener that compares defer_until <= now will re-open the record on its next tick, defeating the purpose of parking. Consider rejecting wake-at <= now + <min-window> (a few minutes to hours) so parking always means real deferral. Malformed / missing-Z / non-UTC dates ARE rejected correctly — that half is good.
