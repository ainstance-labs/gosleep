2 GSL-284 MINOR Permission hook timeout functionality

PASS — Хук разрешений отвал по таймауту: exit 0 без stdout

Verdict: PASS. Timeout semantics documented and validated.

Method. Invoked tools/hooks/permission-request-hook.sh directly with a synthetic PermissionRequest stdin payload (Bash tool, ls /tmp/e2e-run08-permission-probe-marker), exported GOSLEEP_WEB_QUESTIONS=1 GOSLEEP_HOOK_TIMEOUT_S=8 GOSLEEP_CORE_URL=http://127.0.0.1:7351 GOSLEEP_INTERNAL_SECRET=<scratch>. Did NOT answer from the panel — let the wait expire.

Observed.

  • Hook POSTs /internal/permissions/post → row p-20260810-210225-29ebe77e inserted (kind='permission', status='open').
  • Hook long-polls /internal/questions/:qid/answer-wait?timeout_s=8.
  • After exactly 8 s wall-clock the shim exits rc=0 with empty stdout. Debug-log line: {outcome:"timeout", qid:"p-20260810-210225-…", elapsed_ms:8000}.
  • Per hooks.md:223 a hook exit 0 with no output means "no decision, continue normal permission flow" — Claude Code renders the native TUI dialog as fallback. Terminal is NOT killed and does NOT deny.
  • The permission row remains status='open' in the DB with the command visible in the question payload; the panel keeps showing it until an owner answers (or the row is deferred). No auto-timeout on the DB row.

Recommended follow-up (informational). No open finding — behaviour matches design. If a future policy wants row-level TTL cleanup, that's a new capability, not a defect.

11 GSL-318 MINOR Env — scratch core is not hermetic architecture

ENV NOTE — Scratch-core на :7351 индексирует внешние Claude Code сессии, не изолирован

The GOSLEEP_DB_PATH env correctly redirects DB writes to the worktree-local scratch DB, but the Fleet indexer (process-fingerprint adapter) still enumerates all live Claude Code processes on the host machine and populates agent_sessions from them. As a side-effect the scratch core came up with two live rows (tasty-lunch-57 on Fable 5, gosleep-d9 on Opus 4.7) on first boot, from the conductor session and an unrelated tasty-lunch session in another tmux window.

That was actually FORTUITOUS this run (turned the ambient live sessions into legitimate multi-session concurrency evidence for finding #3), but it means the E2E env is not fully hermetic. A future E2E harness knob — e.g. GOSLEEP_FLEET_ADAPTER=noop or a session-cwd allowlist — would make scratch runs reproducible regardless of what else the developer has open.
