3 GSL-333 MAJOR C3 — Permission-timeout (BLOCKER — shim expire POST omits Origin header, always 403s) functionality

Shim's expire POST omits `Origin` header → CSRF middleware rejects with 403 → orphan-answer bug is NOT fixed for real dev-agents

The server endpoint, the panel display, and the decide-409 guard are all correct. But the shim-side call that the fix commit adds (permission-request-hook.sh:249–255, the new curl block that fires on the 204 wait branch) issues POST /internal/permissions/:qid/expire without an Origin header. Every other state-changing curl in the same shim sets -H "Origin: $ORIGIN_HEADER" (see the sibling /internal/permissions/post block); this one does not. The core's requireLocalOrigin middleware demands Origin/Referer on any non-safe method and returns 403 origin required when both are absent. Result: the expire POST always fails in the real deployed path — the row stays status=open, the panel keeps Allow/Deny live, and a subsequent owner click lands as answered while the shim is dead and CC has moved on to the TUI. That is exactly the run-09 finding #7 orphan-answer bug the fix was written to close.

Evidence chain, all against the scratch core on 127.0.0.1:7355 with the branch-tip shim:

  1. Live non-bypass Sonnet dev-agent in tmux pane e2e-reverify:1.%306 (GOSLEEP_HOOK_TIMEOUT_S=30) was asked to run a curl command. The PermissionRequest hook fired and posted row p-20260811-123912-685d2b09 (status=open at 12:39:12Z). The TUI dialog then appeared in the pane, and the DB row stayed status=open for over three minutes (screenshot c3-questions-before-timeout.png: Allow / Deny live in the panel).
  2. Diagnostic re-run of the same shim from the shell with GOSLEEP_HOOK_DEBUG_LOG=/tmp/perm-hook-debug.log and GOSLEEP_HOOK_TIMEOUT_S=8 produced a single debug line: {"outcome":"timeout","qid":"p-20260811-124353-a1ec1e65","elapsed_ms":8000,"expire_status":"403"}. The shim reached the 204 branch, called expire, and the server rejected it.
  3. Reproduced the middleware behaviour directly on a live open row:
    - POST …/expire without Origin → 403 origin required (identical to what the shim sends).
    - POST …/expire with Origin: http://127.0.0.1:7355 → 200 {status:"timed-out", transitioned:true}.
  4. With the row forced to timed-out via the direct POST, POST /actions/permissions/decide{decision:"allow"} returned HTTP 409 "permission question … is not open (status=timed-out)" — the decide guard works, once the row is expired. And screenshot c3-questions-after-timeout.png shows the panel's neutral badge + explanatory note replacing Allow/Deny.

Root cause is a one-line omission in the FIX-3 diff; the shim's other POSTs prove the pattern is already in the file.

Suggested fix (single line):

     EXPIRE_STATUS="$(curl -sS -o /dev/null -w '%{http_code}' \
         --connect-timeout "$CONNECT_TIMEOUT_S" --max-time "$((CONNECT_TIMEOUT_S + 3))" \
         -X POST \
         -H "Host: $HOST_HEADER" \
+        -H "Origin: $ORIGIN_HEADER" \
         -H "X-Internal-Secret: $INTERNAL_SECRET" \
         "$CORE_URL/internal/permissions/$QID/expire" 2>/dev/null || echo "000")"

Why the pre-merge tests passed: the new regression suite in internal.test.ts calls the endpoint directly with headers of its own choosing (or bypasses the middleware entirely), and the commit's own "live proof" was a manual six-step sequence against a hermetic core — not a shim-driven one. A shim-in-the-loop live check catches this in one attempt; C3 above is that check.
