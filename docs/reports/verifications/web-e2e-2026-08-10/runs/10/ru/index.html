3 GSL-333 MAJOR C3 — Permission-timeout (BLOCKER — expire-POST у shim без Origin, всегда 403) functionality

Shim-овский expire POST не шлёт `Origin` → CSRF-миддлварь отвечает 403 → orphan-answer из run 09 НЕ починен для реальных агентов

Серверный endpoint, отображение в панели и decide-409 guard — все три работают. Но новая часть shim'а из FIX-3 (permission-request-hook.sh:249–255, блок curl на ветке 204-таймаута) шлёт POST /internal/permissions/:qid/expire без заголовка Origin. Каждый другой state-changing curl в том же shim'е ставит -H "Origin: $ORIGIN_HEADER" (см. соседний блок /internal/permissions/post) — этот нет. Middleware requireLocalOrigin требует Origin/Referer на любом небезопасном методе и на отсутствие обоих отвечает 403 origin required. Итог: expire у shim'а всегда падает в реальном деплойменте — строка остаётся status=open, панель держит Allow/Deny живыми, и последующий клик владельца зайдёт как answered уже после того, как shim умер и CC ушёл в TUI. Это ровно тот orphan-answer bug из finding #7 run 09, который фикс и должен был закрыть.

Цепочка доказательств, всё против scratch core 127.0.0.1:7355 и shim'а с вершины ветки:

  1. Живая non-bypass Sonnet-сессия в tmux-панели e2e-reverify:1.%306 (GOSLEEP_HOOK_TIMEOUT_S=30) попросила выполнить curl. PermissionRequest-hook сработал и создал строку p-20260811-123912-685d2b09 (status=open в 12:39:12Z). В панели появился TUI-диалог, а строка в БД оставалась status=open больше трёх минут (см. c3-questions-before-timeout.png: Allow / Deny живые).
  2. Диагностический прогон того же shim'а из shell с GOSLEEP_HOOK_DEBUG_LOG=/tmp/perm-hook-debug.log и GOSLEEP_HOOK_TIMEOUT_S=8 дал одну debug-строку: {"outcome":"timeout","qid":"p-20260811-124353-a1ec1e65","elapsed_ms":8000,"expire_status":"403"}. Shim дошёл до 204-ветки, вызвал expire — сервер отклонил.
  3. Прямая перепроверка поведения middleware на живой открытой строке:
    - POST …/expire без Origin → 403 origin required (то же, что и shim шлёт).
    - POST …/expire с Origin: http://127.0.0.1:7355 → 200 {status:"timed-out", transitioned:true}.
  4. С row'ой, принудительно переведённой в timed-out прямым POST'ом, POST /actions/permissions/decide{decision:"allow"} вернул HTTP 409 "permission question … is not open (status=timed-out)" — decide-guard работает, как только строка «протухла». Скриншот c3-questions-after-timeout.png показывает: панель заменила Allow/Deny на нейтральный badge + пояснение.

Root cause — пропущенная строка в диффе FIX-3; в самом файле уже есть образец, как правильно.

Предлагаемый фикс (одна строка):

     EXPIRE_STATUS="$(curl -sS -o /dev/null -w '%{http_code}' \
         --connect-timeout "$CONNECT_TIMEOUT_S" --max-time "$((CONNECT_TIMEOUT_S + 3))" \
         -X POST \
         -H "Host: $HOST_HEADER" \
+        -H "Origin: $ORIGIN_HEADER" \
         -H "X-Internal-Secret: $INTERNAL_SECRET" \
         "$CORE_URL/internal/permissions/$QID/expire" 2>/dev/null || echo "000")"

Почему тесты не поймали: новые тесты в internal.test.ts бьют по endpoint'у сами (с любыми headers, что нужно), а «live proof» из коммит-мессаджа — ручная шести-шаговая последовательность против hermetic core, не через shim. Живая проверка shim → server в цикле ловит это с первого раза; C3 выше — именно она.
