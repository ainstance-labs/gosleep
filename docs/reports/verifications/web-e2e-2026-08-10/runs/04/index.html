1 GSL-QA04 MAJOR SSE cross-tab consistency functionality

Permission decisions do not fan out cross-tab — second tab shows stale status until manual refresh

The /actions/permissions/decide handler writes only to the SQLite questions table (and wakes the paused CLI hook via SessionAdapter.deliverAnswer). It never writes to the JSONL event log, so the tail indexer/SSE broadcaster never sees the state change. Because useQuestions in apps/web/src/data/queries.ts has no refetchInterval, a second tab viewing /questions keeps rendering the row as open — with the Allow/Deny buttons still active — after another tab clicked Allow. Repro (verified in run 04): open /questions in tab A and tab B, POST a fresh permission via /internal/permissions/post (tab B sees it appear — new-row insert path DOES fan out), click Allow in tab A (DB row flips to answered/allow, applied_by=owner), tab B keeps rendering the same permission as open for the entire 6+ seconds we watched, only refreshing after a full page reload. Contrast with the docs comment at queries.ts:151-155 promising SSE fan-out; that fan-out relies on question.answered events which the decide path never emits.

Referenceapps/web/src/data/queries.ts:86-91 (useQuestions has no refetchInterval)

2 GSL-QA04 MAJOR Responsive layout design

SPA layout overflows horizontally at narrow viewports (320px = 114px scroll)

The root grid grid-cols-[240px_1fr] in apps/web/src/main.tsx/router shell renders a fixed 240px sidebar and never collapses. Measured at 320×640 viewport: document.documentElement.scrollWidth = 424, clientWidth = 310, i.e. a 114px horizontal scrollbar. The content beside the sidebar is squeezed under 80px, cards overlap the sidebar, and horizontal-swipe becomes required to reach any button. This is a control-plane app designed for desktop, but the panel is served on 127.0.0.1 which the owner reaches from a phone during on-call — the phone view is broken. Either drop the sidebar to a hamburger under a md breakpoint, or explicitly refuse below 640px with a friendly "open on desktop" message.

Shippedapps/web/src/main.tsx + router.tsx (root grid is unconditional 240px+1fr)
3 GSL-QA04 MINOR Client-side action dedup functionality

Per-click random Idempotency-Key + client `isPending` race lets 5 rapid clicks send 5 server requests

newIdempotencyKey() in apps/web/src/data/queries.ts mints a fresh crypto.randomUUID() per invocation, so the server-side server_intents.intent_id replay cache can never collapse a double-click — each click is a distinct intent. The only client protection is disabled={isPending} on the button, which flips via useMutation, which flips via a React state update, which is asynchronous. When 5 clicks land in the same JS microtask, all 5 fire before React re-renders. Verified in run 04: 5 synchronous JS clicks on Allow for p-qa04-perm fired 5 POSTs to /actions/permissions/decide; the server logged 1 ok and 4 fail (409, correct — the SQL WHERE status='open' guard held), leaving 5 rows in server_intents. State stayed correct (no data corruption) but the ledger fills with duplicate error rows and the UI's error-toast plumbing gets 4 negative responses to swallow. Fix: derive Idempotency-Key from (qid, decision, session-nonce) so a rapid replay collapses server-side.

Shippedapps/web/src/data/queries.ts:158-165 (newIdempotencyKey) and the ActionRow buttons
4 GSL-QA04 MINOR Error UX design

401 recovery hint hardcodes port 7331 even when the SPA runs on a different port

When the SPA loses its Bearer (sessionStorage cleared, wrong ?token=), the error surface renders: HTTP 401 from http://127.0.0.1:<port>/… followed by Check that gosleep-core is running on 127.0.0.1:7331 and the Bearer token in sessionStorage is current. The hint is hardcoded to port 7331. In this QA run the SPA runs on 127.0.0.1:7344; the same string ships. Dev/QA/staging deployments (or the exact GOSLEEP_CORE_PORT env override the app already reads) will show a misleading diagnostic that points at the wrong port. Trivial fix: template the port from the actual runtime origin.

Shippedapps/web/src/components/QueryStatus.tsx:~50 (hint string)
5 GSL-QA04 MINOR Questions rendering design

Question `options` shown as raw JSON in a `<pre>` block instead of clickable choices

For every non-permission question, the Questions card renders the options array as raw pretty-printed JSON inside a .mono <pre>, then offers only a free-text textarea in the Answer dialog. Permission cards correctly render Allow/Deny as buttons. For a regular AskUserQuestion this means: the owner reads the label/description JSON (with quotes, brackets, indentation), then TYPES the answer literally into the free-text field. Nothing enforces that the answer matches an option label, so Da\nNyet\nMaybe all reach the agent unchecked. Either render options as radio/toggle buttons (mirroring the CLI-native AskUserQuestion picker), or drop the JSON dump and only surface the labels.

Shippedapps/web/src/screens/QuestionsScreen.tsx (options rendered as JSON <pre>)
