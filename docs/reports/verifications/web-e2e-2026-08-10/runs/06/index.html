Findings

1 GSL-315 MAJOR Permission cards functionality

Permission card does not surface the actual command being requested

The panel's Questions screen shows a card labelled "Permission request: Bash" with Allow / Deny buttons — but nothing else. The specific shell command being approved (cd /Users/…/gosleep && git checkout -b GSL-315-todo-app, bun install, gh pr create …) is invisible.

During this run the dev-agent tried to run cd /Users/romanlidovskyi/Documents/dev/harness/gosleep && git checkout -b GSL-315-todo-app — a HARD-BANNED write into the shared gosleep tree. An owner reading the panel card had no way to see that. Six such cards were batch-denied by this runner via API only because the transcript (~/.claude/projects/…/…jsonl) exposed the actual input.command — a surface the real owner does not have.

Verified in DB: the questions table stores only the question string "Permission request: <toolName>" and canonical Allow/Deny options. tool_input (which the internal POST endpoint receives) is discarded before insert. See sqlite3 gosleep.db "select qid, question, options from questions where kind='permission'".

Fix sketch: persist tool_input (or a preview of it) into a new column and render it as a <pre> block on the card. For Bash: show the command verbatim. For MCP: show tool + a summary of params. Truncate at ~4KB.

2 GSL-315 MAJOR PR discovery functionality

No panel surface links to the PR the dev-agent just opened

After the dev-agent ran gh pr create --title "GSL-315 React to-do app" … and the PR was created (https://github.com/ainstance-labs/gosleep-e2e-todo/pull/3), the panel showed no link to it anywhere. The Tasks screen mentions GSL-315 and GSL-316 by key but not the PR URL. The Timeline events feed includes Bash tool_use payloads (Bash intent_id) but does not extract gh pr create's stdout URL. 3 GSL-315 MAJOR Fleet accuracy functionality

Fleet screen shows wrong model — displays global settings, not the --model flag override

The dev-agent was launched with claude --model haiku --permission-mode acceptEdits, and the transcript confirms 62 assistant turns as claude-haiku-4-5-20251001 + 3 sub-agent turns as claude-sonnet-5 (Explore agent). But the Fleet screen columned this session as claude-fable-5[1m] — the value fleet-poll read from ~/.claude/settings.json.

This is a UI/reality mismatch on the surface that owners use to know "which model is doing what". A run explicitly forcing Haiku shows up as Fable, and the owner has no way to correlate cost/behaviour to the actual model without opening the transcript.

Verified via API: GET /fleet → {"name":"todo-workspace-47","model":"claude-fable-5[1m]","cwd":"…/todo-workspace","status":"idle"} even after 60+ Haiku turns.

Fix sketch: the fleet-poll worker reads process arg list (ps -p <pid> -o command) — grep for --model <x> and prefer that. Fall back to settings only when the flag is absent. Alternative: have the tool-observed feeder (which knows the model per event) update the row.

4 GSL-315 MINOR AskUserQuestion UX design

Multi-option question has no one-click variant selection

AskUserQuestion payloads carry options: [{label, description, pros?, cons?}] — the panel renders each as a display card (label / description / pros / cons rows). But the answer submit path is a single textarea that expects free text: the owner must MANUALLY copy the option's label string and paste it into the textarea to "pick" a variant.

During this run the S4 scenario ("answer question 1 by clicking a variant") had to be simulated by pasting the exact string "Базовый: добавить/отметить/удалить" into the textarea. If the owner mistypes even one character the agent gets the mistyped text as the answer.

This is a UX/polish gap, not a correctness bug — the mechanism works, but the variant metadata is presentational only. Adding a "pick this variant" button per option would eliminate a class of typos and speed up the common case.

5 GSL-315 MINOR Hook robustness architecture

PermissionRequest hook occasionally falls through to native TUI dialog

The panel-driven allow/deny flow worked most of the time (✓ Allowed by PermissionRequest hook visible in the terminal for a majority of tool calls), but at least twice during this run the native TUI permission dialog appeared for a call that had ALREADY been decided in the panel. Evidence: s6-perm-request-in-terminal.txt shows the TUI "Do you want to proceed?" prompt for mcp__atlassian__createJiraIssue after the panel had a matching qid open.

Hypothesis: two paths racing — the model re-tries the tool call while the hook is still holding the long-poll, so the second attempt fires a fresh PermissionRequest that the panel operator hasn't seen yet, and Claude Code renders the TUI as fallback. Also: my auto-allow guardrail loop had a jq-syntax bug (empty select(length>0) collapsed the whole object → empty payload → {"ok":false,"error":"qid required"}) that was invisibly retrying — a real owner would have hit the same class of bug in their own tooling.

Fix sketch: on the shim side, when the same tool_use_id fires a second PermissionRequest while the first is still open, dedupe (return the first's outcome). On the client side, add a "recent decisions" tail on the Questions screen so the owner sees *what was just decided* without having to switch tabs.
