Гарнесс выдержал live-fire тест: настоящий Claude Haiku в качестве dev-агента собирал React to-do приложение, а все вопросы, решения по разрешениям и одобрения Bash проходили через веб-панель gosleep. Все шесть основных «ног» петли подтверждены живьём: ответ вариантом, ответ свободным текстом, permission-deny, permission-allow, детект в Fleet, живой SSE на Timeline. Находки: три MAJOR capability-gap (команда не видна в permission-карточке, ни на одном экране панели нет ссылки на PR, вызовы Jira MCP были денайнуты потому что dev-агент рванул их раньше, чем задача устаканилась) и четыре MINOR-полирующих (шумный retry-луп хуков и устаревшая колонка «модель» во Fleet). Ноль CRITICAL. Рекомендуется закрыть три capability-gap до расширения пилота за пределы одного владельца.

Находки

1 GSL-315 MAJOR Permission cards functionality

В карточке разрешения не видно, какую команду запрашивают

На экране Questions карточка помечена "Permission request: Bash" с кнопками Allow / Deny — и больше ничего. Конкретная shell-команда, которую предлагают одобрить (cd /Users/…/gosleep && git checkout -b …, bun install, gh pr create …), не показана.

В этом ране dev-агент попытался выполнить cd /Users/romanlidovskyi/Documents/dev/harness/gosleep && git checkout -b GSL-315-todo-app — жёстко запрещённый write в общий gosleep-tree. Владелец, читающий карточку, увидеть это не мог. Шесть таких карточек были денайнуты пачкой через API — только потому, что транскрипт (~/.claude/projects/…/…jsonl) содержит настоящий input.command. У реального владельца этой поверхности нет.

Проверено в БД: таблица questions хранит только строку "Permission request: <toolName>" и канонические Allow/Deny options. tool_input, который приходит на internal POST, теряется до insert.

Эскиз фикса: сохранить tool_input (или его превью) в новую колонку и отрисовать как <pre> на карточке. Bash — команда как есть. MCP — имя тула + сводка params. Обрезать ~4КБ.

3 GSL-315 MAJOR Fleet accuracy functionality

Fleet показывает не ту модель — из глобальных настроек, а не с флага --model

Dev-агент запущен как claude --model haiku --permission-mode acceptEdits, транскрипт подтверждает 62 assistant-хода моделью claude-haiku-4-5-20251001 + 3 sub-agent-хода claude-sonnet-5 (агент Explore). Но Fleet отобразил эту сессию как claude-fable-5[1m] — значение, которое fleet-poll прочитал из ~/.claude/settings.json.

Это разъезжание UI и реальности на поверхности, по которой владелец понимает «какая модель что делает». Ран с явным Haiku показывается Fable — корреляция «стоимость/поведение → модель» невозможна без открытия транскрипта.

Проверено через API: GET /fleet → {"name":"todo-workspace-47","model":"claude-fable-5[1m]","cwd":"…/todo-workspace","status":"idle"} даже после 60+ Haiku-ходов.

Эскиз фикса: воркер fleet-poll читает ps -p <pid> -o command — грепнуть --model <x> и предпочесть это значение. Fallback на settings только если флага нет. Альтернатива: пусть tool-observed feeder (он знает модель на каждое событие) апдейтит строку.

4 GSL-315 MINOR AskUserQuestion UX design

На вопросах с вариантами нет клика по варианту — всё через free-text

AskUserQuestion передаёт options: [{label, description, pros?, cons?}] — панель отрисовывает каждый вариант как display-карточку (label / description / pros / cons). Но submit-путь ответа — единственный textarea под free-text: чтобы «выбрать вариант», владелец должен вручную скопировать label варианта и вставить в textarea.

В этом ране S4 (ответ вопросу 1 «кликом по варианту») пришлось симулировать вставкой строки "Базовый: добавить/отметить/удалить" в textarea. Если владелец опечатается на один символ — агент получит опечатку как ответ.

Это UX-полироcка, не bug: механизм работает, но метаданные вариантов чисто презентационные. Кнопка «выбрать этот вариант» на каждый option убила бы класс опечаток и ускорила бы 90% случаев.

5 GSL-315 MINOR Hook robustness architecture

Хук PermissionRequest иногда проваливается в нативный TUI-диалог

Панельный allow/deny работал в большинстве случаев (✓ Allowed by PermissionRequest hook в терминале для большинства вызовов), но как минимум дважды за ран нативный TUI-диалог появился для запроса, уже решённого в панели. Evidence: s6-perm-request-in-terminal.txt — TUI "Do you want to proceed?" для mcp__atlassian__createJiraIssue при уже открытом матчащем qid.

Гипотеза: гонка двух путей — модель ретраит tool call, пока хук держит long-poll; второй заход отправляет свежий PermissionRequest, оператор его ещё не видит, Claude Code рендерит TUI как fallback. Плюс: мой авто-allow loop имел jq-баг (пустой select(length>0) схлопывал весь объект → пустой payload → {"ok":false,"error":"qid required"}) и молча ретраил — реальный владелец наступил бы на тот же класс багов в своей оснастке.

Эскиз фикса: на стороне shim при повторном PermissionRequest от того же tool_use_id — дедуп (возвращать исход первого). На клиенте — «недавние решения»-хвост на экране Questions, чтобы владелец видел, что именно только что решил.

7 GSL-315 MINOR Diagnostic tooling design

Hook-debug лог пишет outcome только для AskUserQuestion, не для PermissionRequest

В сессии dev-агента был выставлен GOSLEEP_HOOK_DEBUG_LOG=/…/logs/hook-debug.log. В конце рана в логе была ровно одна строка — про ответ на AskUserQuestion Q1 ({"ts":…, "hook":"ask-user-question", "outcome":"allow", "qid":"q-2026-08-10-001", "elapsed_ms":284000}). Ни одной строки на ~10 PermissionRequest-событий за ран.

Диагностировать post-hoc «панель на самом деле решила этот вызов или хук тайм-аутнулся» становится сильно сложнее. Код permission-хук-shim'а по коду похож на AskUserQuestion (оба грепят GOSLEEP_HOOK_DEBUG_LOG) — надо проверить, unconditional ли debug-write, или он гейтится на «outcome=allow» happy-path.
