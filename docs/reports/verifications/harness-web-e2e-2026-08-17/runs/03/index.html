1 GSL-TBD MINOR Fleet card / server functionality

current_tool / current_intent don't clear after the intercepted tool call completes

After a real fixture fires AskUserQuestion, the shim intercepts, the panel answers, and Claude proceeds to status=idle. The Fleet card's Current tool and Intent fields, however, stay pinned to AskUserQuestion / AskUserQuestion pending owner answer — indefinitely, until the next observed tool call overwrites them. This is a live server-side value, not a client cache: a raw curl /fleet shows the same string.

Reproduction: launch the fixture, prompt it to AskUserQuestion, answer via the panel, wait for Claude to return to prompt, then 

curl -sf -H "Authorization: Bearer $TOK" http://127.0.0.1:7368/fleet \
  | jq '.sessions[] | select(.name=="e2e03-c3") | {status, current_tool, current_intent}'

 → {"status":"idle","current_tool":"AskUserQuestion","current_intent":"AskUserQuestion pending owner answer"}.

Root cause: tools/hooks/tool-observed-feed.sh only fires from PreToolUse; there is no matching PostToolUse hook (or shim-side reset call) that writes a null observation once the question terminates. Compare run-02 m-3 (client-side stale label) — that was resolved for the label but the underlying data source keeps the stale value.

Owner impact: cosmetic only — the card still shows the true status transition (busy → idle) and the CURRENT TOOL string is the LAST observed tool, which is arguably useful history. But it looks stuck.

2 GSL-TBD MINOR Submit task dialog design

Submit-task dialog gives no warning when the target session has an open question

With the fixture parked on a pending AskUserQuestion (long-poll active in the shim), opening Submit task on the same session's Fleet card produced the normal preview modal — no banner, no chip, no colour cue. Sending from the modal succeeded (outcome=delivered) and Claude Code queued the text under “Press up to edit queued messages” until the question resolved.

The behaviour itself is defensible (the message queues, no data lost, Claude processes it after the answer), but the owner has to know this at the terminal to interpret their action: if they intended the text as an answer to the question, it would silently miss the AskUserQuestion tool_input and end up as a follow-on prompt. A small info banner on the modal (“This session has an open question — the text will queue until the question is answered.”) would close the gap.
