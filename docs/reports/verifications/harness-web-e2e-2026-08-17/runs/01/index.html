1 verifier MAJOR Observer / session_control registration functionality

Shim heartbeat POST silently fails to register the live fixture; Take-control is unusable until session_control is seeded by hand

Failure scenario. A newly-launched fixture (Claude Code 2.1.233, GOSLEEP_WEB_QUESTIONS=1, GOSLEEP_INTERNAL_SECRET matching the running core, GOSLEEP_CORE_URL=http://127.0.0.1:7361) successfully processed three AskUserQuestion round-trips through the panel (A1, A2, A3 — questions posted, answered, answers echoed back to the fixture). The /internal/questions/post path clearly reached the core with the correct secret and Host. Yet session_control stayed empty:

sqlite> SELECT * FROM session_control;
(no rows)

Panel action POST /actions/sessions/<sid>/take-control refused with "session_id 53eb568b-… not found in session_control — shim has never checked in". Only after I manually POSTed /internal/sessions/<sid>/shim-heartbeat with the exact body the gate emits ({"pid":23086,"env_opt_in":true}) did the row appear and Take-control begin working (state=controlled, source=env, activated_by=shim-env). Release-control was correctly refused as env-locked per the runbook §8 reframing note.

Impact. The default onboarding path — "start a session with the env flag, watch it appear in Observed, click Take control" — appears to work for questions but silently leaves the runtime-toggle side inert. Phase C task submission requires state=controlled, so this defect also blocks Lane D via the "recommended path" the panel dialog implies.

Root-cause hint (not verified end-to-end). The shim runs its heartbeat as a detached background subshell (( curl … ) < /dev/null >/dev/null 2>&1 & — GSL-368 shape). That form intentionally swallows every error and never re-tries. If any single component (INTERNAL_SECRET, CORE_URL, HOST_HEADER) fails to reach the sub-shell env, the POST is lost and no operator-visible log line ever fires. My manual POST with the exact same headers succeeded, so the endpoint itself is fine; the loss is between the shim's foreground scope and the backgrounded curl. Recommend a per-invocation debug line ("hb_ok" / "hb_fail http=<code>") in GOSLEEP_HOOK_DEBUG_LOG even for backgrounded heartbeats — silence today is indistinguishable from success.

Recommended fix. Either (a) fire the heartbeat synchronously before returning from the shim (the added latency is a couple of ms on the loopback, and the shim already survives a ~100 ms budget on cold start), or (b) keep it backgrounded but tee its outcome into the debug log with a probe curl fallback. Add a smoke that asserts session_control gains a row within N seconds of a hook invocation.

2 verifier MAJOR Task submission — default framing functionality

Default prompt-boundary framing refuses every submission to a live Claude Code 2.1.233 session — recommended path is broken

Failure scenario. From the fresh Submit-task dialog on the fixture's Fleet card, I typed a 92-byte body, accepted the recommended framing "Wait for prompt (default, 5 s ceiling)", ticked the two acknowledgements, and hit Send. The task_submissions row landed with outcome='not_at_prompt', error "pane not at prompt after 5000 ms wait", and no text ever left for the tmux pane. Repeating the exact same submission with framing switched to none (send verbatim) delivered the text and the fixture acted on it.

Root cause (verified). isPaneAtPrompt() in apps/core/src/sessions/submit.ts reads pane_current_command from tmux_panes and expects one of {bash, zsh, fish, sh, dash, ksh, tcsh, csh, claude}. On the fixture pane, both tmux display-message -p '#{pane_current_command}' and the row cached in tmux_panes return 2.1.233. Claude Code 2.1.233 sets its process argv so that its command name reads as its version string, not "claude"; the allowlist misses it and the wait times out every time.

Impact. This is the "recommended default" the dialog focuses. An owner following the happy path — enable Phase C, open the dialog, type the task, hit Send — will get 100% not_at_prompt refusals with a message ("pane not at prompt after 5000 ms wait") that does not explain what to try instead. The failure is silent from the fixture side (no text ever lands) and only recoverable by knowing to switch to none. The task_submissions row is written correctly and a task.submit.failed timeline event fires — the observability is intact — but the primary user path is broken until either the executor's allowlist widens (add the version-shaped tag, or match a "claude*" prefix, or read the parent process command instead), or the dialog changes its default to none for CC sessions, or the runbook / dialog copy warns the operator.

3 verifier MINOR Observer attribution — parent-cwd false match functionality

Fleet / Observed attach unrelated parent-cwd sessions to the fixture's tmux pane (parent-dir false match)

Failure scenario. The fixture pane e2e01-fixture:@47.%431 only contains a single claude 2.1.233 process (pid 24044, session id 53eb568b-…, cwd = .claude/worktrees/e2e01). Yet GET /fleet attributes three sessions to that pane:

53eb568b  e2e01-75            pid=24044  cwd=.claude/worktrees/e2e01     ← the real fixture ✅
5abd9a22  observed:gosleep    pid=None   cwd=.claude/worktrees/e2e01     ← the orchestrator, NOT in this pane
2e5a1372  observed:gosleep    pid=42722  cwd=/…/gosleep (repo root)      ← unrelated, cwd is a PARENT of the pane's cwd

The 2e5a1372 row is the classic parent-dir false match: its cwd sits above the pane's real cwd in the tree, so it cannot possibly be the process running in that pane, yet the heuristic still binds it there. The brief called out "pidtree primacy — no sibling-dir false matches" as the fix — this run shows the primacy is not upheld for the parent-dir case.

Secondary observation. Several observed sessions in /fleet are returned as duplicate rows (once with a real pane ref, once with e2e01-fixture:@47.%431) — likely the same JOIN emitting one row per candidate attribution. Consumers of /fleet that dedupe on session_id will render one card, but any counter or list that trusts row count will over-report.

Impact. The panel lists ghost sessions on the fixture card, cluttering the Observer view and making Take-control mis-target trivially possible. Attribution should discard candidates whose cwd is not equal-to or a strict descendant of the pane's true cwd (from pidtree), never a strict ancestor.

4 verifier MINOR Questions — defer / reopen functionality

A deferred question cannot be answered before its defer_until; there is no /reopen endpoint (and no button)

Failure scenario. After deferring a question with the 5 min preset (defer_until = opened_at + 300 s, exact to the second — the math itself is correct), an attempt to answer it before the timer elapses returns:

POST /actions/questions/answer   { qid: "q-…-003", answer: "OK-A" }
→ 400  question q-2026-08-16-003 is not open (status=deferred)

The panel itself surfaces no "reopen now" affordance on the deferred card, and there is no /actions/questions/reopen endpoint in the codebase (grep -n reopen apps/core/src/routes/actions.ts returns only comments about the auto-reopen worker). The only paths back to open are (a) wait for the auto-reopen worker to fire at defer_until (verified to work — this run recovered that way), or (b) UPDATE the row in SQLite.

Impact. An owner who defers by mistake, or wants to answer sooner than the preset, is stuck. This is a small workflow gap, not a functional break — the primary flow (defer + auto-reopen) works. Recommend either a "Reopen now" button on deferred cards, or accepting /actions/questions/answer on status=deferred as an implicit reopen-then-answer.

5 verifier MINOR Questions — variant-click affordance design

List-level variant buttons open the answer modal (with the option pre-filled), not a one-click submit — contradicts the "click a variant to answer" hint

Failure scenario. The Questions list on the panel shows each option as a button under the hint "click a variant to answer" (see A1 screenshot). Clicking one does NOT submit — it opens the "Answer q-…" modal with the option pre-loaded into the textarea. The modal then repeats the variant buttons under the header "PICK A VARIANT (SUBMITS IMMEDIATELY)"; those do submit on one click. So the owner-facing gesture ends up being two clicks instead of the promised one.

Impact. Small. The flow works and is discoverable (the modal is unambiguous). The hint on the list is just misleading. Two options: (a) reword the list hint to "click a variant to open the answer dialog with it pre-filled", or (b) make the list-level click actually submit and use the modal only for free-text.
