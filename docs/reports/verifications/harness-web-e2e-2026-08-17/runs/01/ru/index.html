1 verifier MAJOR Observer / регистрация в session_control functionality

Shim-хартбит молча не регистрирует живую фикстуру; Take-control недоступен, пока в session_control не посадить строку вручную

Сценарий сбоя. Свежая фикстура (Claude Code 2.1.233, GOSLEEP_WEB_QUESTIONS=1, GOSLEEP_INTERNAL_SECRET совпадает с ядром, GOSLEEP_CORE_URL=http://127.0.0.1:7361) успешно провела три раунда AskUserQuestion через панель (A1, A2, A3 — вопросы легли, были отвечены, ответы вернулись в фикстуру и она их вывела). Значит путь /internal/questions/post действительно дошёл до ядра с правильным secret и Host. Однако session_control остался пустым:

sqlite> SELECT * FROM session_control;
(нет строк)

Кнопка Take-control (POST /actions/sessions/<sid>/take-control) отклонилась с сообщением "session_id 53eb568b-… not found in session_control — shim has never checked in". Только после ручного POST на /internal/sessions/<sid>/shim-heartbeat с телом, которое посылает gate ({"pid":23086,"env_opt_in":true}), строка появилась и Take-control начал работать (state=controlled, source=env, activated_by=shim-env). Release-control корректно отказал как env-locked согласно reframing-заметке §8 runbook.

Эффект. Стандартный путь «запусти сессию с env-флагом, посмотри её в Observed, нажми Take control» кажется рабочим для вопросов, но тихо оставляет runtime-toggle нерабочим. Phase C submit-task требует state=controlled, так что этот дефект косвенно ломает и ленту D по «рекомендованному» диалогом пути.

Гипотеза о причине (не проверена до конца). Shim шлёт хартбит фонового детач-подшелла (( curl … ) < /dev/null >/dev/null 2>&1 & — форма из GSL-368). Эта форма намеренно глотает любые ошибки и не ретраится. Если хоть один компонент (INTERNAL_SECRET, CORE_URL, HOST_HEADER) не пробросился в подшелл — POST теряется и в логах нет ни одной строки. Мой ручной POST с теми же заголовками прошёл, значит эндпойнт исправен; потеря на участке между foreground shim и backgrounded curl. Рекомендую в GOSLEEP_HOOK_DEBUG_LOG оставлять пометку "hb_ok" / "hb_fail http=<code>" даже для фонового хартбита — сегодня тишина неотличима от успеха.

Рекомендуемая правка. Либо (а) присылать хартбит синхронно до выхода из shim (задержка на loopback — единицы мс, shim и так укладывается в ~100 мс cold-start), либо (б) оставить фоновым, но записывать исход в дебаг-лог с fallback-пробником. Отдельно — smoke, проверяющий, что session_control получил строку в течение N секунд после hook-вызова.

2 verifier MAJOR Submit-task — дефолтная упаковка functionality

Дефолтная упаковка prompt-boundary отклоняет любую отправку в живую сессию Claude Code 2.1.233 — рекомендованный путь сломан

Сценарий сбоя. Из свежего диалога Submit-task на карточке фикстуры во Fleet: тело 92 байта, оставлена рекомендованная упаковка «Wait for prompt (default, 5 s ceiling)», обе галки, Send. Строка task_submissions легла с outcome='not_at_prompt', error "pane not at prompt after 5000 ms wait", в панель ничего не ушло. Повтор с framing=none (send verbatim) — доставлено, фикстура отработала.

Причина (подтверждена). isPaneAtPrompt() в apps/core/src/sessions/submit.ts берёт pane_current_command из tmux_panes и ждёт одно из {bash, zsh, fish, sh, dash, ksh, tcsh, csh, claude}. На фикстур-панели и tmux display-message -p '#{pane_current_command}', и кэшированная строка в tmux_panes отдают 2.1.233. Claude Code 2.1.233 переустанавливает argv так, что имя команды читается как версия, а не «claude»; allow-list мимо, wait каждый раз таймаутится.

Эффект. Это «рекомендованный дефолт», который подсвечен в диалоге. Владелец, идущий счастливым путём — включить Phase C, открыть диалог, набрать задачу, нажать Send, — получит 100% not_at_prompt с сообщением ("pane not at prompt after 5000 ms wait"), которое не подсказывает, что делать. От фикстуры не приходит никаких сигналов (текст не долетел), восстановиться можно только зная о переключении на none. Строка task_submissions и событие task.submit.failed пишутся корректно — обзервабилити цела — но первичный путь пользователя сломан, пока не расширят allow-list в executor (добавить «version-shaped» тег, matched-by-prefix "claude*", читать команду родителя), или пока диалог не сменит дефолт на none для CC-сессий, или runbook / текст диалога не предупредит оператора.

3 verifier MINOR Атрибуция observer — parent-cwd false match functionality

Fleet / Observed привязывают к фикстур-панели чужие сессии с cwd в родительской папке

Сценарий. Панель фикстуры e2e01-fixture:@47.%431 содержит один единственный процесс claude 2.1.233 (pid 24044, session id 53eb568b-…, cwd = .claude/worktrees/e2e01). Однако GET /fleet приписывает к этой панели три сессии:

53eb568b  e2e01-75            pid=24044  cwd=.claude/worktrees/e2e01        ← настоящая фикстура ✅
5abd9a22  observed:gosleep    pid=None   cwd=.claude/worktrees/e2e01        ← оркестратор, НЕ в этой панели
2e5a1372  observed:gosleep    pid=42722  cwd=/…/gosleep (корень репо)       ← чужая, cwd — РОДИТЕЛЬ панельного cwd

Строка 2e5a1372 — классический parent-dir false match: её cwd находится выше реального cwd панели в дереве, значит она не может быть процессом в этой панели, но эвристика её всё равно туда привязывает. В брифе прямо говорилось «pidtree primacy — no sibling-dir false matches» — для parent-dir случая primacy не выдерживается.

Побочное. Часть observed-сессий в /fleet возвращается дважды (один раз с реальной панелью, второй раз с e2e01-fixture:@47.%431) — похоже, JOIN отдаёт по одной строке на каждый кандидат-мэтч. Клиенты, дедуплицирующие по session_id, покажут одну карточку, но любой счётчик или список, доверяющий строкам, будет завышать.

Эффект. Панель показывает «ghost»-сессии на карточке фикстуры, засоряет обзервер и тривиально ловит Take-control не туда. Атрибуция должна отбрасывать кандидатов, у которых cwd не равен реальному cwd панели (из pidtree) и не является его строгим потомком — никогда не строгий предок.

4 verifier MINOR Questions — defer / reopen functionality

Deferred-вопрос нельзя ответить до defer_until; эндпойнта /reopen нет (и кнопки нет)

Сценарий. После defer с пресетом 5 мин (defer_until = opened_at + 300 с, ровно посекундно — сама арифметика правильная), попытка ответить до срабатывания таймера возвращает:

POST /actions/questions/answer   { qid: "q-…-003", answer: "OK-A" }
→ 400  question q-2026-08-16-003 is not open (status=deferred)

На карточке в панели нет affordance «reopen now», и в коде нет /actions/questions/reopen (grep -n reopen apps/core/src/routes/actions.ts отдаёт только комментарии про worker). Обратно в open два пути: (а) ждать worker'а авто-переоткрытия на defer_until (проверено — сработал), (б) UPDATE строки в SQLite.

Эффект. Владелец, отложивший по ошибке или желающий ответить раньше пресета, застревает. Это небольшой workflow-gap, а не поломка — основной путь defer + auto-reopen работает. Предложение: либо кнопка «Reopen now» на deferred-карточках, либо /actions/questions/answer должен неявно reopen+answer при status=deferred.
