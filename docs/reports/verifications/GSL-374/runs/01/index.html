Findings

1 GSL-374 MINOR stdin peek — size ceiling functionality

session_id peek is bounded to first 4 KiB of stdin — silent fall-through if a large tool_input precedes it

The new pure-shell peek reads only the first 4 KiB of the payload:

LC_ALL=C head -c 4096 "$_GOSLEEP_STDIN_PEEK" 2>/dev/null \
  | LC_ALL=C sed -n -E 's/.*"session_id"[[:space:]]*:[[:space:]]*"([^"]+)".*/\1/p' \
  | head -n 1

The commit comment argues, correctly for today: Claude Code emits session_id in the top of the JSON payload before any large tool_input, so 4 KiB always suffices. The verifier reproduced this: with a hand-crafted 5 KiB question that pushes session_id past byte 4096 (fixture large_first.json), both origin/main and HEAD fall-exit rc=0 identically — no behavioural regression today.

The concern is future-facing, not present: if a future Claude Code version reorders JSON keys or grows the payload preamble (transcript_path, cwd, permission_mode already sit next to session_id), the peek could silently miss it on the runtime-toggle (env=0) path. The gate then reports UNKNOWN and the shim fast-exits — a session opted-in via panel toggle would silently drop back to the TUI dialog with no debug signal to the owner.

Recommendation (non-blocking): either widen the cap to a comfortable ceiling (e.g. 32–64 KiB, still trivial cost) or add a debug-log breadcrumb when the peek returns empty on a non-empty stdin. Neither is required to merge — the change is a strict superset of origin/main today.

2 GSL-374 MINOR stdin peek — greedy regex functionality

sed regex is greedy — .*"session_id"... captures the LAST occurrence when Claude Code emits single-line JSON

Claude Code emits its PreToolUse payload as one long line. The leading .* in the sed regex is greedy — for a single-line input it captures the LAST occurrence of "session_id":"..." in the file, not the first. Today that is a non-issue: any secondary occurrence inside tool_input question text would appear JSON-escaped as \"session_id\" (backslash-quote), which the regex correctly refuses to match (the character before session_id would need to be a bare ", not \"). Verified: fixtures binary.bin and noNL.json both produce identical fast-exit rc=0 byte-for-byte vs origin/main.

The concern is hardening, not exploit: any future path where an unescaped literal "session_id":"..." can appear in tool_input (e.g. a raw text field that Claude Code decides to pass through without re-JSON-encoding, or a nested structure whose string values contain raw JSON) would resolve to the wrong session and let a shim try to reach the core with a stranger's sid. Blast radius is small — the gate returns 404-then-observer and the shim fast-exits — but the intent gets corrupted.

Recommendation (non-blocking): either replace the leading .* with a non-greedy anchor (BSD sed and GNU sed both support -E, but ERE has no non-greedy — a two-pipe grep -o-then-head would be safer) or accept the current shape and document that only the FIRST occurrence should ever appear. Not required to merge — no real Claude Code payload triggers this today.

Heartbeat fd-detach — mechanism, zombies, error silencing

The GSL-368 change is a single-line addition — a < /dev/null > /dev/null 2>&1 redirection on the ( … ) & subshell group. That re-parents fd 0/1/2 for the subshell BEFORE curl exec's, so the child no longer holds the parent shim's stdout pipe — which was the leading hypothesis for the shift-78 9.4 s release-cutover outlier (parent held on its on('close') until every child dropped the write end).

Zombies / orphans: disown stays for bash job-table cleanup; the backgrounded subshell is inherited by init on parent exit and reaped normally. No new zombie risk.

Error silencing: the existing 2>/dev/null || true inside curl was already swallowing all curl errors (correct for a fire-and-forget heartbeat). The outer 2>&1 adds no new silencing — every fd that could carry a diagnostic now points at /dev/null, but nothing was emitting diagnostics to begin with. Consistent with the pre-existing intent.

Residual observation: the dev-history honestly documents that the specific 5–10 % ~3 s bench outlier persists under both heartbeat-off and heartbeat-fd-detach conditions — the fd-detach is a defensible defensive fix for the 9.4 s signature, not a reproduction of it. The verifier concurs and did not re-observe the outlier in n=10 runs.
