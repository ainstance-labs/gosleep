1 GSL-374 MINOR stdin peek — верхний предел functionality

Peek session_id ограничен первыми 4 KiB stdin — тихий fall-through, если большой tool_input идёт раньше

Новый peek на чистом shell читает только первые 4 KiB полезной нагрузки:

LC_ALL=C head -c 4096 "$_GOSLEEP_STDIN_PEEK" 2>/dev/null \
  | LC_ALL=C sed -n -E 's/.*"session_id"[[:space:]]*:[[:space:]]*"([^"]+)".*/\1/p' \
  | head -n 1

Комментарий в коммите утверждает — и на сегодня это верно: Claude Code выдаёт session_id в самом начале JSON-нагрузки до любого большого tool_input, так что 4 KiB всегда достаточно. Проверяющий воспроизвёл это: на подделанной 5 KiB-вопросной нагрузке, где session_id уехал за байт 4096 (фикстура large_first.json), и origin/main, и HEAD fast-exit rc=0 идентично — сегодня регрессии поведения нет.

Замечание про будущее, не про настоящее: если следующая версия Claude Code переставит порядок ключей JSON или разрастит преамбулу (transcript_path, cwd, permission_mode уже соседи с session_id), peek на ветке runtime-toggle (env=0) может тихо промахнуться. Гейт вернёт UNKNOWN, шим fast-exit — и сессия, включённая тумблером из панели, тихо откатится к TUI без диагностического сигнала владельцу.

Рекомендация (не блокирующая): либо расширить лимит с запасом (например, 32–64 KiB — стоимость всё равно копеечная), либо добавить breadcrumb в debug-log, когда peek возвращает пусто на непустом stdin. Мерж этого не требует — сегодня изменение — строгий supersеt origin/main.

2 GSL-374 MINOR stdin peek — жадная regex functionality

sed-выражение жадное — .*"session_id"... захватывает ПОСЛЕДНЕЕ вхождение при однострочном JSON от Claude Code

Claude Code выдаёт PreToolUse-нагрузку одной длинной строкой. Ведущий .* в sed — жадный, и на однострочном входе он захватывает ПОСЛЕДНЕЕ вхождение "session_id":"..." в файле, а не первое. Сегодня это не проблема: любое вторичное вхождение в тексте вопроса из tool_input появилось бы в JSON-эскейпе как \"session_id\" (обратный слэш+кавычка), что regex корректно НЕ матчит (перед session_id должна была бы стоять голая ", а не \"). Проверено: фикстуры binary.bin и noNL.json дают тот же fast-exit rc=0 байт-в-байт, что и origin/main.

Замечание — про упрочнение, не про эксплойт: любой будущий путь, где в tool_input может появиться неэскейпленная литеральная "session_id":"..." (например, свободное текстовое поле, которое Claude Code передаёт без повторного JSON-энкода, или вложенная структура с сырым JSON в строках), разрешится в чужую session_id, и шим попробует пойти в core с чужим sid. Blast radius маленький — гейт вернёт 404/observer, шим fast-exit, — но смысл искажён.

Рекомендация (не блокирующая): либо заменить ведущий .* на негадкий якорь (BSD sed и GNU sed оба поддерживают -E, но в ERE нет non-greedy — безопаснее была бы связка grep -o+head), либо принять текущий вид и задокументировать, что появляться должно только ПЕРВОЕ вхождение. Мерж этого не требует — реальный Claude Code сегодня этот путь не активирует.

Heartbeat fd-detach — механика, зомби, глушение ошибок

Изменение GSL-368 — одна строка: перенаправление < /dev/null > /dev/null 2>&1 на группу ( … ) &. Это переносит fd 0/1/2 в /dev/null для subshell ДО exec curl, и потомок больше не держит stdout-pipe родительского шима — а это была ведущая гипотеза 9.4 с outlier на смене 78 (родитель не разрешал on('close'), пока каждый ребёнок не отпустит write end).

Зомби / сироты: disown остался для очистки job-table bash; фоновая subshell после выхода родителя перехватывается init и нормально «жуётся». Новых зомби нет.

Глушение ошибок: уже существовавший 2>/dev/null || true у curl и так проглатывал все ошибки (это корректно для fire-and-forget heartbeat). Внешний 2>&1 не добавляет нового глушения — все fd, куда могла бы уйти диагностика, теперь ведут в /dev/null, но исходно никто ничего в них не писал. Согласовано с исходным замыслом.

Остаточное наблюдение: dev-history честно фиксирует, что конкретный 5–10 % ~3 с bench-выброс сохраняется и без heartbeat, и с fd-detach — fd-detach это защитный фикс для сигнатуры 9.4 с, но не её воспроизведение. Проверяющий согласен и выброс на n=10 не увидел.
