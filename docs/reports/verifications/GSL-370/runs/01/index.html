Findings

1 GSL-370-followup-a11y MINOR Question card options — screen-reader name design

Option button accessible name concatenates label + description + pros + cons

The outer QuestionOptions renders each variant as a bare <button> with no aria-label; the button's accessible name defaults to its concatenated textContent. For a variant like Blue / "Cool and neutral" / +accessible / +brand-aligned / −overused, VoiceOver announces the full string as one utterance, and the leading numeric index ("1.") is spoken too.

Failure scenario. A screen-reader user hearing "1. Blue Cool and neutral plus accessible plus brand-aligned minus overused, button" has to parse the whole payload before deciding to click. On a question with 8 variants that is 8 long utterances.

Recommended fix (post-merge, not a blocker). Add aria-label={opt.label} to the outer variant <button> (and to the in-dialog variant Button). The rest of the metadata still renders inside the button visually, but the primary accessible name becomes just the label; description / pros / cons remain reachable via nested landmarks and visible text.

2 GSL-370-followup-stale-options MINOR Answer dialog — options snapshot lifecycle architecture

Answer dialog holds a captured options snapshot instead of the live row

When the owner clicks a variant on the outer card, the dialog opens with options: normalizeOptions(question.options) materialised into AnswerDialogState. Same at :769 for the raw "Answer" button click. If the underlying question row is subsequently mutated (e.g. an SSE-driven refresh replaces the row's options payload while the dialog is still open), the in-dialog variant row keeps rendering the stale snapshot.

Failure scenario. The write path for question options is not user-facing today, so this is exceedingly unlikely to fire in production; it is a lifecycle smell, not a live bug. Filed for record so a future feature that lets options mutate (e.g. an agent re-poses a question in place) does not silently hit a stale dialog.

Recommended fix (post-merge, not a blocker). Either (a) re-read the live row from the useQuery cache inside the dialog by qid and re-normalise per render, or (b) leave the snapshot in place and document the "options are frozen at open" invariant in a comment above AnswerDialogState.options so any future author knows.
