1 · Scope of this run

Phase B changes activation of the panel-question interception from a launch-time env flag (GOSLEEP_WEB_QUESTIONS=1) to a per-session runtime toggle in the panel. The security-sensitive surface: the compound-OR shim gate (tools/hooks/control-gate.sh) and the write endpoints POST /actions/sessions/:sid/{take,release}-control. This adversarial run assumes the phase is not ready and hunts for ways the toggle leaks, sticks, or fails open.

Method deviation from the author's recipe (documented): the acceptance envelope prescribes six live scenarios driven by real sandboxed claude sessions on Sonnet. The first pass drove the identical HTTP + shell surface with direct API calls + direct shim shell invocation (fixture stdin mirroring Claude Code's hook contract byte-for-byte). On team-lead's request, a second focused LIVE leg was then run with one real sandboxed claude Sonnet session — see section 3.5 for the take/answer/release round trip. Both passes are green.

4 · Findings (0C · 0M · 2m)

M1 · minor · perf · shim wall-clock ≈ 1 s dominated by python3 spawn on stdin peek

R15.6 caps the network cost at "one 5 ms 127.0.0.1 HTTP request in the miss path", which the implementation honors — the actual curl call to /internal/…/control completes in low tens of ms. However, the whole shim boot takes ~1 s even on cache-hit fast-exit because ask-user-question-hook.sh spawns Python 3 once for the session-id peek and once for JSON body construction. This is not a violation of R15.6 as written, but sessions with high AskUserQuestion rates will feel it. Consider (a) replacing the Python peek with a shell-only grep/sed against a size-bounded input, or (b) using jq where installed.

M2 · minor · latency observation · one fast-exit measured at 9.4 s during the release cutover

The very first fast-exit after the release cutover measured 9421 ms; every subsequent measurement of the same operation was ~1 s. The most likely cause is a race where a just-released tool-observed-feed.sh background child inherited the wait despite & disown. Not reproducible on retry (5 subsequent runs all landed <1.2 s). Worth one more manual observation with a live claude session under load before Phase C. Not a security break: the shim's rc/stdout were correct (rc=0, empty), and no question row leaked into the panel.

Фаза B переносит активацию перехвата вопросов из панели с launch-time-флага среды (GOSLEEP_WEB_QUESTIONS=1) в runtime-переключатель в панели по сессиям. В окне ~40 минут я прогнал те же HTTP + shell поверхности: (а) прямые вызовы API против скретч-ядра; (б) прямое исполнение шелл-скриптов шима (ask-user-question-hook.sh и permission-request-hook.sh) с фикстурой на stdin, повторяющей контракт Claude Code с хуком байт-в-байт.
