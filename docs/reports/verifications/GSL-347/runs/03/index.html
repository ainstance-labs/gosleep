6 · Findings

M1 · F16-S6 missing task_submissions row on release-mid-submitMAJOR

Where: apps/core/src/routes/actions.ts lines 2429-2446 (the confirm phase's re-preview short-circuit).

What: The confirm phase calls previewSubmission(getDb(), …) a second time to re-verify state + shim + body_sha256. When the session was released between preview and confirm, previewSubmission returns {ok:false, reason:'session-not-controlled', httpStatus:409}. The endpoint returns that 409 to the client and returns without invoking the executor. Because the task_submissions INSERT lives ONLY inside the executor branch (line 2469-2479), the row is silently missing. The executor itself has a released_mid_submit branch (apps/core/src/sessions/submit.ts lines 445-461), but it is unreachable under the current endpoint wiring.

PRD says (F16-S6): "the confirm POST returns 409 with body {reason: "session-not-controlled"} and does not send. The submission-history row is written with outcome='released_mid_submit'."

Live proof: GET /sessions/sess-f/submissions after F16-S6 → {"submissions":[],"count":0}. See captures/f16-s7-sess-f.json.

Note: The endpoint test at apps/core/test/actions.submitTask.test.ts:348-350 EXPLICITLY asserts rows.c === 0 — the code and its tests intentionally deviate from the PRD's wording. Either the PRD's F16-S6 sentence needs revising ("no history row is written on release-mid-submit; the timeline event stream still records the attempt") or the endpoint needs to insert a row before returning 409. Currently the attempt disappears from both surfaces (no task_submissions row AND no timeline event, because the timeline emit lives in the same executor-only branch).

Failure scenario: Owner presses Send-task in the panel; before the confirm POST arrives, they click Release-control on the same card. The submit returns 409. The submission history drawer for that session shows nothing. The timeline shows nothing. The owner has no record that the attempt happened — R16.6 "every submission is auditable end-to-end" is violated for this outcome class.

M2 · Cross-session Idempotency-Key reuse bypasses R16.3MAJOR

Where: apps/core/src/routes/actions.ts lines 2352-2364 (the cross-endpoint replay guard).

What: The endpoint writes endpoint = \`POST /actions/sessions/:session_id/submit-task session=${sessionId}\` into server_intents.endpoint — INCLUDING the session id. But the replay guard checks only existing.endpoint.startsWith("POST /actions/sessions/:session_id/submit-task"), ignoring the trailing session=<sid>. Any client with the panel Bearer can (a) preview a body against session A, (b) confirm the same body under the same Idempotency-Key against session B's URL, and the endpoint accepts the confirm as a legitimate follow-up. The confirm phase's own guards (previewSubmission re-check + body_sha256 match) pass because the body is byte-identical.

Live proof: Preview verify-adv-cross-sess → sess-a returns resolved_target:verify378-target-a:@38.%412 (see captures/adv-cross-sess-preview.json). Confirm verify-adv-cross-sess → sess-g URL returns 200 with {"submission_id":"b3a86bdb-…","session_id":"sess-g","outcome":"delivered", "pane_ref_at_dispatch":"verify378-target-g:@44.%418"} (see captures/adv-cross-sess-confirm.json). SELECT * FROM task_submissions WHERE session_id='sess-g' after the run shows one delivered row with body_len=18 ("cross-session body").

Impact: R16.3 ("Dry-run preview is mandatory") assumes the owner reviews the specific target's preview (resolved_target, keystroke_bytes, advisory warnings) before authorising the delivery. Under this bug the owner-review contract holds only for the session that was previewed; a crafted or buggy client can reroute the delivery to any other controlled session under the same key.

Fix sketch: Compare on FULL endpoint string (or extract the session=<sid> suffix and compare to the current request's session id). Under mismatch, return the same 409 the cross-endpoint branch returns today.

Panel-in-practice mitigation: SubmitTaskDialog mints a fresh submit-<18 hex> key on every preview cycle (apps/web/src/components/SubmitTaskDialog.tsx lines 73-81) and discards it on body change or dialog close, so the panel-as-shipped never hits this bug. It is a server-side hardening gap, not a live user-facing regression today.

m3 · isPaneAtPrompt whitelist includes node / bunMINOR

Where: apps/core/src/sessions/submit.ts lines 230-249.

What: The prompt-set for the "at prompt?" heuristic includes node, bun, claude. When a Claude session spawns a Bash or Node subprocess to run a tool, tmux #{pane_current_command} may report node (or the shell name) even while the tool is still executing. In that case isPaneAtPrompt() returns true and the submission lands mid-execution, interleaving the owner's typed body with the tool's output. On the receiving Claude, this looks like an out-of-turn user message and may derail the tool call. The prompt-boundary framing was supposed to protect against exactly this.

Fix sketch: Restrict the prompt-set to pure shells (bash/zsh/fish/sh/dash/ksh), and only treat claude as prompt-idle when a paired "claude-idle" signal (e.g. events.claude.awaiting_input) confirms it. Not observed live in this run — the F16-S1 target was a bash pane and prompt-boundary correctly saw bash.

m4 · cwd_project_root empty-string handling in resolvePaneRefMINOR

Where: apps/core/src/sessions/submit.ts lines 177-202.

What: The SQL guards on a.cwd_project_root IS NOT NULL but does not guard on non-empty. A row with cwd_project_root='' would produce heur.pane_current_path LIKE '/%' — matching ANY absolute path. The MAX() aggregation would then return the LEXICOGRAPHICALLY LARGEST pane_ref across the whole tmux_panes table, i.e. a foreign pane. Today the fleet enumerator never writes empty-string cwd_project_root (it writes NULL or the actual toplevel), so the bug is latent. Add AND length(a.cwd_project_root) > 0 or normalise at the writer layer.

6 · Найдёныши

M1 · Отсутствует строка task_submissions при release-mid-submit (F16-S6)MAJOR

Где: apps/core/src/routes/actions.ts строки 2429-2446 (короткое замыкание re-preview в фазе confirm).

Что: Фаза confirm вызывает previewSubmission() повторно, чтобы ещё раз проверить state+shim+body_sha256. Если сессия была released между preview и confirm, previewSubmission() возвращает {ok:false,reason:'session-not-controlled',httpStatus:409}, endpoint отдаёт 409 клиенту и выходит, не запуская исполнителя. INSERT в task_submissions лежит только внутри ветки исполнителя, поэтому строка молча теряется. У исполнителя есть ветка released_mid_submit (submit.ts 445-461), но при текущей проводке endpoint-а она недостижима.

PRD (F16-S6): «confirm возвращает 409… в историю отправок пишется строка с outcome='released_mid_submit'».

Живое доказательство: GET /sessions/sess-f/submissions после F16-S6 → {"submissions":[],"count":0}.

Замечание: endpoint-тест apps/core/test/actions.submitTask.test.ts:348-350 ЯВНО ассертит rows.c === 0 — код и тесты сознательно отступают от PRD. Либо PRD F16-S6 требует переформулировки («строка не пишется на release-mid-submit; timeline-событие фиксирует попытку»), либо endpoint должен писать строку перед 409. Сейчас попытка исчезает с ОБЕИХ поверхностей (нет ни строки в task_submissions, ни timeline-события, потому что timeline emit тоже лежит внутри той же executor-only ветки).

Сценарий провала: Владелец жмёт Send-task; до confirm-POST кликает Release-control. Submit возвращает 409. В шторке истории для этой сессии — пусто. В timeline — пусто. У владельца нет записи о произошедшем — R16.6 «каждая отправка auditable end-to-end» нарушена для этого класса исходов.

M2 · Переиспользование Idempotency-Key между сессиями обходит R16.3MAJOR

Где: apps/core/src/routes/actions.ts строки 2352-2364 (guard от cross-endpoint replay).

Что: Endpoint пишет endpoint = \`POST /actions/sessions/:session_id/submit-task session=${sessionId}\` в server_intents.endpoint — с session id в хвосте. Но guard проверяет только existing.endpoint.startsWith("POST /actions/sessions/:session_id/submit-task"), игнорируя суффикс session=<sid>. Любой клиент с bearer панели может (а) сделать preview тела против сессии A, (b) сделать confirm с тем же ключом и телом против URL сессии B — endpoint примет confirm как легитимное продолжение. Собственные guard-ы confirm-фазы (re-preview + сверка sha) проходят, потому что тело байт-в-байт.

Живое доказательство: см. adv-cross-sess-preview.json (target sess-a) и adv-cross-sess-confirm.json (outcome=delivered в sess-g).

Влияние: R16.3 «Dry-run превью обязателен» подразумевает, что владелец просматривает превью конкретной цели (resolved_target, keystroke_bytes, warnings) перед подтверждением. При этом баге контракт «владелец видел превью» держится только для превьюеной сессии; поддельный или кривой клиент может перенаправить доставку в любую другую controlled-сессию под тем же ключом.

Эскиз фикса: сравнивать полную строку endpoint (или парсить session=<sid> и сверять с session_id текущего запроса). При расхождении — тот же 409, что уже возвращает cross-endpoint-ветка.

Смягчение в текущем UI: SubmitTaskDialog минтит свежий ключ submit-<18 hex> на каждый цикл preview и выбрасывает его при изменении тела или закрытии диалога (SubmitTaskDialog.tsx 73-81), поэтому as-shipped панель этот баг не триггерит. Это server-side hardening gap, не пользовательская регрессия сегодня.

m3 · node/bun в whitelist isPaneAtPromptMINOR

Где: apps/core/src/sessions/submit.ts строки 230-249.

Что: Prompt-set включает node, bun, claude. Когда Claude-сессия запускает Bash- или Node-подпроцесс для tool call, tmux #{pane_current_command} может показать node (или имя шелла) ПОКА tool ещё выполняется. Тогда isPaneAtPrompt() вернёт true и отправка приземлится посреди выполнения, смешавшись с выводом tool-а. На принимающем Claude это выглядит как out-of-turn user message и может сорвать tool call. Фрейминг prompt-boundary должен был защищать именно от этого.
